# 技术路线：小米 14 Pro（澎湃 OS）上的 DSH 手机端

> 目标：在小米 14 Pro 上有一个原生应用，能**实时看到本机 harness 的状态**，
> 并且能**和 harness 实时对话**。
> 硬约束：不 root、不解锁 Bootloader、不刷机 —— 即"不弄坏手机操作系统"。

---

## 1. 先说结论：三层架构

```
┌─────────────────────────── 电脑（Arch Linux）───────────────────────────┐
│                                                                        │
│   dsh web (127.0.0.1:3080)                                             │
│     ├── 原有浏览器 UI（Typert Remote：/api + /api/remote.mux WS）        │
│     └── dsh-phone-bridge  ← 本项目新增，Host 平面 Cordis 插件            │
│           ├── 消费 webServer         → 注册 /phone/* 路由                │
│           ├── 消费 sessionController → list / follow / prompt / cancel   │
│           ├── 消费 jobs / goals / sessionTitle / agentDefaultModel       │
│           └── 对外只讲 JSON + SSE，不讲 Typert 协议                       │
│                                                                        │
└───────────────────────────────┬────────────────────────────────────────┘
                                │  adb reverse tcp:3080 tcp:3080
                                │  （USB 线内，不经过局域网、不监听 0.0.0.0）
┌───────────────────────────────┴────────────────────────────────────────┐
│                        小米 14 Pro / HyperOS 3                         │
│                                                                        │
│   com.dsh.phone （原生 Kotlin + Jetpack Compose）                       │
│     ├── 状态页   ← SSE /phone/events（会话、运行中任务、goal、模型）      │
│     ├── 会话页   ← GET /phone/state                                     │
│     ├── 聊天页   ← SSE /phone/sessions/<id>/live + POST .../prompt       │
│     └── 通知栏   ← 前台服务，同一条 SSE，关着 App 也能看                 │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

一句话：**harness 里加一个桥接插件把内部状态翻译成简单 JSON/SSE，
手机用 adb reverse 通过 USB 直连，App 是原生客户端。**

## 2. 关键取舍（以及为什么不选另外几条路）

### 2.1 为什么不在 Android 上重写 harness 的浏览器协议

harness 的浏览器传输是 **Typert Remote**：`/api` 前缀 + `/api/remote.mux` 上的
WebSocket，带 RPC 信封、schema 校验、事件/瀑布流双向调用、流式端点。

在 Kotlin 里复刻这套协议意味着：

- 把 TS 侧的类型系统手抄一遍，还得跟着上游版本同步；
- 浏览器认证（browser-auth / api-request-trust）要重新实现；
- 任何一次 harness 升级都可能让手机端静默失效。

**代价远高于收益。** 桥接插件只依赖少数几个稳定 Service
（`sessionController` / `jobs` / `goals`），升级时坏在哪一目了然。

### 2.2 为什么不用 WebView 套壳

WebView 加载 `http://127.0.0.1:3080` 确实能"零开发"拿到完整 UI。但它给的
是**浏览器界面**，不是**手机应用**：

- 状态无法进入通知栏、无法做息屏/后台提醒；
- 三指缩放一个桌面布局，触控体验差；
- 想要"打开就停在某个会话"这类手机习惯的交互做不了。

本项目保留了这条路作为兜底（见 §7），但主线走原生。

### 2.3 为什么用 SSE 而不是 WebSocket —— 一个具体的坑

桥接插件有两种装载方式：

| 方式 | 生效 | 生命周期 | 能力边界 |
| --- | --- | --- | --- |
| **静态插件**（生产） | 随 `dsh web` 启动 | 持久 | 完整 Node |
| **动态插件**（开发） | 进程内即时 | 重启即失效 | 受限 ctx，**没有 crypto** |

动态宿主只提供 `ctx / console / btoa / atob / TextEncoder / TextDecoder`
这几个 builtin。WebSocket 握手要对 `Sec-WebSocket-Key` 做 SHA-1 + base64，
**动态宿主里拿不到 crypto**，硬写一个纯 JS SHA-1 既丑又慢。

SSE 只需要一个长连接 + `text/event-stream`，两种宿主都能跑，
Android 侧用 OkHttp 读 body 流按行解析即可（本项目就是这么做的，
连 `okhttp-sse` 依赖都省了）。

实时性上 SSE 与 WebSocket 对本场景没有区别：都是服务端推送。

### 2.4 为什么走 adb reverse 而不是局域网

| | adb reverse（USB） | 局域网直连 |
| --- | --- | --- |
| 暴露面 | 仅手机回环 | 需要 harness 监听 `0.0.0.0` |
| 依赖 | 一根线 | WiFi 必须同网段 |
| 换网络 | 无影响 | 换网即失效 |
| 明文 HTTP 风险 | USB 线内 | 同一局域网可被嗅探 |

`adb reverse tcp:3080 tcp:3080` 让**手机上的** `127.0.0.1:3080` 指向电脑的
`127.0.0.1:3080`。harness 依然只绑回环，不需要任何配置变更；拔线通道即消失。

## 3. 桥接接口（`/phone/*`）

全部 JSON，UTF-8，路径前缀 `/phone`。`token` 为空时不校验。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/phone/health` | 探活，返回 `{ok,name,version,ts}` |
| GET | `/phone/state?max=60` | 整机快照：模型、会话列表、任务、goal |
| GET | `/phone/events` | **SSE**：`hello` 首帧 + 状态变化时推 `state` |
| GET | `/phone/sessions/<id>/history?max=40` | 一页历史消息（已归一化） |
| GET | `/phone/sessions/<id>/live?max=60` | **SSE**：`snapshot` → `messages` / `delta` / `attempt` |
| POST | `/phone/sessions/<id>/prompt` | body `{text}` → 投递用户消息 |
| POST | `/phone/sessions/<id>/cancel` | 打断当前回合 |
| POST | `/phone/new` | body `{cwd?}` → 新建会话 |

### 3.1 数据从哪来

| 桥接字段 | harness 来源 |
| --- | --- |
| `model` | `agentDefaultModel.currentSelection()` |
| `sessions[]` | `sessionController.list()` |
| `sessions[].title` | `sessionTitle.get(session)`（仅活会话） |
| `sessions[].goal` | `goals.get(agent)`（仅活会话，冷会话没有 Agent） |
| `jobs[]` | `jobs.list()` |
| 聊天消息 | `sessionController.follow()` 的开场快照 + 增量帧 |
| 发消息 | `sessionController.prompt({requestId, sessionId, mode:'queue', content})` |
| 打断 | `sessionController.cancel({sessionId})` |

### 3.2 两个实现上的坑（已踩）

1. **`follow` 是 `async *` 生成器**，调用即返回异步迭代器，**不是 Promise**。
   写成 `await sc.follow(...)` 或 `.then()` 会直接失败。
2. **`cancel` 是同步方法**，返回 `SessionCancelValue` 而不是 Promise，
   必须包一层 `Promise.resolve()` 才能统一处理。
3. 动态宿主**没有 `AbortController`**，而这些 Remote 方法都要求传 `signal`。
   桥接里给了一个鸭子类型替身（`aborted` / `addEventListener` / `abort()`），
   实测 DSH 只读 `signal.aborted` 并挂 abort 监听，替身足够。

### 3.3 消息归一化

harness 的会话日志是事件流（`user/message`、`assistant/message`、`tool/call`、
`tool/result`、`turn/start` …），手机不该理解这套领域模型。
桥接把它压成：

```json
{ "seq": 16, "time": 1792043924028, "role": "assistant",
  "text": "收到", "interrupted": false, "usage": {"input": 9531, "output": 2} }
```

`role ∈ {user, assistant, tool, tool-result}`。
用户消息额外带 `source`：`user` 是人说的，`plugin` / `skill-catalog` /
`runtime-context` 是 harness 注入的上下文 —— App 默认**折叠**这些，
避免手机屏幕上刷满系统提示词（可在设置里打开）。

## 4. 装载桥接的两种方式

### 4.1 静态插件（生产，持久）

`bridge/` 是一个标准的 Profile Bundle：

```
bridge/
├── package.json        dsh.bundle.patch → ./cordis.patch.yml
├── cordis.patch.yml    - insert: 一行 phone-bridge
├── lib/index.js        ESM 入口，inject: [webServer, sessionController]
└── bridge-core.js      全部逻辑（宿主无关）
```

安装：

```bash
dsh plugin --profile web add <本仓库>/bridge
# 然后重启 dsh web
```

**为什么必须重启**：web profile 的 `patchReload: startup`，
新增 bundle 只在启动时参与组合。

**为什么它属于 Host 平面**：桥接消费 `webServer` 与 `sessionController`，
服务的是整个进程的 HTTP 面，消费方（手机）在 agent 平面之外。
按 Cordis 的分层规则，这类"发布给会话之外的消费者"的能力必须挂宿主组成，
放进 agent preset 会在第二个会话挂载时冲突。

**为什么补丁层要写 `- insert:`**：`--patch` / bundle patch 默认是按 id
*覆盖已有行*，直接写 `- id: xxx` 会得到
`patch: entry "xxx" not found`。新增行必须显式放在 `insert:` 下。

### 4.2 动态插件（开发，即时）

`bridge/tools/gen-dynamic.mjs` 把 `bridge-core.js` 的函数体原样内联进
`cordis_define` 的 `code.host`，于是同一份逻辑可以在**不重启 harness** 的
前提下立刻上线调试。重启后消失，属于开发路径。

### 4.3 更省的做法：动态加载器（不内联源码）

内联 32KB 源码代价不小（去注释去缩进后仍有 32KB），而且等于在插件定义里
放了桥接的**第二份副本**，两边会走叉。更好的做法是让动态插件当**加载器**：

```js
ctx.effect(function mount() {
  let dispose = null, stopped = false
  Promise.resolve().then(async function load() {
    const fsSvc = ctx.get('fs')
    const target = await fsSvc.resolve(BRIDGE_PATH, {})
    const raw = await fsSvc.readText(target, undefined)
    // 去掉 ESM 的 export，否则 Function 编译报 "Unexpected token 'export'"
    const body = raw.replace(/^export\s+function\s+createBridge/m, 'function createBridge')
    const createBridge = new Function(body + '\nreturn createBridge')()
    dispose = createBridge(ctx, { token: TOKEN })
  }).catch(e => console.error('load failed: ' + e.message))
  return function disposeAll() { stopped = true; if (dispose) dispose() }
})
```

十几行，运行时从磁盘读 `bridge-core.js` 现场编译 —— 桥接逻辑仍然只有一份。

**前提是探测过的，不是想当然**：动态 Cordis 宿主虽然只暴露
`ctx / console / btoa / atob / TextEncoder / TextDecoder`，
但 `new Function` 是 JS 语言本身的能力、并没有被挡；
`fs` 服务也在，能读到宿主机文件。所以先花几十行写个探针插件确认
（实测 `new Function('return 1+1')()` 返回 2、`fs.readText` 读到 43544 字节），
再写加载器。

这条路径的价值：**不用重启正在用的 harness** 就能把桥接挂上真实进程。
重启 `dsh web` 会结束当前对话，所以当用户不想中断工作时，
动态加载器是唯一能立刻用上真实数据的办法。代价是重启后消失 ——
持久生效仍然要走 §4.1 的 bundle 装载。

## 5. Android 端

- Kotlin + Jetpack Compose（Material 3），`minSdk 26 / targetSdk 37 / compileSdk 37`
- 工具链：JDK 21 + Gradle 9.8.1 + AGP 9.4.1 + build-tools 37.0.0
- 唯一的网络依赖是 OkHttp；JSON 用系统自带 `org.json`
- 四个界面：**状态** / **会话列表** / **聊天** / **设置**
- 实时性来自两条 SSE：
  - `/phone/events` → 整机状态（事件驱动推送，另有 3–5s 轮询兜底，
    防止澎湃 OS 的省电策略静默掐断长连接）
  - `/phone/sessions/<id>/live` → 会话内消息与模型输出增量
- 模型输出增量按 chunk 类型累加：`text-delta` 进正文、
  `reasoning-delta` 进思考区；收到定稿 `messages` 帧后清掉草稿并按 `seq` 去重
- 前台服务 `StatusService` 复用同一条状态 SSE，把状态写进常驻通知
  （可选，默认关闭）
- 支持用 intent 直达某个会话，便于脚本/快捷方式/通知跳转：
  `adb shell am start -n com.dsh.phone/.MainActivity --es sessionId <id>`

## 6. "不弄坏手机"是怎么保证的

| 动作 | 是否触及系统 |
| --- | --- |
| `adb install` 一个普通 APK | 等价于手动点安装包，走系统正常安装流程 |
| `adb reverse` | 只在 adb 连接上建端口转发，拔线即消失 |
| `adb shell am start` | 只是启动应用 |
| 请求通知权限 | 系统标准运行时权限弹窗 |
| **没有**：root / 解锁 BL / 刷机 / 改系统分区 / 装 Magisk / 改 build.prop | — |

卸载：`adb uninstall com.dsh.phone`，手机侧设置里"卸载"同样有效。
电脑侧改动只有 `~/.dsh/profiles/web` 里加了一个 bundle（`dsh plugin remove` 可撤销）。

## 7. 已知限制与后续可做

- **`adb reverse` 不稳定**。拔插数据线必然失效；实测在系统重新协商 USB 时也可能被清掉
  （adb transport 重新握手，`adb reverse --list` 变空）。重跑
  `scripts/install-to-phone.sh` 即可恢复。
  长期方案是把 USB 换成局域网直连（App 设置里改地址即可，桥接不用动），
  但那时应把 `/phone` 的 `token` 配上，并把 `dsh web --host 0.0.0.0` 的暴露面想清楚。
  考虑过用 `adb shell input` 做自动化验证，被澎湃的 `INJECT_EVENTS` 限制挡住，
  因此 App 改用截图 + intent 直达会话（`--es sessionId`）来做无人值守验证。
- **掉线时的降级**：聊天页单独维护一个 `chatError`（而不是只靠整机连接状态），
  因为"聊天页空白"和"真的没有消息"看起来完全一样，而掉线是常态。
  掉线时显示横幅并提供「重试」；通道恢复后 SSE 快照会补齐历史，无需重启 App。
- **App 目前不能发图片/附件**。桥接的 prompt 只收 `{type:'text'}`；
  要支持图片得走 `attachments` / `fileUploads`，是明确可加的下一步。
- **不展示 diff / 文件预览 / 工具卡片**。`tool/result` 目前只显示截断文本。
- **WebView 兜底**未实现。若想要"完整 UI 且零维护"，
  加一个 `WebView` 指向 `http://127.0.0.1:3080/?token=...` 即可，成本很低。
- 动态插件路径（§4.2）需要把内联后的代码贴进 `cordis_define`，
  体积约 30KB，属于调试工具而非交付物。

## 8. 复现步骤


## 9. 踩坑清单（都是实测出来的，不是推测）

### 9.1 组合 / 插件侧

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| `patch: entry "xxx" not found` | 补丁层默认是按 id **覆盖已有行**，不是新增 | 新增行必须写在 `- insert:` 下 |
| 动态宿主里 WebSocket 做不了 | 动态 ctx 只给 `ctx/console/btoa/atob/TextEncoder/TextDecoder`，**没有 crypto**，算不了握手用的 SHA-1 | 改用 SSE |
| `sc.follow(...)` 当 Promise 用会失败 | 它是 `async *` 生成器，调用即返回异步迭代器 | 直接 `iter[Symbol.asyncIterator]()` |
| `sc.cancel(...)` 没有 `.then` | 它是**同步**方法，返回 `SessionCancelValue` | 包一层 `Promise.resolve()` |
| 冷会话没有标题，列表全长一样 | 只从 `sessionTitle.get(session)` 取，而冷会话没有 Agent | 改用 `list()` 自带的 `projections.values.title` 投影（持久化，冷热通吃） |
| `AbortSignal` 缺失 | 动态宿主没有 `AbortController` | 给鸭子类型替身（`aborted` + `addEventListener` + `abort()`） |

### 9.2 Android 构建侧

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| `Dependency ... requires AGP 9.1.0 or higher` | 2026 年的 AndroidX（Compose 1.12 / lifecycle 2.11）已经要求 AGP 9 + compileSdk 37 | 升到 AGP 9.4.1 + Gradle 9.8.1 + compileSdk 37，**不要**降库 |
| `The 'org.jetbrains.kotlin.android' plugin is no longer required` | **AGP 9 内置 Kotlin 支持**，再应用 kotlin-android 会直接报错 | 从顶层和模块 build 文件里都删掉它；Compose 编译器插件保留 |
| `Unresolved reference 'icons'` | Compose 1.12 起 `material3` 不再传递引入图标核心包 | 显式 `implementation("androidx.compose.material:material-icons-core")`（BOM 钉版本） |
| `Type annotations are not allowed on destructuring declarations` | Kotlin 语法：解构声明不能带类型标注 | 拆成逐个 `val` |
| `Alignment.Start` 传给 `Box(contentAlignment=)` 编译不过 | `Alignment.Start` 是 `Alignment.Horizontal`，不是 `Alignment` | 用 `Alignment.TopStart` / `Alignment.TopEnd` |
| `gradle ... \| tail` 返回 0 却其实失败了 | shell 管道取的是 `tail` 的退出码 | 重定向到日志再读，或 `set -o pipefail` |

### 9.3 澎湃 OS 侧（都是系统限制，不是代码问题）

| 现象 | 系统设置 |
| --- | --- |
| `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user` | 开发者选项 → **「USB 安装」/「通过 USB 安装」** 打开（可能要求登录小米账号）。不开的话用文件管理器手动点安装包也可以 |
| `adb shell input tap` 报 `SecurityException: ... INJECT_EVENTS` | 开发者选项 → **「USB 调试（安全设置）」** 打开。不开的话无法用脚本模拟点击，只能手动操作手机 |
| 拔插数据线后 App 连不上 | `adb reverse` 是 adb 连接级的，拔线即失效；重跑 `scripts/install-to-phone.sh` |

## 10. 外网访问：为什么是 Tailscale，以及它在这台机器上的三个坑

需求从"插着线用"变成"人在外面、电脑在家"之后，USB 那条路就不够了。
公网可达有三条路：Tailscale / Cloudflare Tunnel / IPv6 直连。
选了 Tailscale，理由是它 CGNAT 可达、端到端加密、地址固定、且**不把 harness 暴露到公网**
（README 里写了对比）。落地过程中遇到三个必须记下来的坑。

### 10.1 坑一：控制面域名被 DNS 污染

```
$ getent hosts controlplane.tailscale.com
2001:2::fc      controlplane.tailscale.com     <- 封锁用的黑洞地址
$ curl https://controlplane.tailscale.com/key?v=148
000 (20s 超时)
$ curl -x http://127.0.0.1:7897 https://controlplane.tailscale.com/key?v=148
200                                            <- 走本机代理就通
```

真实地址在 `192.200.0.0/24`（通过 DoH 查得 192.200.0.101~116），
直连这些 IP 是可以的，所以**问题只在 DNS**。

`tailscaled` **不认 `HTTPS_PROXY` 环境变量**（试过，仍报
`fetch control key: context deadline exceeded`）。
最终解法是给它挂上本机 HTTP 出口：

```ini
# ~/.config/systemd/user/tailscaled-userspace.service
Environment=HTTPS_PROXY=http://127.0.0.1:7897
```

挂上之后日志出现 `Switching ipn state Starting -> Running`，netmap 才拿得到。

### 10.2 坑二：免 root 只能用 userspace 模式，于是只能用 serve

这台机器 `sudo` 要密码，所以走 **userspace-networking**：`tailscaled`
不建 TUN、不改内核路由、不碰 `/etc/resolv.conf`。
代价是「tailnet IP 不是本地网卡地址，没法直接 bind」，
入站只能靠 `tailscale serve` 在进程内代理。

`serve` 的 HTTPS 模式失败了：

```
error enabling https feature: ... Post "https://unused/machine/feature/query":
all connection attempts failed
```

（控制面 feature 查询走不通，跟 10.1 同源。）
所以改用 **纯 TCP 转发**：

```bash
tailscale serve --bg --tcp=3080 127.0.0.1:3080
# |-- tcp://dsh-home.<tailnet>.ts.net:3080 (tailnet only)
```

TCP 层没有 TLS，但整条链路已经是 WireGuard 端到端加密，
所以 App 侧对 tailnet 地址放行明文是安全的（见 `network_security_config.xml`
的注释）。**不要**因为"没 TLS"就以为内容会裸奔。

### 10.3 坑三：对称 NAT，但 IPv6 救了一命

`tailscale netcheck` 的关键几行：

```
* UDP: true
* IPv4: yes, 101.82.168.86:23023          <- 联通上海的真实出口
* IPv6: yes, [240e:46c:...]:50340
* MappingVariesByDestIP: true             <- 对称 NAT，UDP 打洞基本无望
* Nearest DERP: Los Angeles 303ms         <- 中继都在境外
```

对称 NAT 意味着 IPv4 打洞失败，只能走 DERP 中继，而最近的也在洛杉矶 300ms+。
但**两边都有全局 IPv6**，于是实际跑起来是这样：

```
$ tailscale ping <phone>
pong from <phone> (<tailnet-ipv4>) via [<tailnet-ipv6>]:40895 in 58ms
```

手机用自己的蜂窝 IPv6、电脑用家宽 IPv6，**打洞成功走直连，58ms**。
这是本次最幸运的一点：中国的联通/电信蜂窝与家宽普遍有全局 IPv6，
只要两边都有，Tailscale 就能绕开对称 NAT 和境外中继。

### 10.4 顺带做的加固与 App 改动

| 改动 | 原因 |
| --- | --- |
| `/phone/*` 强制令牌 | 一旦离开回环，令牌是唯一门禁。实测无令牌/错令牌 401，正确令牌 200（含走 tailnet） |
| App 端点改成**有序列表** | "在家 USB、在外 tailnet"要自动切换，不能靠人手改地址 |
| `BridgeClient.probe()` 用 2.5s 短超时 | 默认 8s 连接超时下，在家试第一个端点会白等，出门试 USB 端点更会卡住 |
| 每次操作/每次 SSE 重连都重新解析端点 | 从家里出门（USB 断、tailnet 通）能自动切过去，反之亦然 |
| intent 预置 `endpoints` / `token` | 澎湃的 `INJECT_EVENTS` 限制让脚本没法模拟点击，只能靠 intent 灌配置 |

### 10.5 手机侧还有一个必须交代的前提

Android 的 `VpnService` 是**按 UID 路由**的，`adb shell` 的流量不走 VPN。
所以"从手机 shell 里 curl 一下 tailnet 地址"验证不了任何东西 ——
必须让 App 自己去连。这一点浪费过一次排查。

另外，手机上必须把 Tailscale 设为「始终开启的 VPN」并关掉电池优化，
否则澎湃 OS 会在后台杀掉它，表现为 App 突然连不上（`tailscale status` 里
手机变成 `offline, last seen Nm ago`）。

## 11. 工作区（项目文件夹）：harness 已有的那一层，别再造一套

需求里「新建文件夹 + 创建 harness 工作区 + 看历史工作区」正好对上 harness
自带的 `workspaceRegistry` / `workspaceController`，所以桥接只是把它翻出来，
没有自己造目录模型。

### 11.1 数据从哪来

`workspaceRegistry.list()` 同步返回durable 顺序的工作区，
每个带 `path` / `title` / `sessionIds[]` / `createdAt` / `updatedAt`。
`sessionIds` 是 harness 按 canonical-cwd 索引过滤好的 —— **直接用，不要自己按
cwd 匹配**，否则两边规则一旦不同就会不一致。

### 11.2 三个实测出来的坑

**坑一：`create({cwd})` 建的会话不会挂进工作区。**

| 建会话方式 | 挂进工作区 |
| --- | --- |
| `{ workspaceId }` | 会 |
| `{ cwd }` | 不会 |

只带 `cwd` 的会话能正常跑，但在工作区列表里看不见 —— 界面上像是"丢了"。
解法：给 `cwd` 时先 `workspaceRegistry.resolveByPath(cwd)` 反查再带上 id。

**坑二：`workspaceRegistry.create(path)` 只收已存在的目录。**
它内部走 `fs.realpath`，路径不存在直接 reject。所以"新建文件夹"必须
先 mkdir，再登记工作区，再开会话 —— 三步，顺序不能换。

**坑三：mkdir 会被沙箱静默丢弃。**
组合里 `sandbox-policy` 的默认值是：

```yaml
- id: sandbox-policy
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
    workspaceRoot: !!js process.cwd()
```

工作区目录通常在 `process.cwd()` 之外，于是 `shell.run` 里的 `mkdir`
**退出码 0 但文件没建出来**（沙箱是 partial enforcement，写入被吞掉）。
桥接做了两件事：显式传 `sandboxPolicy: { mode: 'danger-full-access', ... }`，
以及建完用 `fs.stat` 复核 —— 不信退出码。

### 11.3 目录浏览为什么不走 directoryPickerController

它看着最合适（`list` / `createDirectory` 就是为这个设计的），
但这台机器的组合装的是 `dsh-host-directory-picker-auto`，
在桌面 Linux 上选了 **native** 后端，于是：

```
directoryPicker.list needs the browse capability; the composed picker serves "native"
```

harness 的设计是"组合不能提供的动词就明确拒绝，而不是糊弄过去"。
所以桥接改用自己的两条路：

- **浏览**：`fs.resolve(path)` + `fs.listDir(target)`（`fs` 服务两种宿主都有）
- **新建**：优先 `directoryPicker.createDirectory`，不可用则退回 `shell` 执行 `mkdir`

走 shell 就必须自己把关，因为命令是字符串而不是 argv 数组：

```js
// 只接受绝对路径、拒绝 .. 段；名字只接受单个路径段
// 然后 POSIX 单引号转义，再拼进命令
'mkdir -p -- ' + shellQuote(target)
```

实测 `"x; touch /tmp/PWNED"` 这种名字在名字校验阶段就被拒了，
`/tmp/PWNED` 没有被创建。

## 12. 用户提问（ask_user_question）在手机上的接入

### 12.1 坑：瀑布是按 agent 作用域派发的，根监听器收不到

最直觉的写法是监听那个瀑布事件：

```js
ctx.on('user-questions/request', function (request, next) { ... })
```

**实测收不到** —— 诊断计数一直是 0。原因是 `ask()` 的派发：

```js
this.ctx.waterfall(scopeTarget(agent, agent), 'user-questions/request', {...}, noAnswerer)
```

带 agent 时它派发到 **agent 自己的作用域**上，注册在根上下文上的监听器不在那个
作用域里。（浏览器 UI 的回答者是通过 `typertGateway.registerRemoteEvents`
按 agent 注册的，所以它能收到。）

### 12.2 解法：把 `userQuestions.ask` 包一层

绕开作用域问题，语义还更直白：

```js
const uq = ctx.get('userQuestions')
const original = uq.ask
uq.ask = function (request) {
  return askPhoneFirst(request, function () { return original.call(uq, request) })
}
```

- 手机正开着那个会话 → 推给手机，等回答
- 没开 / 超时 / 中止 → `original.call(...)`，浏览器 UI 照常接管

**只在手机真的开着该会话时才拦截**，所以你人在电脑前时不会有额外延迟。
"开着"的判断来自 App 打开聊天页时建立的那条 `/live` 流 —— 不需要额外的心跳接口。

清理时把 `ask` 还原（`disposers` 里存了 restore 函数），插件卸载后不留痕。

### 12.2bis 判断"手机在看"必须用心跳，不能用连接是否开着

第一版用"`/live` 连接还在吗"来判断，**有个 180 秒的坑**：

手机静默掉线（App 被杀、蜂窝断、没发 FIN）时，那条 TCP 连接可能挂很久才被系统
回收。这期间桥接以为手机还在看，把提问推给一条死连接，**电脑要干等满超时**。

改成**心跳新鲜度**（`WATCH_TTL_MS = 15000`）：

- 心跳搭在 App 本来就有的 `/phone/state` 轮询上 —— `?watching=<sessionId>`，
  不额外加请求
- 心跳一停，最多一个 TTL 之后就不再算"在看"
- 待回答问题还会在心跳失效后 **3 秒**就交还电脑，不等满超时

**实测**（直接 `am force-stop` 模拟静默断开）：

```
+4s  watched=[...]   +8s  watched=[...]   +12s watched=[...]   +16s watched=[]
```

**还有一个同源的坑**：App 退到后台时轮询仍在跑，心跳会继续，
提问就被推给一个用户看不见的屏幕。所以心跳要求**同时满足**「App 在前台」
和「开着那个会话」。前台判断用 `Activity.onResume/onPause` 打标志位
（避开 Compose 生命周期 API 的版本差异）。

三层保证合起来：

| 情况 | 结果 |
| --- | --- |
| 手机在看 | 提问只弹手机，电脑不弹 |
| 手机没开聊天页 / 在后台 | 提问立刻走电脑（同步 fallback） |
| 手机静默断开 | 最多 16 秒后走电脑 |

### 12.3 顺带修正的呈现问题

原来的 `deriveMessages` 把 reasoning 用 `"[思考] "` 前缀**塞进正文**，
既难读也和电脑上的呈现不一致。现在：

| 字段 | 含义 |
| --- | --- |
| `text` | 正文（只含 text / image / file / tool-result 块） |
| `reasoning` | 思考过程，独立字段 —— 手机上渲染成可折叠的独立区块 |
| `title` | 工具调用的一行摘要（`command` / `file_path` / `query` …） |

工具卡片因此能一眼看出"干了什么"，完整参数收在"参数"折叠里，
和电脑上的卡片是一个意思。

### 12.4 `/phone/diag`

排查"手机上没收到提问"这类问题用的自检接口，直接暴露内部状态：

```json
{ "watchedSessions": [...], "sessionStreams": [...], "pendingQuestions": [...],
  "questionEventCount": 1,
  "lastQuestion": { "sid": "...", "watched": true, "intercepted": true, ... } }
```

`questionEventCount` 为 0 就是"监听器压根没被调用"（12.1 那个坑），
`watched` 为 false 就是"手机没开着这个会话"。

## 13. 反向：让电脑能通过网络调试手机

前面所有通道都是**手机连电脑**。要反过来（电脑 `adb` 连手机），
有两个各自独立的障碍：

1. **内核没有到 tailnet 的路由。** tailscaled 跑在 userspace 模式（为了免 root、
   不建 TUN），所以只有它进程内部的 `serve` 能接收入站 —— 本机 socket 到不了
   `100.x.x.x`。
2. **adb 不支持 SOCKS。** 而 userspace 模式下唯一能主动出站到 tailnet 的路径
   就是 tailscaled 的 SOCKS5 出口。

解法是两者之间加一层用户态 TCP 桥（`scripts/tailnet-tcp-bridge.py`，
纯标准库）：本地端口 → SOCKS5 → tailnet 目标。然后
`adb connect 127.0.0.1:<本地端口>` 即可。

再配合手机上 `adb tcpip 5555`（只需在 USB 上执行一次），
之后拔线也能调试。全流程在 `scripts/adb-over-tailnet.sh` 里。

**安全提醒**：`adb tcpip` 会让 adbd 监听**所有网卡**，不只是 Tailscale。
手机连公共 WiFi 时，同网的人可能连上 adb（等于 shell）。
不用时执行 `scripts/adb-over-tailnet.sh off` 切回 USB 模式。

## 14. 未读回复提醒

### 14.1 harness 没有「已读」概念，别去找

翻遍了 `*.d.ts`：所有 `unread` 命中都是"文件不可读"，没有任何服务端已读状态。
**这是对的** —— 已读天然是每个观察者自己的状态，不该写进共享的会话存储。

所以分层：

| 谁 | 负责什么 |
| --- | --- |
| 桥接（电脑） | 提供**判断依据**：每个会话最后一次助手回复 / 最后一次人提问的 seq 和时间 |
| App（手机） | 保存已读 watermark（SharedPreferences），算未读、出角标 |

会话存储仍然只在电脑上；已读是手机侧的小状态，换手机重装就重新计未读。

### 14.2 判断依据怎么来

两路合并：

1. **实时**：`session/event` 火线。
   注意它和 §12.1 那个瀑布不一样 —— 瀑布按 agent 作用域派发、根监听器收不到，
   而这个火线**能**到根监听器（实测计数在涨，带 `session-…` 和 `tool/call`/seq）。

2. **回填**：挂载时对最近 7 天活跃、且尚未被实时跟踪到的会话（最多 60 个）
   串行读一次日志尾部（`follow({maxMessages: 8})`，拿完即关）。
   没有这步，"挂载之前就已经存在的未读回复"就看不出来。

只认 `user/message` 里 `source.kind === 'user'` 的 —— harness 注入的运行时提醒、
技能目录那些不算"人提问"，否则每个会话都会被判成"助手在最后说话"。

### 14.3 未读的定义

```
未读 = 助手最后说话(agentSpokeLast)   // lastReplySeq > lastUserSeq
     && lastReplySeq > 手机已读 watermark
     && lastReplyAt 在 7 天窗口内
```

「助手最后说话」比单纯"有新事件"准得多：如果最后一条是人提问、助手还没答，
那不该提醒你（是你在等它）。

**标记已读**的判定集中在 `refreshUnread()` 里：
「App 在前台 && 正开着这个会话」就写入 watermark。放在一处，
就不会出现"某个入口忘了标已读、角标永远消不掉"。

### 14.3bis 但光有"集中"不够 —— 时机错了照样漏标

第一版只在 `refreshUnread()` 里标，而它要等状态（5s）或工作区（20s）刷新后
才知道那个会话的 `lastReplySeq`。**用户点进去看一眼、几秒内就退出 ——
还没等到那次刷新，watermark 从来没写进去**，表现就是"点过了还是未读"。

实测：点进去等 **30 秒**才写进 prefs。这不是偶发，是必然。

修法是两件事：

1. **维护一张"已知 activity"表**（只增不减），`refreshUnread()` 每次
   从状态和工作区往里灌。查找时优先读它。
2. **在打开和关闭的瞬间各标一次**（`openSession` / `closeSession`），
   不再依赖轮询。

这样从"必须停留到一个轮询周期"变成"点下去就标"。
实测：热状态下点进一个未读会话，**3 秒**后 prefs 里已有
`seen_session-…=2520`。

教训是通用的：**"什么时候"和"在哪算"一样重要。** 只把逻辑收敛到一处，
但如果那一处只在低频路径上被触发，对用户来说就等于没生效。

### 14.4 一个自找的对不上

第一版角标显示 21、区块只列 20 —— 因为角标把 `/phone/state` 里那 60 条最近会话
也算进去了，而区块遍历的是全部工作区。**两边必须同源**：
统一只以工作区为来源（它还更全）。这种"两处各算一遍"的分歧是 UI 里最容易漏的。

### 14.5 通知栏

`StatusService`（可选，默认关）每分钟拉一次工作区算未读，
写进常驻通知的正文和展开区。它和 App 内**共用同一份已读 watermark**，
所以在 App 里点开过的，通知栏也不会再算未读。

## 15. Markdown 渲染与可点链接

### 15.1 为什么自己写

手机上原来把 `**粗体**` 原样显示 —— harness 的正文是 markdown，得渲染。
没有引第三方库：Compose 1.12 / AGP 9 这一代里现成的 markdown 库大多还没跟上，
版本一冲突就是整包编不过；而需要的规则本身并不复杂。

`ui/Markdown.kt`，纯 Compose 原生，约 300 行。

### 15.2 链接靠 LinkAnnotation，不自己发 Intent

```kotlin
withLink(LinkAnnotation.Url(url, TextLinkStyles(SpanStyle(
    color = linkColor, textDecoration = TextDecoration.Underline,
)))) { append(label) }
```

**不给 `linkInteractionListener` 时，点击会落到平台的 `UriHandler`**，
也就是系统默认浏览器 —— 正是要的效果，而且不用自己拿 Context 发 Intent。

只认 `http://` / `https://`：`intent://`、`javascript:` 这类 scheme 不进链接，
免得一个消息就能触发任意组件调用。

行内解析是**手写扫描而不是正则**：标记会互相嵌套（`***粗斜体***`、链接文字里带
`` ` ``），一个正则塞多组很快就不敢改了。

### 15.3 实测踩到的两个

**坑一：`***粗斜体***` 会渲染成字面的 `*粗斜体*`。**
因为 `**` 分支先命中，吃掉了前两个星号，剩下 `*x*` 当一个星号处理。
三星号的分支必须排在两星号**之前**。

**坑二：测试方法本身会骗人。**
用 `adb shell am start --es send '...'` 发测试样本时，
样本里的**反引号被设备 shell 当命令替换执行了**，消息被吃掉大半，
看起来像"渲染坏了"。第一版截图里我只写了 `` `**粗体**` ``（把 markdown 样本
包在反引号里），结果原样显示其实是**正确**的 —— 白白怀疑了一轮。

教训：**用会被两层 shell（本机 bash + 设备 sh）解析的通道传测试样本，
先确认样本原样到达**，否则你验证的是通道不是功能。

### 15.4 覆盖范围

| 语法 | 支持 |
| --- | --- |
| `**粗体**` / `__粗体__` | ✅ |
| `*斜体*` / `_斜体_` | ✅ |
| `***粗斜体***` | ✅ |
| `` `行内代码` `` | ✅ 等宽 |
| `~~删除线~~` | ✅ |
| `[文字](url)` / 裸链接 | ✅ 可点，走系统浏览器 |
| `#` ~ `######` 标题 | ✅ 逐级加大 |
| `-` / `*` / `1.` 列表 | ✅ 保留有序编号 |
| `>` 引用 | ✅ 左侧竖条 + 斜体 |
| ``` 代码块 ``` | ✅ 带底色 + 等宽 |
| `---` 分隔线 | ✅ |
| 表格 | ✅ 见 §15.5 |
| 图片、脚注 | ❌ 未做（会原样显示） |

### 15.5 表格

Compose 没有内置表格控件，用 `Row` + 每格 `Modifier.weight(1f)` 拼了一个：

```
│ 语言    │   用途   │   年份 │   ← 表头（加粗 + 底色）
├─────────┼──────────┼────────┤
│ Kotlin  │ 安卓开发 │   2011 │
```

- **列宽按内容量**，不搞等分：用 `TextMeasurer` 把每个单元格量一遍，
  取该列最大值（夹在 48dp ~ 220dp 之间）。等分列宽会把长内容挤成一行几个字；
  而让各行各自"按内容撑开"又会导致列对不齐 —— 必须统一量一次。
- **比屏幕宽时横向滚动**：外面套一层 `Modifier.horizontalScroll(...)`。
  实测 6 列的长表格，视图里最后一列在右边缘被切掉、后两列完全在屏外，
  说明溢出成立、可以左右滑。
- **列对齐**从分隔行读：`:---` 左 / `:---:` 中 / `---:` 右
- **单元格内的行内标记照常解析**（粗体、代码、链接都能用）
- 支持转义竖线，不会被当成分隔符
- 短的一行自动补空凑齐列数，不会串列

**判定表格的关键是「下一行是分隔行」**：只看到竖线就当成表格的话，
一句普通的话里带个竖线就会被误判。

另外记一笔：写这个解析器时，我在 Kotlin 里用原始字符串（三个双引号）
写正则 `:?-+:?`，而它正好落在一段 Python 三引号脚本里 ——
**两者引号形式相同，直接把脚本本身搞崩了**，白跑两次。
跨语言写脚本时，字符串定界符要错开。

流式输出也过同一套渲染。未闭合的标记在流中途会短暂显示成字面量，
但定稿后就被解析掉 —— 比全程显示 `**` 要好。

## 16. 停止生成 与 模型切换

### 16.1 停止：接口本来是好的，坏的是"按钮不出现"

`sessionController.cancel({sessionId})` 一直是对的，但**按钮只在 `running` 为真时显示**，
而那个 `running` 来自 5 秒一次的状态轮询 —— 于是经常该出现时不出现，
用户的感觉就是"没有停止按钮"。

修法是把运行态改成**三源取或**：

```kotlin
running = session?.running == true || liveRunning || streamText.isNotEmpty()
```

`liveRunning` 来自会话实时流里新转播的 `turn` 帧（`turn/start` → true，
`turn/end` → false），`attempt` 帧也置 true。这样开始思考的瞬间按钮就出来。

UI 上也从顶栏那个小 `✕` 挪到**输入框旁边**，变成显眼的红色「✕ 停止」。

**接口本身补做了验证**（之前从没验过）：

```
停止前 running = True
调 /phone/sessions/<id>/cancel → {"ok":true,"cancelled":true}
停止后 running = False
```

注意 `cancel` 对**未挂载的会话会抛 `session/not-found`** ——
它作用于活 Agent，不是冷会话。桥接把这情况如实当 500 报出去。

### 16.2 模型切换

harness 现成的两件东西正好够：

| 用途 | 接口 |
| --- | --- |
| 列目录 | `sessionController.modelCatalog()` |
| 切模型 | `sessionController.selectModel({sessionId, provider, model, reasoningEffort?})` |

>`modelCatalog()` 返回 `{default, routableProviders, groups[], failures[]}`，
>每个模型还能带 `reasoning.efforts[]` 和 `defaultEffort`。

**当前会话用的是哪个模型**，从 `sessionController.list()` 的投影里取：
`summary.projections.values.modelSelection` 有 `{lastUsed, next}`，
取 `next` 回退 `lastUsed`。所以只多花一次 list，不用逐个会话去问。

这台机器实测能路由 2 个 provider、8 个模型：

```
[deepseek-official] deepseek-v4-flash / v4-pro / v4-flash-vision-exp / flash   efforts: off low high max
[kimi-coding]       k3 / k3-256k / kimi-for-coding / -highspeed                 efforts: 各不同
```

UI：顶栏右侧显示当前模型短名，点开是底部面板 —— 按 provider 分组、
选中项打勾；**只有当前正用着的、且支持推理强度的模型才展开强度选项**，
免得一屏全是按钮。

## 17. 消息折叠 与 输入草稿缓存

### 17.1 工具结果也收起

原来只有「思考」和工具「参数」折叠，**工具结果全文铺开** —— 而 bash 结果动辄
几十行，会把整屏真正要读的东西挤走。

现在和思考一致：收起时给一行摘要 + 首行预览，点开才展开。

```
▸ 结果 · 16 行 · 716 字
=== 当前 prefs 里有 draft 键吗 ===
```

三类折叠（思考 / 参数 / 结果）用的是同一个模式：`▸`/`▾` 前缀 + `clickable` +
`remember(m.seq)` 的展开状态。**按 seq 做 key**，否则列表滚动复用时展开状态会串。

### 17.2 输入草稿缓存

需求是"误退出不丢编辑"，所以**不能用 `rememberSaveable`** ——
它只扛配置变更和进程被回收，**完全退出 App 就没了**。要落盘。

- 存在手机侧 SharedPreferences，**按会话分开**（`draft_<sessionId>`）
- 输入时**防抖 400ms** 落盘，不是每敲一个字写一次
- **离开聊天页时立即落盘**（`closeSession` 里 `flushDraft`），不走防抖 ——
  这一下就是要防丢的那一下
- 发出去之后清空

为什么放 ViewModel 而不是 ChatScreen 的 `remember`：离开聊天页再回来、
退出 App 重进，草稿都还在。

**验证**：直接往 prefs 里写一条 `draft_<sid>`，启动 App 打开该会话 ——
输入框自动填回那行字（不依赖"模拟打字"，那条路被 INJECT_EVENTS 封着）。

顺带一个真实事故：写这篇的时候我第一次注入失败，因为
**heredoc 没加引号，`$key` 被 bash 展开成空**，写进去的键名是空的。
同一个坑在这台机器上已经踩过好几次（跨语言/跨 shell 的引号与变量展开），
统一规矩：**凡是往脚本里嵌变量，heredoc 一律用引号定界符**。

## 18. 选中复制：一个被"想多了"去掉的功能

用户报"正文选不中、没法复制"。原因很直接：

> 当初把 markdown 接进来时，我**主动去掉了正文外面的 `SelectionContainer`**，
> 理由是"怕长按选择和点链接抢手势"。

**那是想多了。** Compose 里：

- **点按**由 `LinkAnnotation` 处理（开链接）
- **长按 / 拖动**由 `SelectionContainer` 处理（起选区）

两者作用在不同手势上，不冲突。去掉它换来的只是"正文整个没法复制"。

修法就是加回来，正文、思考、参数、工具结果四处现在都有 `SelectionContainer`，
长按即可选中并用系统工具条「复制」。

这条的教训和 §12.2bis、§14.3bis 是同一类：
**没有实测支撑的取舍，很可能是在砍功能而不是在防冲突。**
当时的注释写得很笃定（"免得互相抢手势"），但没有任何一次实际点击验证过。

### 18.1 顺带：一次真实的异地验证

改这个的时候手机被带出门了（WiFi 换到 `192.168.5.x`，USB 已拔）。
`adb -s 127.0.0.1:15555` 依然 `device` —— 装包、截图、取日志全部照常。
中间出现过一次 `device offline`，是**切网那一瞬间**，重连即恢复。

这正是 §10 那套远程通路要证明的事，只是这次不是构造出来的测试，
而是真的"人在外面、电脑在家里"。

## 19. 工作区展开状态要活过导航（和退出）

需求：从会话返回后，之前展开的工作区要**保持展开**，直到用户自己点收起 ——
这样一眼能看出最近看过哪些工作区。

### 19.1 根因是状态放错了地方

```kotlin
// 会话页里
var expanded by remember { mutableStateOf(setOf<String>()) }
```

`remember` 的生命周期跟着**这个 composable 在组合树里的存在**。
一进聊天页，会话页整个从组合里移除，`remember` 就被丢弃 —— 返回时全收起。

修法两步：

1. **提到 ViewModel**（`_expandedWorkspaces: StateFlow<Set<String>>`）。
   仅这一步就解决了"返回后全收起"。
2. **落盘** SharedPreferences。这样连退出 App 重进都还在，
   才是真正的"我最近看过什么"。

### 19.2 顺便：打开会话时自动展开它所属的工作区

`openSession` 里查一下这个会话在哪个工作区，把它展开（**只展开不收起**，
免得把用户手动收起的又弹开）。返回列表时，刚读的那个工作区就是开着的。

### 19.3 验证

- **写入**：prefs 里出现了 `expandedWorkspaces = a0253bce…`（某个工作区），
  是 App 自己写的，不是我注入的
- **渲染**：列表里该工作区显示为 ▾ 并列出会话

「读取」那一侧没拿到干净的独立证据（验证时用户正在用手机，
我重启 App 会打断他，就没反复试）—— 但它和 §17.2 的草稿走的是同一套
`SharedPreferences` 读写，而草稿是端到端验过的（注入 prefs → 输入框自动填回）。

顺带观察到：改这个的时候用户的模型已经切成 `k3` 了 ——
上一轮做的模型切换已经有人在用。

## 20. 在手机上点开文档

需求：会话产出一个 `.md` 文档后，手机上点一下（像超链接那样）就能看渲染好的内容。

### 20.1 桥接：读文件

新增 `GET /phone/file?path=<p>&sessionId=<id>`。两个关键决定：

1. **相对路径按"该会话的 cwd"解析。** 用户在正文里点的是
   `docs/技术路线.md` 这种相对写法，不可能要求他写全路径。
   桥接先用 `sessionController.list()` 查出该会话的 cwd 再拼。
2. **有大小上限**（默认 512KB，最多 2MB），超了截断并在响应里标记
   `truncated` —— 不能因为一个巨型文件把手机内存吃光。

读的是 harness 自己的 `fs` 服务（`resolve` + `stat` + `readText`），
不是另开一条文件访问路径。

### 20.2 让路径变成可点的

两处来源：

| 来源 | 怎么识别 |
| --- | --- |
| 工具调用的标题 | 桥接在 `toolSummary` 里判断摘要取自 `file_path`/`path` 时，额外给一个 `titlePath` 字段 |
| 正文里的行内代码 | `looksLikeDocPath()`：含 `/`、末段有扩展名、扩展名在文档白名单里 |

第二处是启发式，所以**限定得比较死**（必须像路径才认），
否则每个变量名都会变成链接。

### 20.3 为什么用私有 scheme 而不是自己发 Intent

链接点击在 Compose 里最终落到 `LocalUriHandler`。所以在 `MarkdownText` 外层
`CompositionLocalProvider(LocalUriHandler provides ...)` 包一层：

```kotlin
if (uri.startsWith("dshfile:")) onOpenFile(uri.removePrefix("dshfile:"))
else platformHandler.openUri(uri)      // http(s) 照旧交给系统浏览器
```

好处是**解析层保持纯函数**：`inline()` 只负责生成 `dshfile:<path>` 这样的 URL，
不需要知道任何回调。而且 http 链接的行为一点没变。

### 20.4 验证

加了一个 `--es file <path>` intent 参数（和 `tab`/`send`/`sessionId` 同一套路，
本身也能当深链用），于是可以无人值守验证：

```
adb shell am start -n com.dsh.phone/.MainActivity \
  --es sessionId <id> --es file "docs/技术路线.md"
```

结果：标题栏显示 `技术路线.md`、副标题显示**解析后的绝对路径**，
正文的 `#` 标题、`>` 引用、``` 代码块``` 全部正确渲染。

**"点击"这个动作本身没验证**（注入手势被 INJECT_EVENTS 封着），
但点击之后的所有环节都验过了。

### 20.5 又一个"replace 没加断言"的教训

`Models.kt` 里给 `ChatMessage` 加 `titlePath` 时，我用
`s.replace("title = ...", "title = ...\ntitlePath = ...")` **没带数量限制** ——
于是这个字段被同时塞进了 `parseState` 和 `parseWorkspaceSessions`，
而那两处构造的对象根本没有这个参数，直接编译不过。

规矩：**跨多处出现的文本做替换，要么带 `count=1`，要么先 `assert` 存在且唯一**
（grep 出来的行号也要看一眼是不是同一处）。

## 21. 长按管理：会话与工作区

需求：长按会话弹出和电脑上「···」同一批操作（归档 / 重命名 / 分支），
长按工作区弹出删除工作区等。**并且这些操作要真的同步到电脑。**

### 21.1 用 harness 自己的接口，不自己写存储

| 操作 | 接口 |
| --- | --- |
| 重命名会话 | `sessionController.rename({sessionId, title})` |
| 分支会话 | `sessionController.fork({sessionId, atSeq?})` |
| 归档会话 | `workspaceController.archiveSession({sessionId})` |
| 重命名工作区 | `workspaceController.rename({workspaceId, title})` |
| 删除工作区 | `workspaceController.delete({workspaceId})` |

因为走的是同一套服务，**电脑上的 UI 和手机看到的是同一份状态** ——
不需要任何"同步"逻辑，本来就是同一个后端。

### 21.2 「删除」的语义必须在 UI 里讲清楚

两个都容易被误解，所以对话框里直接写明：

- **会话没有删除**：日志是只追加的，harness 提供的是**归档**
  （从工作区分组里隐藏，日志完整保留）。而且**没有反归档接口** ——
  这一点让"归档"比"删除"更需要二次确认。
- **删除工作区删的是注册记录**：电脑上的目录和里面所有会话日志都不动。
  验证方式很直接：删除后对那个目录执行 `rmdir` 成功了，
  说明目录确实还在（`delete` 没碰它）。

对话框里因此分别写成「归档」和「删除注册」，而不是一个含糊的「删除」。

### 21.3 UI

长按用 `combinedClickable(onClick, onLongClick)`，菜单用 `DropdownMenu`
**挂在每一行自己的 Box 里**（DropdownMenu 相对父级定位，所以必须挨着那一行）。

回调收成一个 `DshActions` bundle 传进 `SessionsScreen` ——
否则参数列表会有十来个 lambda，没法读也没法改。

### 21.4 又踩了一次同一个坑

给 `Screens.kt` 加 import 时用了
`s.replace("import ...Card", "import ...AlertDialog\nimport ...Card")`，
结果 `Card` 是 `CardDefaults` 的前缀，**把 `CardDefaults` 也改了**，
变成 `OutlinedButtonDefaults` 这种不存在的类。

这是本项目里**第三次**因为"替换没加约束"出错（§20.5 是没加 count，
这里是前缀匹配）。规矩再收紧一条：
**改 import 之类的短标识符，替换串里带上换行或结尾锚点，别只给标识符本身。**

## 22. 别把正在翻旧记录的读者拽回底部

问题：助手正在流式输出时，用户往上翻想看上一轮说了什么 ——
结果每来一个 chunk，页面就被拉回底部，根本读不了。

原因就是那段自动滚动**无条件执行**，而且它的 key 里带着 `streamText.length`：

```kotlin
LaunchedEffect(visible.size, streamText.length) {
    listState.scrollToItem(target - 1)   // 每个 chunk 跳一次
}
```

改成「只在用户本来就贴着底部时才跟随」。难的是**怎么判断"贴着底部"**。

### 22.1 第一版判断错了，而且一截图就露馅

第一版看的是**滚动位移的方向**：索引/偏移变小 = 用户往上翻了。

写完一装上，截图里**刚打开会话就显示「↓ 回到最新」** —— 说明 `followTail`
被误判成 false 了。

原因：**布局自身的调整也会改这两个值**。消息从 SSE 合并进来、去重、重新排序，
都会让 `firstVisibleItemIndex` 变化，被当成了"用户往上翻"。

### 22.2 改对：只有"用户正在滚"时的位移才算意图

```kotlin
snapshotFlow {
    Triple(listState.isScrollInProgress,
           listState.firstVisibleItemIndex,
           listState.firstVisibleItemScrollOffset)
}.collect { (inProgress, idx, off) ->
    val movedUp = idx < prevIdx || (idx == prevIdx && off < prevOff)
    if (inProgress && movedUp) followTail = false      // 用户往上翻 → 停止跟随
    else if (!inProgress) {                            // 停下时：到底了就恢复
        if (lastVisibleIndex >= totalCount - 1) followTail = true
    }
    ...
}
```

关键在于**位移只有配合 `isScrollInProgress` 才解读为意图**；
不在滚动时的位置变化一律忽略（那八成是布局在动，不是人在动）。

另外还加了个「↓ 回到最新」按钮：上翻之后总得有个一键回去的入口，
不然用户只能一路手动滑。

### 22.3 为什么"在内容变化时判断是否到底"一定失败

顺带记下这个反直觉点：不能在 `LaunchedEffect(visible.size)` 里去问
"最后一屏可见吗"。那一刻 `totalItemsCount` 已经涨了、
`visibleItemsInfo` 还是旧的 —— 问出来的答案必然是"不在底部"，
于是跟随永远开不起来。**判断必须基于变化之前的意图，而不是变化之后的布局。**

## 23. 阅读位置要能"接着看"

需求：看到一半退出（去处理别的事），再点回来要停在原处继续看。

### 23.1 光把 LazyListState 提到 ViewModel 不够

滚动位置提到 ViewModel 只解决了"进程内导航"。还有两个坑：

**坑一：不能在 `closeSession` 里清空 messages。**
清空之后列表变空，`LazyListState` 的索引会被夹到 0 —— 位置就没了。
所以 `closeSession` 刻意**保留 messages**，只断开实时流。
再点回来时 `openSession` 认出是同一个会话，就直接接着用旧列表和旧位置。

**坑二：不能在列表还空着时恢复位置。**
所以换会话时先把存档读出来，**等历史加载完**才 `scrollToItem`。

### 23.2 第一次验证失败，原因很典型

注入一份存档（`scroll_<sid> = 8,0,0`，表示"看到第 8 条、没在跟随"）后打开会话 ——
结果它还是停在最新，也没出现「回到最新」按钮。存档确实写进去了，说明是代码没生效。

原因是 §22 那段 `snapshotFlow`：它在**非滚动状态**下也会评估"是否到底"，
而**启动那一刻列表还短，最后一个 item 必然可见** ——
于是把刚恢复出来的 `followTail = false` 又覆盖成了 `true`。

改成**只在"一次真正的滚动刚结束"时才评估**（`isScrollInProgress` 的下降沿），
外加"手指还在屏幕上且往上挪了就立刻停止跟随"。
这样启动时的布局状态不会污染用户意图。

这已经是这个滚动逻辑的**第三次**修正了，三次都栽在同一个点上：
**分不清"布局在动"和"人在动"。**

## 24. 三个板块的互斥分类：「最近会话」是怎么切出来的

需求：会话页顶上再加一块**「最近会话」**，方便在手机上快速找回刚点开过的会话。
但一加就撞上一个必须先回答的问题：**一个会话到底该出现在哪一栏？**

### 24.1 问题出在「未读」的定义上

原来的未读判据是（`ActivityInfo`，见 §13）：

```
agentSpokeLast && lastReplySeq > seen && 7 天内
```

`agentSpokeLast` 只看"最后说过话的是助手还是人"。问题是**一轮里助手会说很多次话**：
调工具前的说明、工具返回后的中间结论、最后才是收尾回复 —— 它们**都带 seq**，
都会被 `assistant/message` 事件记进 `lastReplySeq`。

于是一个正在跑、**还没有最终回复**的会话，会被算成"有未读回复"：

- 用户点进去，只看到半截输出（甚至还在转圈），**这就是骗人**；
- 它明明在「正在工作」栏里，却同时又出现在「未读回复」栏，**两栏打架**。

实测（改动前，电脑侧真实数据）：143 个会话里旧规则算出 3 条未读，
其中 **2 条其实正在跑** —— 包括用户当时正盯着看的那一个。

### 24.2 规则：三栏互斥，优先级从"动"到"静"

```
正在工作 = 电脑上 running（或手机正开着且实时流说在跑）
未读回复 = 没在跑 且 助手最后说话 且 手机没看过这条 且 7 天内
最近会话 = 没在跑 且 已读 且 手机上点开过（按点开时间新→旧）
```

一个会话**只出现在一栏**里。所以"退出一个还在跑的会话"之后它仍在「正在工作」，
跑完变成「未读回复」，你点开看过之后才落到「最近会话」。
这正是"已读且停止工作的才算最近"的字面含义。

### 24.3 两个实现细节

**一、「正在工作」的数据源要取新的，不能取并集。**
两份快照都来自电脑上同一次 `sessionController.list()`：
`/phone/state` 每 ~5 秒一次，工作区树 ~20 秒一次。
如果用并集（任一份说在跑就算在跑），一个 20 秒前就做完的会话会被旧快照
按在「正在工作」里出不来 —— 「未读」就永远不出现。
所以按"谁新用谁"：state 里有这个会话就用 state 的，不在 state 最近 60 条里才回退。
再叠上手机自己那条实时流的 `turn/start`（比 5 秒轮询还快）。

**二、「最近」是手机侧的记忆，电脑端一个字节都不改。**
存 `SharedPreferences`，格式 `会话id:时间戳\n...`，新的在前。
**记 12 条、显示 6 条**（`RECENT_MAX` / `RECENT_SHOWN`）：多留一倍是为了
"正在跑"或"有未读"的那几条被上面两栏借走时还能往下补位，
免得最近会话一眼看上去是空的；30 天没点开过的自动过期。
界面上按这个顺序映射到工作区树里的会话对象 ——
映射不到的（刚被归档/删掉）自然消失，不需要额外清理。
`openSession()` 里记一笔，所以未读卡片、工作区树、通知、`--es sessionId` 深链
全都算"点开过"。

> 注意"显示 6 条"不等于"永远有 6 张卡"：只有手机上点开过、且此刻不在
> 「正在工作」/「未读回复」里的才在这里，所以条数是浮动的。

### 24.4 顺带挖出来的一个真 bug：`onNewIntent` 在这台机器上根本没被调

验证时按老办法用 intent 打开会话：

```bash
adb shell am start -n com.dsh.phone/.MainActivity --es sessionId <id>
```

**没用**。事件日志里 `result code=3`（`START_DELIVERED_TO_TOP`，意思是"已投递给栈顶实例"），
但 App 的 `onNewIntent` 没有跑 —— `lastSessionId` 和最近列表都没变。
（澎湃的 `ActivityStarterImpl: boost warm start` 走了 `LAUNCH_MULTIPLE` 路径。）

对着"一条新 APK + 强制 stop 后冷启动"再试就正常，说明是**已在栈顶时的投递**这条路径坏了。
修法是给 Activity 加 `android:launchMode="singleTop"`：
单 Activity 应用本来就该这样，顺带也杜绝了重复实例。
加完之后同一条 `am start` 立刻生效（最近列表按新→旧写入三笔，见 §24.5）。
这也说明了那条纪律：**"参数传对了"不等于"代码跑了"**，必须回读落盘结果。

### 24.5 验证

- 电脑侧用真实数据重放分类规则：`未读 ∩ 正在工作 = ∅`，旧规则里 2 条"正在跑的假未读"被摘掉。
- 连发三次 `--es sessionId`，`recentSessions` 落盘为
  `14c08bcc:…\ne994c242:…\na8f31a46:…`（新→旧），顺序正确。
- 截图核对：`未读回复（1）` / `正在工作`（3 条）/ `最近会话`（3 条，带「清空」）/ `工作区`
  四段从上到下依次渲染，底部导航的未读角标与「未读回复（1）」一致。

## 25. 手机上的电脑终端：不用 SSH，用宿主已有的真 PTY

需求：在手机上也能操作这台电脑 —— 尤其在会话里复制一段命令后，
切到终端粘上就能跑。

### 25.1 为什么不用 SSH

SSH 是第一直觉，但它对**这个**项目是更差的选择：

| | SSH | 走桥接（实际选的路） |
| --- | --- | --- |
| 手机侧依赖 | 要往 APK 里塞一个 Java SSH 实现（密钥、known_hosts、密码/私钥输入全自己做） | 无（就是 OkHttp） |
| 通道 | 再开一条（`adb reverse 22` 或 `tailscale serve 22`） | 复用已有的 `/phone/*`（一个端口、一把令牌） |
| 延迟 | 差不多（都是本地/tailnet） | 在家 `adb reverse` ~5ms，在外 tailnet ~58ms |

省掉的不是"协议"，是**一整套客户端实现 + 第二套鉴权与端口**。

### 25.2 关键是宿主本来就有真 PTY

先查 Inspect 的 `Service.listService`，发现两个候选：

- `shell.start(spec)` —— 管道式的流式命令，**不是终端**（没有 job control、没有行编辑）；
- `subprocess.spawnTerminal(spec)` —— 描述原文是
  *"Allocate a real terminal and start one owned process session."*，
  返回 `{ pid, output: Readable, write(data), signalForeground(sig), terminate(), done }`。

这就是要的东西。还有个 `terminals` 服务（`spawn(owner, ...)` / `read` / `startSend`），
但它按 **Agent 归属**、读法是"拉一屏滚动文本"，不适合手机这种"一直挂着看"的用法，
所以选了更底层的 `subprocess.spawnTerminal`。

于是整条链路是：

```
手机终端页 ──POST /phone/term/<id>/input──▶ 桥接 ──handle.write()──▶ PTY(bash -l)
        ◀──SSE /phone/term/<id>/stream──── 桥接 ◀──handle.output──┘
```

### 25.3 四个必须处理的细节

**一、UTF-8 会被切开。** 一次 read 可能正好切在一个汉字中间。
桥接侧用一个 `TextDecoder` 实例反复 `decode(chunk, {stream:true})`（**不能**每次新建），
手机侧同理：`AnsiParser` 把半截转义序列留着，等下一块接上再解析。
（宿主没有 `Buffer`，但 Builtin 里有 `TextDecoder`。）

**二、PTY 尺寸是分配时定死的。** 没有 resize 接口，所以列数必须按手机屏幕
实际能放多少列来传：终端页用 `rememberTextMeasurer` 量一个等宽字符的宽度，
再除以可用宽度。实测小米 14 Pro 竖屏是 **54 列 × 47 行**。
列数传错的后果很直接：`ls`、表格、提示符全部折行。

**三、`TERM=dumb`。** 宿主给的基线环境是 `TERM=dumb`（实测），
后果是没颜色、全屏程序直接报错。
修法**不是**往 `spec.env` 里塞 `TERM` —— 那个字段的语义是"完全指定环境"，
只塞一个 TERM 有把 PATH/HOME 一起抹掉的风险（那就从"没颜色"变成"命令都找不着"）。
改成 argv 前面挂 `/usr/bin/env TERM=xterm-256color`：只覆盖指定的变量，其余原样传递。
`/usr/bin/env` 存不存在是先查一次 `fs.stat` 再决定的，不靠猜。

**四、手机切走时终端不能死。** 用户的用法就是在"会话 ↔ 终端"之间来回切。
所以：离开终端页只**断开输出流**，电脑上的 shell 留着；
桥接给每个终端留一段 96KB 滚动缓冲，重连时先发一帧 `hello.buffered` 把屏幕补全；
真没人要了由 20 秒一次的扫描回收（30 分钟无连接就关）。
**插件卸载时必须全杀** —— 否则 reload 一次就在宿主里漏一堆 bash。

### 25.4 手机侧的文本层：够用就好的 ANSI

`Ansi.kt` 里是一个**有状态的增量解析器**，不是终端模拟器：

- **认** SGR：粗体/暗色/下划线/反显 + 16 色、256 色、真彩色；
- **丢** 光标移动、清屏、OSC（starship 和 shell 集成会发 `\e]3008;...`）、私有模式 `?2004h`；
- `\r` = 重写当前行，`\b` 退格，`\t` 按 8 列制表位展开；
- 样式**跨行保留**（终端本来就这样）。

已知取舍：全屏 TUI（vim/htop）会显示成重绘残影，因为"回到第几行第几列"这类
光标寻址被丢掉了。要真支持得写完整的屏幕缓冲 + 光标模型，对"跑命令、看输出"
这个主用途不划算 —— 需要时再说。

### 25.5 一次真机字节救回来的 bug

合成用例（`hello\n`、`\e[31mred\e[0m`）**17 项全绿**的时候，我把一段真机抓下来的
字节喂进同一个 buffer：结果是**每一行都是空的**。

原因是 PTY 的行尾是 **CRLF**：`文字\r\n` 里的 `\r` 在 `\n` **之前**。
我原来"见到 `\r` 就清行"（为了进度条重绘），于是把这一行的内容在提交前抹掉了。
正确语义是：`\r` 只是"光标回第 0 列"，真正覆盖旧内容的是**回列之后又写来的字符**。
改成懒清行（`crPending`）后，进度条照样对，CRLF 也对了。

这条用例现在固化在 `tests/ansi/AnsiTest.kt` 里，跑 `scripts/test-offline.sh` 就会执行。
教训和 §22/§23 是同一个：**合成数据全绿 ≠ 对，必须拿真机/真进程的字节回放一遍。**

### 25.6 顺手修掉的第二个 UI 坑

功能键那排原本是"横向滚动的 Row"。实测在手机上启动后，
**第一个按钮被挤到屏幕左侧只露出 36px**，文字被裁掉 ——
无障碍树里那一行只剩一个没有文字的 36px 空按钮。
换成 `FlowRow` 自动换行后 12 个键全部可见可点。

顺带的原则：**藏在屏幕外、要滑一下才看得见的键，等于没有。**
（这也和 §24.4 一样：`uiautomator dump` 能把 Compose 的文字读出来，
比截图更适合做"有没有渲染出来"的验证，也不会把用户屏幕上的内容拍进上下文。）

### 25.7 深链（也方便无人值守验证）

```bash
# 直接落到终端页
adb shell am start -n com.dsh.phone/.MainActivity --es screen terminal
# 终端就绪后自动执行一条命令（PTY 是异步开出来的，会等 hello 到了再发）
adb shell am start -n com.dsh.phone/.MainActivity --es termSend "ls -l ~"
```

`screen=terminal` 走的是一个"请求计数器"（`terminalRequest`）：
冷启动和热启动（`onNewIntent`）共用一个入口，不必写两套。

### 25.8 验证

- **离线（不需要 harness / 手机）**：`scripts/test-offline.sh`
  - `tests/bridge/term-harness.mjs`：假 ctx + 真 `script`(PTY) 起一个 HTTP，
    打 `/phone/term/*` 全流程 —— 开、SSE、中文、大段输出、
    Ctrl-C（往 PTY 写 `\x03`，行规程会把它变成前台进程组的 SIGINT）、
    重连拿缓冲、close 杀掉真进程、`dispose` 杀干净。**15/15 通过**。
  - `tests/ansi/AnsiTest.kt`：解析器 + 行缓冲，含真机字节回放。**17/17 通过**。
- **在线**：`scripts/verify.sh` 增加"桥接版本 / 终端接口 / 离线验收"三组（15 项全过）。
- **手机上**：`--es screen terminal` 冷启动后，电脑侧 `/phone/term/list` 里出现
  一条 `cols=54 rows=47` 的真 PTY，`clients=1`；无障碍树里能看到渲染出来的
  starship 提示符、各功能键和输入框。

### 25.9 安全边界

终端 = 这台电脑上的一个**真 shell**。所以：

- `/phone/term/*` 和别的 `/phone/*` 一样，**无令牌 401**；
- 只经 `adb reverse`（USB）或 `tailscale serve`（tailnet only）到达，公网不可达；
- 令牌的强度就是这台电脑的强度 —— 它现在等价于 SSH 私钥，别往聊天里贴；
- APK 是 debug 自签名、只经 `adb install` 安装，不碰系统分区（与全程的硬约束一致）。

## 26. 排队消息：跑着的时候发的那几句去哪了

### 26.1 问题

harness 在跑（思考、调工具）的时候手机又发一条，它进的是会话的**待处理队列**，
要等这一轮跑完才执行。原来的界面什么都不显示 —— 用户的角度就是
"发出去了、没人理"，于是重复发一遍。

### 26.2 宿主已经给了答案，只是散在两个地方

查 Inspect 的 `sessionController` 契约，一次就找齐了：

| 接口 | 作用 |
| --- | --- |
| `control(signal)` | 一条**常驻流**：先给全量基线 `{queues, jobs, projections}`，之后推增量帧 |
| `updateQueue({sessionId, itemId, action})` | 改一条还没执行的：`{kind:'remove'}` / `{kind:'edit',content}` / `{kind:'steer'}` |
| `prompt({mode:'queue'\|'steer'})` | 发消息时就决定"排队"还是"插话" |

桥接做的事就是**镜像**：常驻消费 `control()`，把 `queues` 存下来，
一份供 `GET /phone/sessions/<id>/queue` 查询，一份在变化时推给正在看这个会话的手机
（事件名 `queue`）。不让手机自己去拉 `control()` 的理由很实在：
那是一条长期流，手机一断线状态就丢了；桥接本来就常驻，多镜像一份最省事。

### 26.3 三个容易错的点

1. **段数**。桥接的 `segments()` 会先剥掉 `/phone`，所以
   `/phone/sessions/<id>/queue` 是 **3** 段而不是 4 —— 写多一层会静默落到
   后面的通用分支，报一个"unknown session action: queue"，看着像没实现。
2. **乐观更新**。点「撤回」先在本地把这条拿掉（点下去立刻有反馈），
   权威值随后由 `control()` 推回来覆盖。否则网络一个来回，用户以为没点上。
3. **`QueueAction` 的形状**。三种 action 的字段名各不相同，拼错**不会报错**，
   只会静默不生效。所以离线测试专门断言发出去的 JSON 长什么样
   （`tests/bridge/queue-harness.mjs`）—— 拿假 ctx 推一帧 baseline、一帧增量，
   看镜像对不对、推给手机了没有、updateQueue 收到的是什么。

## 27. 手机上真的能编辑文件了：把终端从"行"改成"屏幕"

### 27.1 第一版为什么不行

需求是"在手机上开终端，`vim test.md` 能顺手改文件"。第一版把 PTY 输出当
**一行行往下写的文本**（见 §25.4）。这有三个后果，用户全撞上了：

1. 全屏程序靠光标寻址反复重绘同一块区域 —— 行式渲染画出来是**残影**；
2. **光标位置根本不知道**，所以没法"滚到你正在编辑的那一行"，
   软键盘一弹就把正在打字的那行盖住；
3. 看起来是"Tab 补全有 bug"：其实 Tab 发出去了、补全也回来了，
   只是补全列表用 `\r` + 光标移动重绘，被行式渲染吃掉了。

所以真正的修法是**把"行"换成"屏幕"**：cols × rows 的格子 + 光标。

### 27.2 `TermScreen`：够用的 VT100

`TermScreen.kt` 是一块真正的屏幕缓冲区。支持到什么程度不是拍脑袋定的，
是按 **vim / nano / htop / less 实际会发什么**倒推的：

| 类别 | 支持 |
| --- | --- |
| 光标 | CUP/HVP、A/B/C/D/E/F、G/CHA、d/VPA、CR/LF/BS/HT、`ESC7/8`、`CSI s/u` |
| 擦除 | ED(J)、EL(K)、ECH(X)、删字符(P)、插字符(@)、删行(M)、插行(L) |
| 滚动 | 滚动区域 DECSTBM(r)、S/T、到底自动上滚 |
| 备用屏 | `?1049` / `?1047` / `?47` —— 进出全屏程序时主屏历史留得住 |
| 其它 | 自动换行（`?7`，含**延迟换行**语义）、`ESC(0` 制表符映射、宽字符占两列、`?25` 光标可见性 |

明确不做：鼠标上报、完整字符集表、真 24 位光标形状。
判断标准是"跑命令、编辑文本够不够"，不是"能不能过 vttest"。

### 27.3 界面跟着屏幕模型一起改

- **进全屏程序自动换输入方式**（`TermState.fullScreen` = 备用屏中）：
  - 命令行模式：输入框写好一行再发送（中文输入法能组词、联想、纠错）；
  - 全屏模式：**逐键直通** —— 隐藏发送框，手机原生输入法打字，
    输入法一提交就把内容发进 PTY 并清空挂钩框。这样中文能组词，
    而 vim 收到的是逐个按键。
  - 多一排电脑上才有的键：Esc / ⏎ / Tab / ⌫ / 方向键 / **Ctrl 锁存**（Ctrl 亮起后按一个键 = 那个控制字符）/ `:` `/` `|` `-` / 粘贴。
- **滚动跟着光标走**，不是跟着最后一行走 —— 这是"键盘盖住正在编辑那行"的根治办法。
- **行不软换行**：PTY 的列数是按屏宽算好的，软换行会把下面所有行挤下去、
  全屏网格当场错位。宁可裁掉超出的最后几个字符。

### 27.4 一个必须记住的语义：裸 LF 不回列

改完屏幕模型，40 项测试里挂了 6 项，全是同一个原因：
**测试数据里写了裸 `\n`**。VT 里 `LF` 只下移一行、**保留列**，
回列是 `CR` 的事；真 PTY 的行尾是 **CRLF**（行规程的 ONLCR 会把程序的 `\n`
翻译成 `\r\n`）。所以我实现的没错，是测试在按"行式"的旧直觉写。
这类"测试数据与真机字节不一致"的坑，这个项目已经踩到第三次了（§25.5 的 CRLF那次）。
现在的规矩：**屏幕相关的用例一律用 CRLF**，并单独留一条用例把
"裸 LF 只下移不回列"的语义钉住，防止以后有人"顺手"改成换行。

### 27.5 验证

- 离线：`tests/ansi/AnsiTest.kt` 40 项（光标寻址、擦除、备用屏、滚动区域、

## 28. "跑着的时候切不了模型"：一次典型的契约漂移

### 28.1 现象与第一直觉（错的）

用户报："回答生成中我想在手机上切模型，切不了。"

第一直觉是"Agent 正忙，不许换模型" —— 毕竟契约里确实有
`session/agent-busy` 这个错误码。但翻源码一看，它只出现在
**子代理路由**和 **prompt 被拒**两处；`selectModel` 的实现是
`resolveAgent()` → `agents.selectForNextRequest(agent, selected)`，
语义是"**对下一次请求**生效"，压根没有"正在跑就不许切"的门槛。

### 28.2 真相：App 请求的路径，桥接根本没实现

拿一个**临时会话**（`/tmp` 下新建、发一条 `sleep 30` 让它跑起来）
真发一次请求：

```
POST /phone/model  {"sessionId":…,"provider":"deepseek-official","model":"deepseek-v4-flash"}
→ {"ok":false,"error":"unknown bridge route","path":"/phone/model"}
```

桥接实现的是 `POST /phone/models`（复数，因为 `GET /phone/models` 是模型目录）。
而 **App 客户端、README 的接口表、桥接代码里那行注释写的全是单数**
`POST /phone/model`。—— 两边各自看着都对，于是"切模型"**从来就没成功过**，
只是平时切完看不出来（当前这轮的输出还是老模型生成的，用户以为"等会儿就好了"）。

修法：路由把单复数都收下（`seg[0] === 'models' || seg[0] === 'model'`），
契约按文档的单数走。

### 28.3 这类 bug 只能靠"真发一次请求"拦住

编译能过、类型能过、读代码也看不出问题 —— 因为**两边各自自洽**。
所以新增了 `tests/bridge/routes-harness.mjs`：把文档承诺过的 24 条
非 SSE 路由**逐条真打一遍**，断言它没有落进"unknown bridge route"兜底。
业务上返回 400/500 都算通过（说明路由到了），只有"路由不存在"判红。

写完还**反向验证了一次**：把路由改回 bug 版本，测试立刻红
（`✗ POST /model → 路由不存在！`）；改回来 26 项全绿。
测试没被验证过，就不知道它到底测没测到东西。

### 28.4 顺带修的体验问题

正跑着的时候切模型，**当前这一轮**用的还是旧模型。原来只提示
"已切到 X"，用户盯着眼前还在生成的回答会以为没切成。
现在跑着切会补一句"（下一轮生效）"。

## 29. "终端断开或已关闭"：状态文案谎报故障

### 29.1 现象与自查

用户报：手机上终端入口显示"终端断开或已关闭"。先看电脑侧：

```
$ curl -H "x-phone-token: …" /phone/term/list
{"terminals":[{"id":"t1-mv9k314e","pid":1439012,"clients":0,"buffered":2745,"exited":false}]}
```

**终端活得好好的**，`clients: 0` 说明只是"手机没在收输出" ——
那是我们**故意**的：用户离开终端页时 `detachTerminal()` 会断开输出流，
电脑上的 shell 留着（§25.3 的第四条）。问题出在这一句：

```kotlin
if (_term.value.id.isNotEmpty() && !_term.value.exited)
    _term.value = _term.value.copy(connected = false, detached = true)
```

原来**没有 `detached` 这个字段**，只把 `connected` 置 false，
而状态文案是这么写的：

```kotlin
connected -> "已连接"
else -> "连接中断，重连中…"        // ← 挂起时也走这条
```

于是"我主动挂起"被显示成"连接中断，重连中…"。
**谎报故障比不显示更糟**：用户会以为坏了，然后去折腾本来没坏的东西。

### 29.2 修：三态分开

| 状态 | 文案 |
| --- | --- |
| 页面开着、流连着 | 已连接 |
| 页面开着、流断了 | 连接中断，重连中… |
| 页面没开（流是我们主动断的） | 已挂起 · 电脑上还开着 |
| shell 退出了 | 已退出（code N） |

`TermState.detached` 是新的、也是唯一能被界面信任的判据。
这套文案逻辑是**纯函数**，所以做成了单元测试（`tests/ansi/StateTest.kt`，10 项）：
拿 `android.jar` 当编译期 classpath，把 `Models.kt` 一起编进去跑。
"看起来差不多的文案"值得单独钉住，因为它的 bug 表现为"用户以为坏了"。

### 29.3 顺带挖出来的真问题：旧 id 会一直重连失败

同一段代码还有个更硬的坑。电脑上的终端会因为三种正常原因消失：
**harness 重启、桥接插件重载（`dispose()` 会杀掉所有 PTY）、30 分钟空闲回收**。
这时手机手里那个 id 就成了孤儿，而 `startTermLoop` 的逻辑是"连不上就退避重连" ——
会**永远重连一个已经不存在的终端**，界面卡在"连接中断"。

修法分两层：

1. **认得出 404**。`/phone/term/<id>/stream` 对不存在的终端返回 404。
   为此给 `BridgeException` 加了 HTTP 状态码，并且 SSE 打开失败时把桥接写的
   error 文案读出来 —— 原来只报 `HTTP 404`，分不清"东西没了"和"网络不通"，
   而这两者的正确反应完全相反（重开 vs 重连）。
   现在：404 → 清掉本地状态 → 按原尺寸（`lastTermCols/Rows`）**重开一个**。
2. **给人一个按钮**。退出/开失败时，页面正中显示原因 + 「重新开一个终端」；
   没有活终端时把按键条和输入框整个藏起来 —— 死控件比没有控件更让人困惑。

### 29.4 真机验证

- 正常打开：`clients: 1`，页面显示"已连接 · pid … · 54×47"，提示符正常渲染。
- 从电脑侧杀掉终端（重载插件）后：页面自己变成
  「电脑上的终端已经退出了」+「重新开一个终端」，按键条和输入框消失。
- 离线：状态文案 10 项、路由契约 26 项、终端 15 项、排队 12 项、屏幕模型 40 项，
  **共 103 项全过**。

## 30. vim 里看不见光标：屏幕模型有了位置，界面却没画

### 30.1 现象

用户在 vim 里编辑时看不到光标 —— 不知道在第几个字、不知道按 `i` 会插到哪，
等于盲操作。

**根因很直白**：§27 把渲染从"行"换成"格子"时，
第一版那个"在行尾追加一个 `▏`"的做法被删掉了，而**新的光标没有补上**。
屏幕模型一直知道光标在哪（`cursorLine()` / `cursorColumn()`），只是没人去画。

### 30.2 两个坑

**一、列 ≠ 字符数。** 光标位置是**列号**，而一个汉字占两列。
按"字符下标 = 列号"去找光标格，行里只要有一个中文，光标就偏一格 ——
而这种偏差肉眼很难发现，编辑时却一直在错位置。

所以先把一行摊成"带起始列的格子"（`renderCells()`），再按列匹配；
这一段是**纯函数**，配了 10 项单元测试（含 `中@0|文@2|x@4` 这种列号断言）。

**二、"没有光标"其实有两个来源。** 除了没画，还有一种：
**光标不在可视区**。PTY 是 54×47，而键盘弹出来时手机只能显示约 12 行 ——
如果滚动没跟着光标走，光标就落在屏幕外，症状和"没画"一模一样。
所以这两件事必须一起做：画光标 + 滚动跟着光标（后者在 §27 已经做了）。

### 30.3 还留了一手：淡光标

全屏程序重绘时会发 `?25l` 把光标藏起来（vim 执行命令时就发）。
命令行模式下藏了就不画（尊重程序）；但**全屏程序里仍然画一个下划线提示** ——
否则用户看到的就是"vim 里没有光标"。这条规则也是纯函数
（`cursorKind(index, cursorLine, fullScreen, visible)` → `NONE/SOLID/DIM`），
配了 6 项单元测试钉住，其中一项就是"全屏程序隐藏时画淡的"。

### 30.4 怎么验证"画出来了"（不截图）

光标块是**一个实心矩形**，所以可以在截图上**数像素**：
找 `#E8ECF2`（光标色）的连通块，再和等宽字一格的尺寸比。

更硬的是**差分**：在 vim 里发三个 `l`（右移三格），前后各截一张：

```
移动前:  x 103..121 (19px)  y 310..346
移动后:  x 160..178 (19px)  y 310..346
位移 = 57px = 3 × 19px     y 不变
```

一格正好 19px —— 位置、尺寸、跟随全都对上了。
这比"看一眼截图说好像有"硬得多，而且**不需要把用户屏幕内容读进上下文**，
只读几个数字。

## 31. Tab 补全不可能成立 —— 以及那个小飞机为什么该删

### 31.1 两件事，同一个根因

用户报了两件事：

1. 终端里那个"小飞机"（发送按钮）该省掉；
2. 敲到 `vim test` 想按 Tab 补全，**办不到**。

它们不是两个 bug，是同一个设计错：命令输入区是**"先在框里写好一行、再发送"**。
只要命令还躺在输入框里，shell 就**没看见**它 —— 拿什么补全？
而"框里有内容要送出去"这件事本身，就需要一个发送按钮。

### 31.2 真终端是逐键直通

改法是把命令行模式也改成**逐键直通**（和 §27 给 vim 做的那套一样）：

- 输入法在挂钩框里组词，**提交时**把那串字符发进 PTY，随即清空挂钩框；
- shell 那边是真的一个字一个字收到 —— 补全、历史（↑）、行编辑（Ctrl-A/E）全都成立；
- 中文照样没问题（输入法只在框里工作）；
- **发送按钮自然消失了**：没有"待发送内容"这回事；
- 「粘贴」= 把剪贴板**打进当前命令行**（不回车，可改可补全），
  「粘贴并跑」= 粘贴 + 回车。

代价是每次按键一次请求。家里 `adb reverse` 下 ~5–15ms 无感；
在外面 tailnet 上 ~60ms，和 SSH 到远端一个体感。
（想再快可以按键攒 40ms 合批发，但要注意 Tab/回车必须先冲刷 —— 暂时没做。）

### 31.3 顺手统一了按键条

原来命令行模式和全屏模式各一套键。既然输入方式统一了，
键也就并成一套：`粘贴 / 粘贴并跑 / ⏎ / Tab / ⌫ / Esc / ↑↓←→ / Ctrl-C / Ctrl(锁存) / 清屏`。
少了一套分支，命令行下也多出了 **⌫（退格）和 Ctrl 锁存** ——
以前只能靠手机键盘自己退格，现在有实体键了。

### 31.4 回车到底发 `\r` 还是 `\n`

统一发 **`\r`**。全屏程序（vim）把 PTY 设成 raw 模式，那时 CR 才是 Enter；
而命令行的行规程有 `ICRNL`，`\r` 一样等于回车。一个字符两边都对。

### 31.5 验证

从电脑侧**逐键**打进 `vim /tmp/dsh-fre`（每个字符一次请求，正是手机现在的行为），
再发一个 `\t`：终端缓冲里出现了 `/tmp/dsh-fresh.txt` —— 补全成立。
界面上再看一遍：小飞机没了，按键条是一套，挂钩框写着"在这里打字，直接进终端（Tab 可补全）"。

## 32. 把终端里的文本选中复制出来

终端画面不是普通文本，能"选中复制"这件事得自己做。三种入口，覆盖三种意图：

| 想干什么 | 怎么做 |
| --- | --- |
| 抄某几行 | 点按键条的「选择」→ 点一行定起点、再点一行定终点 → 「复制」 |
| 快速抄一行 | **长按那一行**直接进入选择模式，锚点就落在那一行 |
| 抄最近 N 行 / 做快捷方式 | 深链：`adb shell am start … --es screen terminal --es termCopy 20` |

选择模式下按键条和输入框会**整条换成**「已选 N 行 / 复制 / 全选 / 取消」——
选择的时候不该还能误敲命令。同时会自动停止"跟随光标"，
否则列表一滚，刚选的行就跑了。

### 32.1 复制的是"看得见的文本"

取的是渲染后的每一行（`lineText`），**去掉行尾空白**、行内空格原样保留。
去行尾是必须的：终端每一行都按列数补齐过，不去掉的话复制出来每条后面都拖一串空格。

复制后会**回显开头 40 个字**（`已复制 4 行（47 字）：DSH-C ⏎ …`）——
用户一眼能看出"抄对了没"，顺带让这条链路可以被无人值守核对（读屏上的文字即可）。

### 32.2 两个想当然会错的地方

**一、"最近 N 行"不能真的取最后 N 行。** 终端屏幕是 47 行，
下面大半是空白 —— 直接取最后 3 行会得到 **0 个字**（实测第一版就是这样）。
用户说的"最近 3 行"是最近的 3 行**内容**，所以要跳过空白行往上数；
中间夹着的空行照旧带上，保持版面可读。这段逻辑（`lastNonBlankRange`）是纯函数，
配了单测，其中一条就是"最近 3 行 ≠ 3 个空行"。

**二、选择是"点两下"，不是拖拽。** 手机上拖选跨行的文本很难控制
（拖动时列表还会跟着滚），点两下确定范围反而稳。

### 32.3 深链是**一次性**的

`--es termCopy N` 进来的请求处理完必须通知外面清掉；
否则离开终端页再进来会**重放一次**，把剪贴板覆盖成莫名其妙的内容。
（这类"外部请求"的字段都按"请求"而不是"状态"对待：带序号、处理完清零。）

### 32.4 验证

离线：范围取文本 8 项 + "最近 N 行"5 项，与其余用例合计 **132 项**全过。
真机：跑三条 `echo DSH-A/B/C` 后用深链请求复制 3 行，
界面上出现 `已复制 4 行（47 字）：DSH-C ⏎ ⏎ …`，与屏幕内容一致。
（长按/点选那条手工路径由用户自己试；这次是他先点到的。）

## 33. 会话里"在跑什么"：后台任务与子代理

需求：电脑端能一眼看到某个会话挂了几个后台任务、派了几个子代理，
手机上原来什么都没有 —— 于是"它到底在干活还是卡住了"只能靠猜。

### 33.1 不用加接口：state 里本来就有

翻 `/phone/state` 的字段：每个后台任务带 **owner**（属于哪个会话），
每条会话带 **parent**（父会话 id）。而 harness 里的"子代理"**就是一条子会话** ——
所以"谁是我的子代理"就是 `parent == 我`，再往下递归还能收出孙代理。

于是这条链路**一个桥接接口都不用加**：手机每 5 秒拉的那份 state 已经够了。
能不加接口就不加 —— 少一个接口就少一处要维护的契约（§28 的事故就是接口名漂移）。

### 33.2 挑数据是纯函数，所以能测

`sessionActivity(state, sessionId)` 和它的 `worthShowing(now)` 都是纯函数，
配了 13 项单测，钉住的正是"看着像对、错了很难发现"的几条：

- 只算 **owner == 自己** 的任务（别人的后台任务不能混进来）；
- 子代理要**含后代**（孙代理漏掉的话，用户会以为只派了一个）；
- 层级 depth 要对（用来画 `↳` 缩进）；
- 在跑的排前面；
- **值不值得显示**：不是"有记录就显示" —— 一个会话昨天派过子代理，
  今天还挂着张卡就没意义了。规则是"有在跑的，或者刚结束 10 分钟内的"。

### 33.3 界面

聊天页底部（排队消息卡上方）一张卡：

```
⚙ 无后台任务 · 👥 3 个子代理在跑          收起 ▾
  子代理（点头部可以进去看）
  ▶ 你是顶会/期刊的敌对审稿人（…）      在跑
  ▶ ↳ 你是顶会/期刊的敌对审稿人（…）    在跑
  · 审计诊断写扎实                       2 分钟前
```

- 有东西在跑时**默认展开**，全停了默认收起；
- 后台任务显示状态、kind、已跑时长与 detail；
- 子代理**点一下就进那个会话**（手机上"进去看"最自然的方式就是打开它）；
- `↳` 的层数表示它是"子的子"。

### 33.4 验证

离线 145 项全过（新增会话活动 13 项）。
真机：打开一个派了子代理的会话，卡片显示
`⚙ 无后台任务 · 👥 3 个子代理在跑`，与电脑端一致。

## 34. 会话仪表盘：跑到第几轮第几步、上下文用了多少

### 34.1 数据从哪来（以及一个反直觉的发现）

三样东西全在会话事件里，不用新接口：

| 想要 | 事件 | 字段 |
| --- | --- | --- |
| 第几轮 | `turn/start` | `turn`（1 起递增 → 最大值就是累计轮数） |
| 第几步 | `step/start` | `step` |
| 上下文用了多少 | `assistant/message` | `usage.inputTokens`（这次请求实际塞了多少） |
| 上下文窗口多大 | `request/context` | `contextWindow`（实测 deepseek-flash 是 1000000） |

**反直觉的发现**：桥接的根监听器（`ctx.on('session/event')`）**只覆盖一部分会话**。
从桥接自己 `sessionController.create()` 出来的会话，它的事件**到不了根监听器** ——
症状是：那个会话的"未读回复"能算出来（靠回填读日志尾部），
但"轮/步"永远是 0。

而 `follow()` 那条**单会话实时流对任何会话都成立**（聊天页本来就是靠它渲染的）。
所以改成：**实时流每来一帧事件，就顺手记一次进度**。
语义上也更顺：手机在看哪个会话，那个会话的进度就一定记得上。

这也是 `diag` 里那份"事件类型直方图"的由来 ——
"某类事件到底有没有到桥接"这种问题，光看代码看不出来，看一眼计数就明白了。

### 34.2 三个来源，逐字段取最全

进度有三个来源，各自有短板：

- 桥接镜像：**桥接重载就清空**（本轮开发中重载了 6 次，看得清清楚楚）；
- 实时流：只有**正在看**的时候才有；
- **历史消息**：`assistant/message` 自带 `turn`/`step`/`usage` ——
  读的就是会话日志本身，App 重开、桥接重启都不受影响，**最可靠**。

所以合并规则是一句话：**每个字段取"更完整"的那个**（`mergeProgress`），
不能整体二选一 —— 桥接那份可能是空壳，历史那份却只有轮号，窗口只有实时那份有。

### 34.3 界面

聊天页最上面一条窄条（不是塞进消息流 —— 这是随时要瞄的状态，不是历史）：

```
🔄 第 3 轮 · 第 7 步 · 累计 12 轮      🎯 进行中 2/10      📊 45%
[==========------------------]
```

- **目标有才出现**（用户明确要求"有再显示没有不显示"）；
  受阻时整块转红并显示受阻原因；
- **窗口未知就不画进度条**：只显示"已用 N tokens（窗口大小未知）"——
  画一根瞎猜的条比不画更糟；
- 小于 1% 写 `<1%`（刚开场是 0.02%，写 0% 会让人以为没在统计）；
- 点一下展开：当前第几轮第几步、累计、token 明细、目标全文。

### 34.4 验证

离线 161 项全过（新增仪表盘 16 项：逐字段合并、从历史推、窗口未知不给比例、文案）。
真机：打开一个有进度的会话，顶部显示 `第 1 轮 · 第 2 步  📊 <1%`，
与电脑侧的日志一致；用一个临时会话驱动一轮，确认
`第1轮第1步 → 第1轮第2步`、`上下文 144 → 217 / 1000000` 都跟着动。

## 35. 往上翻不到更早的消息：历史被"一页 60 条"卡死了

### 35.1 现象

用户："我想看上一次我问了他什么，但他思考了很多、工具调用了很多，
我再往上拉就看不到更早的了。"

根因很直接：`/phone/sessions/<id>/history?max=60` 只有**一页**，
而一轮里工具调用能产生几十上百条消息 —— 60 条可能连一轮都盖不住，
"上一次的提问"自然在窗外。

### 35.2 宿主的向后翻页语义（读了源码才敢用）

`sessionController.page({address, throughSeq, beforeSeq, maxMessages})`
内部的 `paginate` 是这样的：

```js
const end = min(throughSeq + 1, beforeSeq ?? throughSeq + 1)
// 从 end-1 往前数 maxMessages 条"消息类"事件，cut = 最老那组的起点
return { events: events.slice(cut, end), hasMore: cut > 0 }
```

**`beforeSeq` 是开区间上界**：要"比 seq=X 更早的消息"，
得传 `throughSeq = X - 1`（不是 X）。这一条是读宿主源码确认的 ——
光看类型定义（`beforeSeq?: number`）根本看不出来，猜错就会漏掉或重复一整页。

### 35.3 手机侧两件事

**一、翻页要保住阅读位置。** 新消息是插在列表**头部**的：
插进去 N 条之后，原来第一条的下标从 `i` 变成 `i+N`。
补偿方式就是插完 `scrollToItem(i + N, 同一个 offset)` ——
不补的话画面会往下跳 N 行，用户正在看的地方直接飞了。

**二、光能翻页还不够，得让"找我上次的提问"一键可达。**
一轮里几十条工具消息，就算能翻页，一路往上拉也很折磨。
所以加了「↑ 上一条我的提问」：从当前视口往上找最后一条 `role == "user"`；
找不到就**自动再翻一页**（最多 5 页）。
判据单独拎成纯函数 `lastUserIndexBefore`，配了 6 项单测 ——
这条写错的表现是"点了跳到一条工具结果上"，很难一眼看出来。

顶部还有一行状态：正在载入 → 转圈；还有更早 → 「↑ 载入更早的消息」；
到头了 → 「· 已经是最早 ·」。**没有这一行，用户分不清"到头了"和"没加载"。**
滑到顶还会自动接着载，不用在每页交界处停一下手。

### 35.4 验证

- 桥接：对真实会话翻页 —— 第一页 `seq 5998..6087`，
  带 `beforeSeq=5998` 拿到的第二页是 `5902..5994`，**严格更早**且 `hasMore: true` ✓
- 界面：短会话上顶部显示「· 已经是最早 ·」+「↑ 上一条我的提问」（已核对）；
  仪表盘同时显示 `第 40 轮 · 第 13 步 · 累计 40 轮` 与 `🎯 已完成 1/40` ✓
- 离线 167 项全过（新增 6 项：`lastUserIndexBefore`）

## 36. 已完成的目标该不该一直挂着

### 36.1 问题的来源是宿主的语义

用户看到聊天页顶上一直挂着 `🎯 已完成 1/40`，问"是不是该隐藏/收起/销毁"。

翻宿主的 `goals` 契约就明白了：**完成的目标不会被自动清掉**。
`create` 的说明写着"已完成的目标可以被替换，其它阶段必须先清除或恢复"——
也就是说完成的目标会作为**墓碑**一直留在注册表里，直到有人明确清掉它。
UI 不处理，它就在聊天页顶上挂到天荒地老。

### 36.2 分阶段处理（不是一刀切）

| 阶段 | 显示吗 | 为什么 |
| --- | --- | --- |
| `active` 进行中 | ✅ | 它正在推进 |
| `blocked` 受阻 | ✅ | **需要人管，藏起来是最糟的** |
| `paused` 已暂停 | ✅ | 它在等人恢复 |
| `complete` 已完成 | 只露 10 分钟 | 给一个"跑完了"的确认，之后就是噪音 |

判据是纯函数 `goalWorthShowing(goal, now, graceMs)`，7 项单测钉住
（含"几天前完成的就别挂了"和"completed 这种写法也认"）。

### 36.3 「销毁」做成显式动作，不自动做

自动清掉别人的目标是不对的 —— 那是用户的状态。所以：
**展开仪表盘 → 已完成/受阻的目标下面有一个「清除这个目标」**，
点了还要再确认一次（对话框里带上目标正文，免得清错）。

桥接侧新增 `POST /phone/sessions/<id>/goal/clear`：
- `ref`（`{id, revision}`）**由服务端现取**，不信客户端传来的 revision ——
  手机上的显示可能已经过期，过期会被宿主的乐观并发挡下来，
  表现成"莫名其妙清不掉"；
- 宿主的 `clear` 只清"当前目标"，会话日志里的历史仍在
  （它的原话是 "retaining a durable tombstone and history"），所以这个操作是安全的；
- 冷会话没有 live Agent，清不了 —— 这时返回一句人话，而不是一个堆栈。

### 36.4 验证

- 真机：打开那个挂着已完成目标的会话，**顶上只剩轮次信息，目标不再出现** ✓
- 桥接：对本会话执行清除，`goal` 从 `complete` 变成 `None` ✓
  （顺手把用户看到的那个墓碑清掉了）
- 路由契约测试加了一行（27 项），离线合计 175 项全过

## 37. "窗口大小怎么可能未知？" —— 用户是对的

用户的质疑很直接：*harness 上都显示着上下文窗口，同步一下不就行了？*
他是对的。我原来的做法是**等那条实时事件**（`request/context`），
而那条事件只在上下文**变化**时才写一条 —— 冷会话、桥接刚重启、
事件到不了根监听器（§34.1），都会让它"未知"。

### 37.1 harness 自己是怎么知道的

翻它的前端代码，答案一行就完了：

```js
const event = log.findLast((item) => item.type === "request/context")
```

**从会话日志里翻最后一条。** 日志是持久的，App 重开、桥接重启都不影响。
我之前是在等"活的"那一条，方向就错了。

### 37.2 改法：从日志里学，并按模型缓存

1. **读历史时顺手扫一遍**：翻页/快照返回的 records 里本来就带着
   `request/context` 记录（`paginate` 只按"消息类事件"切页，
   但返回的是这个区间的**全部**事件）—— 白捡，不额外请求。
2. **按模型缓存**：窗口是**模型**的属性，不是会话的。
   `provider/model` → 窗口大小存一张表，同型号在别的会话见过一次就够 ——
   于是"同型号的新会话"一进去就有窗口，不用等它自己跑一轮。
3. **挂载时的回填**也会读日志（本来就在做），所以桥接重启后
   第一次回填就把已知型号的窗口全学回来了（实测：重载后立刻就有
   `deepseek-flash: 1000000`、`k3: 1048576`）。

### 37.3 唯一该说"未知"的情况

**谁都没见过的型号**（比如刚切到一个从没用过的模型）—— 这时窗口是真不知道，
就老老实实显示"窗口大小未知"，**不拿别的模型的数字顶上**。
这一条单独写了用例钉住（`tests/bridge/context-harness.mjs`，
5 项：挂载即学到 / 读历史不丢 / 同型号直接有 / 没见过不瞎填 / diag 能看到表）。

### 37.4 教训

"这个信息在电脑上明明有" —— 那就去看**电脑上是从哪拿的**，
而不是自己在事件流里守株待兔。守株待兔的写法平时看着也能用，
一遇到"重启""冷会话""事件没订阅到"就退化成"未知"，
而正确做法往往只是**从同一个持久来源读一次**。

## 38. 查看 session id

用户注意到"打开某个会话的一瞬间能看到 session id"，想要一个正式入口。

那个"一瞬间"其实是标题的兜底：会话列表还没到位时聊天页标题显示
`openId.take(12)`，等状态到了就换成真正的标题。

### 38.1 为什么值得给一个入口

列表上显示的是**标题**，而标题可以重名、可以随时改；
**session id 才是唯一准确的抓手** —— 去电脑上翻日志、在命令行里按 id 打开、
在电脑端搜索，用的都是它。

### 38.2 两个入口 + 一键复制

- 会话页**长按任意会话** → 菜单里多一项「查看 session id」
  （和"打开/重命名/分支/归档"并列）；
- **聊天页点一下标题**也能看 —— 因为"我正开着这个会话，想知道它的 id"
  是最自然的时机。

弹窗里 id 用**等宽字体**显示（`session-xxxx-...` 这种字符串用比例字体看着很费劲），
带一个**复制**按钮 —— 这种长串在手机上手动划选是折磨。

### 38.3 一个"用编译期换验证"的小技巧

`SessionMenu` 的 `onShowId` 我特意**不给默认值**：
会话页里那个菜单有 4 个调用点（未读 / 正在工作 / 最近会话 / 工作区树），

不给默认值，编译不过就是漏了 —— 构建通过即证明 4 处都接上了。

这类"必须处处都接上"的参数，值得用编译器当检查器，而不是靠眼睛数。

## 39. "手机键盘的回车没反应"：输入法把回车吃了

### 39.1 现象与原因

用户报：在终端里按手机键盘的回车，"没反应，什么也没进去"。

原因在输入框的一个参数上：它原来是 `singleLine = true`。
Android 上**单行输入框的回车会被输入法当成"IME 动作"**，
直接交给 `KeyboardActions` 处理 —— 而那里什么都没接，
于是那一击**根本没进到 `onValueChange`**，代码里就永远不会出现 `\n`。
（旁边那个 `⏎` 按钮一直是好的，因为它直接发 `\r`，不经过输入法。）

### 39.2 修法：两条路一起铺

```kotlin
keyboardOptions = KeyboardOptions(imeAction = ImeAction.None),
keyboardActions = KeyboardActions(onSend = { onEnter() }, onDone = { onEnter() }, onGo = { onEnter() }),
singleLine = false,
maxLines = 1,
```

1. `imeAction = None` + 多行：回车**变成换行符进到文本里**，
   由 `onValueChange` 发出去 —— 对输入法最不挑；
2. 万一某个输入法仍然发"动作"，`onSend/onDone/onGo` 也接住。

同一个行为改了两处，是因为**输入法差异太大**：
这类"按键被输入法截胡"的问题，靠赌某一个 IME 的行为是不靠谱的。

### 39.3 判据拎出来做纯函数

真正决定"要不要发、发什么"的逻辑单独成 `hookKeystrokes(text, composing, ctrlLatch)`，
配 7 项单测，其中最关键的一条就是：

> **拿到 `\n` 就是要发出去，不许当成"空内容"吞掉。**

（另一条同样重要的：组词中不能发 —— 中文要能选词。）

### 39.4 这类 bug 的教训

**"按了没反应"要往"事件根本没到"想，而不是往"处理逻辑写错了"想。**
这次代码逻辑一直是对的（`onValueChange` 里 `\n` 的处理从来没错过），
错的是**那一击压根没送到**。输入法、系统组件、中间层，
都可能在你看到回调之前把事件吃掉 —— 所以每过一个中间层，
都值得问一句"它会不会自己处理掉"。

### 39.5 验证的边界

`adb shell input`（tap / keyevent / text）在这台机器上被 MIUI 挡住
（`INJECT_EVENTS`），所以**"按一下真键盘"这一下我验证不了** ——
能验证的是：判据的 7 项单测、`\r` 在真实 PTY 上确实能执行（前面几十次实测）、
以及输入框与按键条都正常渲染。这一条得用户自己按一下确认。

## 40. 排队消息"改到一半"也要能捡回来

### 40.1 和聊天草稿同一个道理

改排队消息的对话框里那段文字，是用户**刚打出来的** ——
被电话、返回手势、App 被杀打断，丢了最气人。
聊天输入框早就有落盘草稿（`draft_<sid>`），排队消息的编辑框却一直是
`remember` 里的一份内存状态，于是"改到一半退出 = 白改"。

### 40.2 语义上分清三种"离开"

| 动作 | 草稿怎么办 | 为什么 |
| --- | --- | --- |
| 返回手势 / 点对话框外面 | **留着** | 这是"意外"，下次打开自动恢复并明说 |
| 点「放弃修改」 | **删掉** | 这是"明确不要了"，留着下次又被恢复出来才是 bug |
| 点「保存」 | 删掉 | 已经写进队列了 |

所以按钮从"取消"改叫**「放弃修改」** —— 名字得配得上它的后果。
恢复时对话框里会写一行「已恢复上次没保存的修改（返回手势不会丢）」，
否则用户会以为是编辑器记错了内容。

排队卡上也给那条打个标：`● 有未保存的修改（点「改」接着写）` ——
不然用户根本不知道还有东西能捡回来。

### 40.3 编码怎么存，以及为什么值得单测

存成「itemId + 换行 + 正文」，一个会话同时只可能在改一条。

**正文自己就可能带换行**（用户改的常常是一段多行命令），
所以只能按**第一个**换行切分 —— 按最后一个切、或者 `split` 全部，
多行修改就会被切坏，而且坏得很隐蔽：**单行的时候完全正常**。

编解码因此单独成两个纯函数（`formatQueueEditDraft` / `parseQueueEditDraft`），
配 7 项单测，其中就有"多行正文不切坏"和"只有换行 → null"。

### 40.4 验证的边界

- 编解码：7 项单测 ✓
- 落盘与装载：`Settings` 只做一次 `getString`/`putString`，编解码走上面那两个函数 ✓
- **界面上的直观确认没做成**：我往手机里注入过一份草稿想验证"卡片打标 + 对话框恢复"，
  但那会儿手机前台是浏览器（用户在忙别的），我没有再抢它的前台；
  痕迹（注入的草稿、临时会话、排队消息）都已清理。
  这一条需要用户本人打开那个会话看一眼。

## 41. 从手机传文件进会话

### 41.1 宿主的做法是"暂存 + 凭据"，不是直接塞进消息

翻 `fileUploads` 的契约就清楚了，upload 与 prompt 是**两步**：

```
POST 上传  →  fileUploads.uploadStream({sessionId, data, name})
           ←  { receiptId, file: {attachmentId, name, bytes} }      ← 暂存凭据
再发消息   →  prompt({ content: [{type:'file', receiptId}, {type:'text', text}] })
```

`sessionController.prompt` 收到 `{type:'file', receiptId}` 会自己
`resolve` + `bindPrompt`（读了实现确认过，不是猜的），所以桥接不用手动 bind。

这条链路的好处：**上传和发送解耦** —— 可以在手机上先把文件传上去，
再慢慢想说什么；也可以只发附件不写字。

### 41.2 桥接侧两个刻意的选择

1. **不把文件拼成一整块再交出去**：请求体（`req`）本身就是
   `AsyncIterable<Uint8Array>`，直接喂给 `uploadStream` —— 几十兆的附件
   不会在桥接里翻倍占内存，也不用 base64（那是 `upload()` 那条老路，
   会平白多 33% 体积）。
2. **先看 `content-length` 再收**：超 64 MB 直接 413，不白写一遍磁盘。

### 41.3 手机侧

- 用系统的 **SAF** 选文件（`OpenDocument`）：不申请任何存储权限，
  用户选了哪个我们才读哪个；
- 读字节在 UI 层做（`ContentResolver` 只有 Context 有，而 ViewModel 刻意不带
  Context），读完把 `(名字, 字节)` 交给 ViewModel；
- 传完的文件在输入框上方排成 `📎 文件名 · 12 KB ✕` —— **必须看得见**，
  否则用户以为传丢了会再传一遍；发送前可以逐个移除；
- 编辑框的发送键在"只有附件没写字"时也是可用的（转发个文件本来就是常见动作）。

### 41.4 一个必须讲清楚的语义

**附件是以"磁盘上的文件"形式给模型的，正文不进上下文。**
实测：发完附件后模型看到的是

```
[文件] <路径> （33 字节）
```

它得**自己去读**那个文件。所以配的话术应该是"读一下这个附件…"，
而不是"附件里写了什么"（后者模型只能回"我看不到内容"）。

这不是 bug，是宿主的取舍：几十兆的文件当然不能塞进上下文，
让模型按需读才合理。但 UI 上值得说一句 —— 我在发出去后的提示里写了
"已传到电脑：xxx（33 B）—— 写字或不写都能发"，话术留给你。

### 41.5 验证

真机（桥接侧全链路）：
1. `curl --data-binary` 传一个 33 字节的中英混合文本 → 返回
   `{receiptId, name: up-test.txt, bytes: 33}` ✓ 字节数完全一致；
2. 用这个 receiptId 发一条 prompt → 历史里出现 `[文件]` + 路径 + 大小 ✓；
3. 再让它"用工具读一下" → 它读到的正是 `hello from phone` / `第二行中文` ✓
   （中文没乱码）。

手机侧的 UI（＋ 选文件、附件条、移除）**没做成自动化验证**：
选文件必须点系统文件选择器，而这台机器的输入注入被 MIUI 挡着。
离线新增路由契约一项（28 项），合计 195 项全过（上下文那一版之后是 219 项）。

## 42. "手机上的上下文占用和电脑上不一样" —— 差的是缓存

用户报：手机上那个上下文用量，和电脑端右下角显示的对不上。

### 42.1 差在哪（不是四舍五入，是差了三个数量级）

我原来是这么算的：读会话日志里最后一条 `assistant/message` 的
`usage.inputTokens`，显示它。实测那个会话是：

| 项 | 值 |
| --- | --- |
| `inputTokens` | **257** |
| `cacheReadTokens` | **617344** |
| 电脑端显示 | **~618K / 1M（62%）** |

差了 2400 倍。原因：宿主的"上下文压力"根本不是 `inputTokens`，
而是（`dsh-token-meter` 里 `pressureFrom`）：

```
pressureTokens  = inputTokens + cacheReadTokens + cacheWriteTokens
projectedTokens = pressureTokens + 采样之后的"表面"增减
```

第二个式子才是关键：它回答的是"**下一次**请求会占多少"，
不是"上一次用了多少"。电脑端右下角那个表读的就是它
（`ui-conversation` 里 `usedTokens = pressure?.projectedTokens ?? pressure?.pressureTokens`，
百分比 `Math.min(100, Math.round(used / window * 100))`）。

### 42.2 于是改成"读同一个投影"

宿主已经把这个投影算好了，就放在 `sc.list()` 每个会话摘要的
`projections.values.contextPressure` 里 —— 和我早就用来拿模型选择的
`projections.values.modelSelection` 是**同一个地方**。所以：

- 桥接 `/phone/state` 里每个会话的 `progress` 直接读这个投影
  （`contextUsed = projectedTokens ?? pressureTokens`，窗口也用它）；
- 事件推算（`assistant/message` 的 usage）降级为**兜底**，且口径改成
  `input + cacheRead + cacheWrite`，不再是光秃秃的 inputTokens；
- 消息里给 App 的 `usage` 也补上了 `cacheRead` / `cacheWrite` 两个字段。

手机侧顺手把写法也照抄了电脑端（`number.thousand` = `{value}K`、
`number.million` = `{value}M`，缩放后 ≥100 取整）：显示成
`上下文：~618K / 1M（62%）` —— 用户就是拿这两个数字对着核对的，
一个写 `618K`、一个写 `617879`，数值一样也会让人以为又没对上。

### 42.3 顺带修掉的第二个坑：不能取最大值

App 原来是"多个来源取最大"。轮号取最大是对的（累计轮数只增不减），
**上下文取最大是错的**：上下文被压缩（compaction）之后会变小，
取最大就永远卡在旧的大数字上。

所以进度分成两层：

| 层 | 来源 | 地位 |
| --- | --- | --- |
| 权威层 | 桥接的 `/phone/state` 与实时 `progress` 事件 | 有值时压过兜底 |
| 兜底层 | 历史消息里的 usage 按同口径推 | 只补权威层缺的项 |

### 42.4 验证

离线新增 5 项（`context-harness.mjs` 5 → 10 项），其中三条是这次的钉子：

- 有投影时报 `projectedTokens`（617879），**不是** 257；
- 投影只有 `pressureTokens` 时退到它（617601）；
- 没有投影时兜底口径含缓存命中（257 + 617344 = 617601），且**不等于 257**。

**反向验证**：拿改动前的 `bridge-core.js` 跑同一份用例 → 那三条全红，
报的正是 257。也就是说"用户看到的那个错"被一条测试钉住了，
而不是靠我这次恰好改对。

真机侧：桥接 `/phone/state` 回报该会话 `617879 / 1000000`，与电脑端
`projectedTokens` 一致 ✓。手机界面上的那一行**没做成自动化核对** ——
当时用户正在手机上打字（输入框里有半截草稿），不适合抢屏去点开仪表盘。

## 43. "手机新建工作区失败了" —— 两个定位字段一起发，宿主直接 400

用户报：在手机上新建了一个工作区，流程失败了。查下来是：

- 工作区**建出来了**（`/home/leli/Documents/nmmiw卡尔曼滤波rl`，标题
  `nmmiw卡尔曼滤波rl`），但**里面 0 个会话**；
- 也就是说：错在"接着开会话"那一步。

复现出来是这个错：

```
{"ok":false,"error":"session.create accepts workspaceId or cwd, not both"}
```

### 43.1 宿主的契约是"二选一"

`SessionCommandController.create`（`dsh-api-session-controller`）：

```js
if (request.workspaceId !== undefined && request.cwd !== undefined)
  throw new RemoteError('gateway/bad-request', '... not both')
// 给了 workspaceId 时：
const cwd = workspace?.path ?? request.cwd ?? defaultCwd
...
if (workspace !== undefined) await workspace.attachSession(sessionId)
```

关键在于：**给了 workspaceId 反而更好** —— cwd 由宿主从 `workspace.path`
自己取，而且还会 `attachSession` —— 那才是会话出现在工作区树里的原因。

### 43.2 我原来的写法恰恰是"两个都带"

`doCreate` 先放 `cwd`，再从 cwd 反查 workspaceId **加**上去：

```js
if (request.workspaceId || !request.cwd) return undefined
return workspaceSvc.resolveByPath(request.cwd).then(w => { request.workspaceId = w.id })
```

于是"手机上点新建会话"这条路径 100% 失败，而且失败得很难看：
工作区已经建好了、会话却没有 —— 用户看到的是一半成功。

现在改成**先决定用哪一个，再拼 request**，两个字段绝不同时出现：

- 有 workspaceId → 只发 workspaceId；
- 只有 cwd → 先 `resolveByPath`；查到了就**换成** workspaceId（仍然只发一个），
  查不到就只发 cwd（没登记成工作区的目录不会被硬塞一个 id）。

### 43.3 验证

新增一个专门的离线用例 `tests/bridge/create-harness.mjs`（17 项）。
它的假宿主**逐字实现上面那段契约**（连错误文案都一样），所以桥接再犯同样的错，
这里立刻红：

- 手机上那条真实路径（新建文件夹 → 建工作区 → 开会话）走通，会话被 attach ✓；
- 宿主收到的请求里**从未**同时出现 workspaceId 与 cwd（计数器为 0）；
- 只给 cwd（已登记的目录）→ 也会 attach；未登记的目录 → 老实只带 cwd；
- 不存在的 workspaceId → 如实报 `not found`，不静默降级。

**反向验证**：拿改动前的桥接跑同一份用例 → 11 项红，第一条就复现出用户看到的
那句 `session.create accepts workspaceId or cwd, not both`。

真机：桥接重载后用"不存在的 workspaceId + 真实 cwd"探针打一次，
报的是 `workspace "ws-nope" not found` —— 说明 cwd 已经被丢掉、满足二选一
（改动前这里报的是 `not both`）。这个探针**不创建任何东西**，
所以没有留下空会话。

合计：离线 7 组 236 项全过。

## 44. "问题跑到电脑上去了，手机一直不回复" —— 投递只走了一条会断的通道

用户报：在手机上开的新会话里，harness 让他"做选择"，可手机上一直没动静，
最后打开电脑才发现选择框在电脑上。

### 44.1 先把事实钉住

桥接的 `diag` 里留着那次提问的记录：

```json
"lastQuestion": {"sid":"session-f5256829-…", "watched": true,
                 "questionCount": 4, "intercepted": true}
```

- `questionCount: 4` —— agent 一次问了 4 个问题；
- `watched: true` —— **提问那一刻，手机确实在看着这个会话**
  （这个心跳是 App 前台 + 开着该会话时才会打的，所以"用户就在手机前面"是确定的）；
- `intercepted: true` —— 桥接把问题判给了手机，**没有**走电脑那条链路。

也就是说：桥接认为"手机在看"，于是扣住问题等手机回答；
手机上却一个字都没出现；问题一直扣着，最后才被交还电脑。

### 44.2 根因：判定"能不能送达"用的是心跳，投递却只走会话流

```js
const streamClients = sessionStreamClients[sid]        // 会话流有没有订阅者
if (!sid || !questions.length || !isWatched(sid)) return fallback()
pendingQuestions[id] = entry
pushQuestion(entry)                                     // 只推给会话流
```

`isWatched` 只说明"最近 15 秒内有人用 `?watching=` 报过我在看这个会话"，
**不代表那条会话 SSE 真的有人连着**。而 `sessionStreamSend` 在没有订阅者时
是**静默返回**的。于是出现最坏的组合：

> 心跳是新鲜的（判给手机），会话流那一刻没有订阅者（推给空气）。

问题被扣住，手机看不见；`expireQuestions` 要等到 120 秒上限才交还电脑 ——
用户看到的就是"手机一直不回复，两分钟后电脑弹出选择"。

**为什么会没有订阅者**：除了网络抖动，还有一个我自己造出来的原因 ——
每次在运行的进程里重载桥接（调试路径）都会新建一个实例，
而 `dispose()` 只断了状态流、**没有断单会话流**。手机那条 SSE 还挂在
**老实例**上（它确实活着，消息照收），而新的心跳打到了**新实例**上。
于是新实例 `sessionStreamClients` 是空的，却被心跳告知"手机在看" ——
分裂成"心跳在新、事件在旧"。实测：重载后 `sessionStreams` 12 秒都回不来。

### 44.3 三处修

1. **问题跟着状态轮询走**（`/phone/state?watching=` 里多一个 `question` 字段）。
   状态轮询每 3~5 秒一次、同时就是心跳 —— 只要心跳说"我在看"，
   下一轮轮询必然把问题带上。会话流降级成"让用户更快看到"的快通道。
2. **会话流一开就补推一次**：断线重连、App 重建、切回前台都能补上。
3. **`dispose()` 断掉单会话流**：reload 之后手机重连到当前实例，
   不再有"心跳在新、事件在旧"的分裂。

顺带修掉一个调试期的隐患：`installQuestionHook` 原来直接
`original = uq.ask`，而 reload 时那已经是上一个实例的包装函数 ——
钩子会随 reload 一层层嵌套、兜底链指向已经 dispose 的实例。
现在包装函数上挂 `__dshPhoneOriginal` 指向真原始函数，装之前先剥到底。

App 侧：`_question` 现在**同时**从会话流的 `question` 事件和状态快照里的
`question` 字段取。取法只有两条规则（`questionToShow`，有纯逻辑用例）：
只显示本会话的、**只增不清**（清除只由 `question-done`/回答成功/切会话负责，
否则一份早于问题到达的快照会把刚显示出来的卡片抹掉）。

### 44.4 验证

新增 `tests/bridge/question-harness.mjs`（24 项）。它的假宿主里那段
`userQuestions.ask` 是**按真实契约**接管的，所以能真的验"扣住/交还/回答"：

- ★ 心跳新鲜但**会话流没有订阅者**时，状态轮询里必须带着这个问题（出事的那组合）；
- ★ 会话流连上时补推（覆盖断线重连）；
- 心跳过期 → 结算为 `expired` → 立刻交还电脑，并把原因记在 `diag`；
- 手机通过 `/phone/answer` 回答 → 原链路拿到答案、状态里不再带它；
- 问的是别的会话时不会串台；
- ★ 再挂一次实例（reload）后钩子仍只有一层。

**反向验证**：拿改动前的桥接跑同一份用例 → 15 项红，
"状态里带着问题""会话流补推""心跳过期交还"全都不成立。

`diag` 里新增 `lastQuestion.streamClients` 与 `settledReason`：
下次再出这类问题，一眼就能看出"推的时候到底有没有人在听"。

## 45. "小程序又连不上了" —— 动态插件活不过一次重启

用户第二次报连不上。这次的现象很干净：**本机回环 `/phone/health` 都是 404**
—— 不是网络问题，是桥接根本没挂载。

### 45.1 时间线（对上了）

| 时刻 | 发生了什么 |
| --- | --- |
| 23:28–23:29 | `dsh web` 被重启（进程 `etimes` 578s，父进程是一个 fish） |
| 之后 | `/phone/health` → **404**：桥接不见了 |
| 23:33–23:43 | profile 的 `package.json` / `cordis.patch.yml` 被改（与本次无关） |

原因一句话：**桥接一直是「动态插件」，而动态插件的定义只存在进程内存里**
（`~/.dsh` 下搜 `bridge-2`/`pkg-6` 只搜得到会话记录，没有任何持久化存储）。
进程一重启，它就没了。这正是我自己在 `gen-dynamic.mjs` 里写过的
"生产不要用这条路径 —— 动态插件重启即失效"。

**"出现过两次"就是这么来的**：只要 `dsh web` 重启一次（更新、改配置、
甚至手滑 Ctrl-C），手机端就断一次。

### 45.2 远程修好它（没有重启、没有数据线）

把桥接装成 **profile bundle**，它就随 harness 常驻：

```bash
# 1) profile 里登记（等价于 dsh plugin --profile web add <repo>/bridge，
#    但用手写符号链接，避免 pnpm 重写 node_modules 打扰正在跑的进程）
~/.dsh/profiles/web/package.json
  dependencies:        "dsh-phone-bridge": "file:<repo>/bridge"
  dsh.profile.bundles: [..., "dsh-phone-bridge"]
ln -s <repo>/bridge ~/.dsh/profiles/web/node_modules/dsh-phone-bridge

# 2) 离线校验组合结果（不需要跑实例、不会碰正在跑的进程）
dsh --profile web --dump-config | grep -A4 phone-bridge
#   - id: phone-bridge
#     name: dsh-phone-bridge
#     config:
#       token: ''
```

**它当场就挂上了** —— 改完 profile 后 `/phone/health` 立刻 200，
手机（`stateClients: 1`，且当时数据线是拔的 → 只能走 tailnet）也马上连了回来。
说明当前这套 harness 会热应用 profile 变更，不必停机重启。

（仍留了后路：`scripts/enable-bridge.sh --status` 看装没装，
`--revert` 干净卸载；`parkReload: startup` 写的是"补丁层在启动时参与组合"，
但实测运行中也会被应用，这一条与文档不符，值得记着。）

### 45.3 教训

- **调试用的动态插件，不能是唯一的生产路径。** 手机端依赖它，
  就等于"这台电脑一重启，手机就失联"，而且现场看起来像"小程序 bug"。
- 排查这类问题第一步永远是 **本机回环先打一发**：
  `curl -w '%{http_code}' http://127.0.0.1:3080/phone/health`。
  404 = 桥接没挂载（部署问题）；超时 = 网络/tailnet 问题。两者修法完全不同。
- 数据线不在也能验：`tailscale serve status` 看端口发布，
  再用 `/phone/diag` 的 `stateClients` 看手机上没连上
  —— 它是"手机是否真的连着桥接"的直接证据。

## 46. "页面左下角黄色自动重连 → 重连失败" —— 不是网络，是宿主太忙

> **完整报告另存一份**：`docs/harness自身问题-自动重连失败.md`
> （现象 / 如何证明不是网络 / 根因与默认值 / 四档解决方案 /
> 给 harness 上游的 8 条建议 / 一手证据与复现命令）。本节是摘要。

用户报：harness 页面左下角黄色「自动重连」，接着「重连失败」，
他只好重启 `dsh web`（而重启把当时的动态插件桥接弄丢了，见 §45）。
他还补了一句更关键的观察：**"就在我问你的这段时间里又出现了同一个情况，
你的思考直接被打断从而停止输出"**。

### 46.1 先看日志：什么都没有

| 查了什么 | 结果 |
| --- | --- |
| `~/.dsh/logs/dsh-web.log` | 只有重启标记；4 份 startup dump **全是 `EADDRINUSE`** |
| 会话日志里的事件类型直方图 | **中断/取消类事件 0 条** |
| `turn/start` vs `turn/end` | 55 : 54 —— 差的那个就是**当时正在跑的这一轮** |
| 监听 3080 的进程 | 还是 `1597028`，已连续存活 35 分钟**没重启过** |

结论很硬：**harness 进程一直活着，agent 也一直在干活** ——
会话日志在"我被打断"那段时间里每几秒就有一条 `tool/call`/`tool/result`。
断的是**浏览器与宿主之间那条连接**（页面收不到流，看起来就像我停止了输出），
不是 agent。

顺带解释为什么"查不到日志"：harness **不写连接日志**，进程也没崩，
startup dump 只在启动失败时写（那 4 份全是 `EADDRINUSE` —— 用户在旧实例还在跑时
又起了一个，第二个必然起不来；**同一时刻只能有一个实例占 3080**）。

### 46.2 机制：客户端的"就绪窗口"默认只有 15 秒

`@deepseek-ai/dsh-client-connection` 的 Config schema（用 Config Inspect 读的）：

```js
recovery: {
  backoffBaseMs: 500, backoffFactor: 2, backoffMaxMs: 10000,
  generationReadyWarnMs: 3000,
  generationReadyTimeoutMs: 15000,   // ★ 连接"就绪"只给 15 秒
}
```

超时后客户端抛 `connection generation was not ready within 15000ms`，
然后按退避重试；**负载持续时就会连续失败 = 界面上的"重连失败"**。
浏览器和 harness 在同一台机器上、走 `127.0.0.1` 的 WebSocket ——
所以"网络条件好"跟这件事完全无关，**决定因素是宿主事件循环有多忙**。

这台机器确实很忙（当时的读数）：

| 指标 | 读数 | 含义 |
| --- | --- | --- |
| `vmstat` 的 `cs` | 24k–56k /秒 | 每秒几万次上下文切换 —— 大量短命进程 |
| `journalctl --user` | 每秒钟几十个 `systemd-run` scope | **多个 agent 会话在并发跑**，每个工具调用都拉一个 scope |
| swap 占用 | 13 GB / 31 GB | 内存吃紧；PSI 记到过 memory `full` 全停 |
| 常驻大户 | 3×ChatGPT、Chrome、Zotero、Claude | 单机同时压着好几个 GB 级应用 |

（我自己的 `build-apk.sh` / `test-offline.sh`（每次起两个 Kotlin 编译器 JVM）
也在这个窗口里反复跑过 —— 这类构建要挑用户不用界面的时候做。）

### 46.3 改了什么

**① 把就绪窗口放宽**（写进 profile 的 `cordis.patch.yml`，实测组合树当场吃到）：

```yaml
# 注意：这两项在 Config 里是 recovery 子对象，不能平铺在 config 下
- id: connection
  config:
    recovery:
      generationReadyWarnMs: 8000
      generationReadyTimeoutMs: 45000
```

8 秒以上就开始记 warn（便于发现"慢但在恢复"），45 秒才判失败 ——
机器再忙也不至于把一次连接握手判死。**浏览器刷新一次页面**才拿到新参数。

**② 给桥接加"事件循环卡顿表"**（`/phone/diag` 的 `eventLoop`）。
桥接的 1 秒 tick 是**在宿主事件循环里**跑的，所以它迟到多少就是宿主有多忙：

```json
"eventLoop": {"tickMs":1000,"lastLagMs":12,"maxLagMs":8421,"avgLagMs":37,
              "over100ms":9,"over1s":2,"worst":[{"at":...,"ms":8421}]}
```

下次再看到黄色重连，先看这张表：`maxLagMs` 若到几十秒，就**不要怀疑网络**。
（这份代码要等下一次 `dsh web` 重启才生效 —— bundle 的**代码**改动不会热加载，
只有 profile/package.json 这类组合变更会。）

### 46.4 以后怎么办

1. **看到黄色重连，先别重启**：进程多半是活的，agent 也在跑。
   终端里打一发 `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3080/phone/health`
   —— 有响应（哪怕慢）就等它自己恢复。**重启会打断正在跑的会话**
   （这正是当时把桥接弄丢的那一刀）。
2. **别起第二个实例**：`EADDRINUSE` 那 4 份 dump 就是重复启动。
   端口被占 = 已经有一个在跑。
3. **降负载**：关掉用不上的 GB 级应用；别同时开多个重活会话；
   构建/批测挑没人用界面的时候跑。
4. （可选，最省心）用 systemd 用户单元把 `dsh web` 托起来并 `Restart=always`：
   真死了自动拉起来，而桥接现在是 profile bundle，手机会自己连回来。
   需要用户明确同意再装 —— 它会改变"怎么启动 harness"这件事。

## 47. 点进会话落在哪儿：有新回复去最新，没有才回原位

用户 2026-10-16 的要求（原文意思）：

> 如果会话到了**未读消息区域**，点进去应该**直接定位到最新内容**；
> 只有当它在「最近看过」里、**甚至已经被挤出 6 条之外、而且没有新消息**时，
> 才应该定位到上次看过的地方。

### 47.1 原来的行为错在哪

原来的判断只有一句：

```kotlin
val saved = settings.chatScroll(sessionId)
_chatFollowTail.value = saved?.followTail ?: true
pendingScrollRestore = saved?.takeIf { !it.followTail && it.index > 0 }
```

它**只看"上次停在哪"**，完全不问"有没有新回复"。于是点进一个未读会话，
你会被丢回上次那一段，还得自己往下翻到新回复 ——
"未读提醒"和"点进去看到的"对不上，这是最让人恼火的一类不一致。

### 47.2 现在的规则

抽成一个纯函数（`Models.kt` 的 `planEntryScroll`，有单测）：

| 进入时的状态 | 落在哪 |
| --- | --- |
| **有新回复**（该会话在「未读回复」区） | **直奔最新**（跟随尾部） |
| 没有新回复 + 上次停在中间某处 | **回到上次的位置**（索引 + 偏移） |
| 没有新回复 + 上次就在尾部 / 没存过 | 看最新 |

"有新回复"的判据 `hasRepliesSince(activity, seenSeq)` 与未读角标**同源**
（`lastReplySeq > 已读水位线` 且最后说话的是助手），但**不看 7 天窗口**：
角标关心"这条回复还新不新鲜"，而"进来该落在哪儿"只关心内容有没有变多 ——
隔了半个月也算有新内容。

### 47.3 两个必须留意的实现细节

1. **判据要在 `markSeenNow()` 之前算**。`openSession` 一进来就把已读水位线
   推到最新（"点进去的瞬间就标已读"，否则快速进出会漏标），
   之后再问"有没有新回复"永远是 false。所以 `hadNewReplies` 在最前面取好，
   后面才用。
2. **"被挤出最近 6 条"不影响回位**。阅读位置按**会话 id** 存在
   `scroll_<id>` 里；`markSessionOpened` 只裁剪 `KEY_RECENT` 那张
   「最近打开」表（`RECENT_MAX` 条），**不碰** `scroll_*` 与 `seen_*`。
   所以列表里看不见的会话照样回得去 —— 这条我特意去 `Settings.kt` 核对过。

### 47.4 验证

`tests/ansi/LogicTest.kt` 新增 11 项，其中两条是这次的钉子：

- ★ 有新回复 → 直奔最新（`followTail=true`、不带旧索引）；
- ★ 没有新回复 → 回到第 42 条 / 偏移 7；
- ★ 还把**旧规则**的取值也算出来对一遍（旧规则会给 42，新规则给"尾部"），
  防止以后被改回去；
- 判据本身：水位线已到最新 → false、最后说话的是用户 → false、
  没有活动信息 → false、**不看 7 天窗口** → true。

### 47.5 真机验收（以及它抓到的第二个 bug）

澎湃禁止 `adb shell input`（注入点击被 MIUI 挡），所以验收是这么做的：

1. **造状态**：`adb shell run-as com.dsh.phone` 取出
   `shared_prefs/dsh-phone.xml`，改掉 `scroll_<sid>`（阅读位置）与
   `seen_<sid>`（已读水位线），再 `run-as cp` 放回去；
2. **进会话**：`adb shell am start -n com.dsh.phone/.MainActivity --es sessionId <id>`
   —— App 支持用 Intent 直接落到某个会话（`openFromIntent`），这条路不需要点击；
3. **读屏幕**：`uiautomator dump` 把屏上的文字与 y 坐标取出来核对
   （不用截图）。

**第一次就翻车了**：植入"存档位置=第 40 条、有未读"之后，屏幕停在
**00:32 的老内容**上，还出现了「↓ 回到最新」——说明判据判成了"没有新回复"。

根因：我原来用 `activityOf(sid).lastReplySeq` 与会话摘要比，
而**冷启动**（`am start` 直接进会话）时 `state` / `workspaces` 还没拉回来，
`activityOf()` 是空的 → 永远判成"没有新回复" → 把用户丢回上次那一段。
**"缓存里还没有"被当成了"没有"。**

改成用**加载到的历史**判断（`hasNewRepliesInHistory`）：最后一条**助手**消息的
`seq` 比进入时的水位线新 → 有新回复。历史任何时候都在手上，冷启动也准。

修完两半都过：

| 场景 | 植入的存档 | 期望 | 实测 |
| --- | --- | --- | --- |
| 有未读 | `scroll=40,0,0`、水位线落后 | 落到最新 | 无「回到最新」按钮，屏上是最新那几条（00:50–00:51）✓ |
| 无新消息 | `scroll=40,0,0`、水位线=999999 | 回到原位置 | 出现「回到最新」；屏上第一条时间 **23:50:21**，而历史页第 40 条正是 **23:50:21**（页尾是 00:29:57）✓ 精确对上 |

教训与 §44 同族：**别拿"当前还不可用的缓存"当判据** ——
要么等它到位，要么改用本来就可靠的那份数据（这里是会话历史）。

## 48. "归档了但手机上没消失" + 会话列表下拉刷新

用户 2026-10-16 报的两件事，一件是 bug，一件是功能。

### 48.1 归档的语义：隐藏是**消费方**的事

宿主 `dsh-workspace` 的文档写得很直白：

> Archiving never touches workspace accounting — an archived session keeps its
> `sessionIds` slot so unarchiving restores its position.

也就是说：

- `archiveSession(id)` 只把 id 加进一个**全局归档集** `archivedSessionIds`；
- 工作区实体的 `sessionIds` **原样不动**（这样"取消归档"才能归位）；
- **"从列表里隐藏"是列表渲染方自己要做的事** —— 电脑端界面按那个集合过滤。

我的桥接原来是直接从 `sessionIds` 生成工作区树的，**没过滤** ✗
于是手机上归档完会话还在列表里。用户看到的提示
"已归档（会话日志仍然保留在电脑上）"还容易读成"电脑端不归档"，更让人困惑。

**改法**（都在桥接里，一处收口）：

```js
function archivedSet() { /* workspaceSvc.archivedSessionIds → 查表 */ }
// listWorkspaces() 里
const ids = (w.sessionIds || []).map(String).filter((sid) => !archived[sid])
```

因为 App 的三栏（未读 / 正在工作 / 最近会话）都是**从工作区树渲染**的
（`byId` 由 workspaces 构建，`pruneRecent(list)` 也吃这份列表），
所以这一处过滤就同时解决三处 ✓；通知栏的未读计数走 `/phone/workspaces` ✓ 也跟着对。

另外 `diag` 加了 `archived` 计数：下次怀疑"归档没生效"，先看它有没有变大。

App 侧的文案也改了：**"已归档：已从手机列表里移除（电脑上的会话日志仍然保留）"**；
宿主拒绝归档时的原话是英文的 `cannot archive session 'x': the session is active (…)`，
现在翻译成 **"这个会话还在电脑上跑着，先停止它再归档"**。

### 48.2 下拉刷新

会话页包了一层 Material3 的 `PullToRefreshBox`，新增 `pullRefresh()`：

**一次拉两样（状态 + 工作区树）**，而不是只拉列表 —— 列表是工作区树渲染的，
但"未读 / 正在工作"要靠状态里的 activity；只拉一个会出现
"会话没了但未读角标还在"这种半截状态。

`refreshing` 与 `conn.phase` 分开：前者是"用户刚拽了一下"，后者是"链路通不通"。

### 48.3 验证与部署状态

- 新增 5 项离线用例（`create-harness.mjs` 17 → 22）：归档前在列表里 →
  归档后消失 → **工作区记账没被改**（保证能归位）→ `diag.archived` 计数 →
  取消归档后回来。**反向验证**：改动前的桥接跑同一份用例，2 项红 ✓。
- ⚠️ **桥接的代码改动不能热加载**（这次踩到了）：Node 的 ESM 模块是按 URL 缓存的，
  用 `plugin_manager` 把插件 disable/enable 一遍只会**重新应用插件定义**、
  仍然复用缓存里的旧模块 —— `archived` 字段依旧不出现。
  要生效只能**重启 `dsh web`**。
  顺带一个坑：这次 disable/enable 往 profile 的 `cordis.patch.yml` 里写进了
  一行 `- id: phone-bridge / disabled: false`（默认值，纯噪音），已还原。

## 49. "手机上报了个错" —— 三处都没有记录

用户传完 7 张截图后说 App 报了个错，问"有没有日志记录"。查下来**三处全空**：

| 查了哪里 | 结果 |
| --- | --- |
| App 的提示 | `say()` 只写内存里的一个 toast，**不落盘**，闪完就没了 |

而 7 个文件在附件库里**尺寸分毫不差**、头都是 `ff d8 ff`（见 §41 的核对方式）。
也就是说：**那个错没有毁掉上传**，但它也没留下任何可供事后判断的痕迹。

### 49.1 让它以后有据可查（两边都加）

**手机侧：错误记录（落盘）**

- `say()` 里顺手判断"这句话是不是出错了"（`looksLikeError`：带
  「失败/错误/连不上/超时/没拿到…」等字样），是就写进 `errorLog`，
  **最新的在最上面，最多 50 条**，存在 prefs 里 —— **不用数据线也能看**。
- 为什么用关键词而不是给 30 多个调用点各加一个 `fail()`：改动面小、不会漏；
  而"话里带失败"这件事本身足够可靠（谁会写"上传失败"表示成功）。
- 连接层的断开（不走 `say`）单独记一笔。
- 界面：**设置 → 错误记录**，显示最近 20 条 + 「清空记录」。

**电脑侧：失败请求留痕**

- 桥接在 `sendJson`/`sendText` 里记 `status >= 400`：路由（`res.__phonePath`
  /`__phoneMethod`，挂在 res 上而不是模块变量 —— 异步处理多个请求不会串）、
  状态码、错误文案，**最多 30 条**；`/phone/diag` 里能看 `http.total`、
  `http.byStatus`、`http.last`。

### 49.2 顺手修掉一个"假警报"的可能来源

共用 OkHttp 客户端是 25 秒读写超时。上传是**大 body + 可能走蜂窝**：
7 张截图每张约 0.5 MB，若上行慢，**服务端已经收下文件、响应却超过 25 秒才回来**，
用户就会看到 `传文件失败：timeout` —— 而文件其实好端端在电脑上（这次正是这个形态）。

所以上传改用**专用客户端**：`writeTimeout 180s / readTimeout 120s`，
普通请求仍是 25 秒（不让一处放大拖慢整体失败判定）。

## 50. "App 活着，但桥接那边一个连接都没有" —— SSE 半死连接

重启 `dsh web` 之后核对新代码，发现一件怪事：

- 桥接 `diag` 里 `stateClients = 0`（一条状态流都没有）；
- 可手机上 App 明明活着（`ps` 有进程），界面也在正常刷新；
- 等了 15 秒、还把 `adb reverse` 补回来、又用 intent 把 App 唤到前台，**依然是 0**。

### 50.1 根因：无限读超时的长连接会"半死"

SSE 客户端为了长连接，读超时被设成**无限**（`readTimeout(0)`）。
这在"连接一直活着"时没问题，但一旦连接**半死** —— 比如 harness 重启时
那个 socket 没有被干净关闭、或者中间设备悄悄把它丢了 —— 客户端会：

- 永远阻塞在 `read()` 上；
- **`onFailure` / `onClosed` 永远不会被调用**；
- 于是重连循环永远不启动，`stateClients` 一直是 0。

App 之所以没显得完全断线，是靠**兜底轮询**（每 3~5 秒一次 `/phone/state`）
撑着 —— 这也解释了为什么"界面看着正常、SSE 却是 0"。
之前还怀疑过"状态流循环死了"，其实是**卡死**，不是死了。

### 50.2 双向修

| 侧 | 改动 |
| --- | --- |
| 桥接 | `openSse` 把每条 SSE 登记进一张总表；新增**独立心跳定时器**（默认 20 秒，`cfg.heartbeatMs` 可注入）给每条连接写一行注释 `: ping <ts>` |
| App | `sseHttp` 的读超时从**无限**改成 **65 秒**（三次没收到心跳）→ 超时抛 IOException → `onClosed` → 重连循环接手 |

注释行（`: ...`）是 SSE 规范里"解析器一律忽略"的东西，所以既不会污染事件，
又能重置客户端的读超时 —— 两头都安全。App 的解析器本来就忽略 `:` 行 ✓。

顺带说明：桥接原来**只给终端流**做心跳（终端可以几分钟没输出），
现在心跳对**所有** SSE 生效（状态流、会话流、终端流），一处收口。

### 50.3 验证

新增 2 项离线用例（`create-harness.mjs` 22 → 24）：开一条 `/phone/events`，
把心跳间隔压到 150ms，断言 1 秒内**收到 `: ping <数字>`**、
且**不是** `event: ping`（不能污染事件）。
**反向验证**：改动前的桥接跑同一份用例，心跳那项红 ✓。
（这个用例还顺手暴露了一件事：那个 harness 原来用空定时器，
心跳永远不触发 —— 已改成真定时器。）

## 51. "加了附件以后，输入框里的字被键盘遮住"

用户报：在手机上给会话加要传的文件时，输入框里的草稿文字应该紧贴在键盘上方，
结果被键盘盖住。

### 51.1 根因：`imePadding()` 加在了**内层**的输入行上

原来的结构（简化）：

```kotlin
Column(Modifier.fillMaxSize().padding(inner)) {      // ← 根容器不吃 IME inset
    LazyColumn(Modifier.weight(1f)) { ... }          // 消息
    if (question != null) QuestionCard(...)          // ┐
    ActivityCard(...)                                // │ 这些都在输入行
    if (queue.isNotEmpty()) QueueCard(...)           // │ **外面**
    if (attachments.isNotEmpty()) FlowRow { chips }  // ┘
    Row(Modifier.imePadding().navigationBarsPadding()) { 输入框 }   // ← IME 只加在这里
}
```

`imePadding()` 只让**输入行自己**变高（在它下方留出键盘的高度）。
它外面的附件条、排队卡、提问卡**完全不缩** —— 内容一多，
整个底部块的高度就超过屏幕，而 `LazyColumn` 的 `weight(1f)` 最多只能缩到 0，
多出来的部分被挤出屏幕下沿 → **输入框（连同里面的字）落到键盘底下**。
这也解释了为什么"加了附件才明显"：附件条是最后压垮它的那几行。

### 51.2 改法：标准写法 + 给上方区域一个上限

```kotlin
Column(Modifier.fillMaxSize().padding(inner).imePadding()) {   // ① IME 加在根容器
    LazyColumn(Modifier.weight(1f)) { ... }                    // 键盘弹起时它跟着缩
    Column(Modifier.heightIn(max = 240.dp).verticalScroll(...)) {  // ② 上方那几块加上限
        QuestionCard / ActivityCard / QueueCard / 附件条 / 报错
    }
    HorizontalDivider()
    Row(Modifier.navigationBarsPadding()) { 输入框 }            // ③ 永远是最后一个孩子
}
```

- ① 让整块内容随键盘上移，而 `weight(1f)` 的消息列表吸收掉被键盘吃掉的高度；
- ② 输入框上方的卡片/附件条再多也不会无限长，内部可滚（附件多时在这里滚，
  不会再把输入框挤出去）；
- ③ 输入行是这个 Column 的**最后一个孩子**，所以它永远贴在键盘正上方。

顺带把"队列 ↔ 附件"之间那条重复的分隔线去掉（整块与输入框之间留一条就够）。

### 51.3 验证说明

这类"键盘遮挡"**没法在真机上自动验**：澎湃禁止 `adb shell input`，
而不用点击/输入法就没法把键盘调出来。所以：

- 能验的：编译通过、装机后布局不崩（`uiautomator` 能读到输入框与附件条）；
- **要用户确认的**：键盘弹起时草稿文字是否就在键盘正上方。

## 52. "加了图片以后没有删除图片的操作"

用户报：给会话加了几张图之后，找不到删除的地方。

### 52.1 根因：删除按钮只有 22dp

附件条上的删除按钮原来是这样：

```kotlin
IconButton(onClick = { onRemoveAttachment(a.receiptId) }, modifier = Modifier.size(22.dp)) {
    Icon(Icons.Filled.Close, contentDescription = "移除附件", modifier = Modifier.size(14.dp))
}
```

- **22dp 的点击区**（Material 的最小点击目标是 **48dp**），图标只有 **14dp**；
- 颜色还没指定，跟着前景走 —— 在浅色 chip 上几乎看不见。

结果就是"**看起来根本没有删除操作**"。这不是用户没找到，是真的太小了。

### 52.2 改法

- ✕ 的点击区 **22dp → 32dp**，图标 **14dp → 18dp**，并显式给颜色
  （`onSecondaryContainer`），`contentDescription` 带上文件名（无障碍也读得懂是删哪个）；
- 一个附件以上时，附件条尾部再加一个 **「清空附件」** 按钮 ——
  一次选七八张时逐个点太折磨，而"哪张不要"往往一开始就清楚；
- 对应 `AppViewModel.clearAttachments()`（只清手机侧的待发列表，
  已经传到电脑上的文件不动）。

### 52.3 教训

**"有没有这个功能"和"这个功能看得见吗、点得中吗"是两件事。** 加附件这条链上
我盯着"传没传上去"（字节、receipt、绑定），却漏了最后一步的可用性 ——
以后再放这种行内小按钮，一律按 48dp 目标 / ≥18dp 图标来，别只看它渲染出来了。

## 53. 待发附件：选中只落手机，点发送才传给电脑

用户 2026-10-16 的要求：**编辑中还没发出去的图片应该进会话缓存，而不是直接传给电脑。**

### 53.1 原来的做法有两个后果

选中文件的那一刻就 `uploadFile` 换 receipt，chip 上写的是"**已传到电脑**"：

1. **孤儿文件**：选了三张、又删掉两张 → 那两张已经在电脑的附件库里了，
   永远没人引用（宿主的附件库没有"删除"接口）；
2. **草稿性丢失**：待发列表只存在内存里 —— 退出 App（或被系统回收）就没了，
   而电脑上文件已经躺着了。**"我的东西还没发出去"这件事，手机自己都不知道。**

### 53.2 现在

| 时机 | 做什么 |
| --- | --- |
| **选中文件** | 只写进手机本地缓存 `cache/draft-attachments/<会话>/<时间戳>.bin`，加进待发列表，**不联网** |
| **待发列表** | 跟这条消息的**草稿**一起落盘（`attach_<会话id>`），切会话 / 退出 App / 被回收都不丢；文件不在的条目自动剔除 |
| **点发送** | 逐个上传换凭据 → 拼进 `prompt` 的 `content` → 成功后清空列表并删掉本地缓存文件 |
| **删除某个 / 清空** | 只删手机本地文件与存档 —— 电脑侧**从来没有过**这些文件，所以不会有孤儿 |

上传时**逐个把凭据写回存档**：万一 `prompt` 那一步失败，重发时已经传过的不用再传一遍。

存档格式（`Models.kt` 的 `formatAttachList` / `parseAttachList`，有单测）：

```
localId \t name \t bytes \t path \t receiptId
```

用制表符分列，是因为除文件名外的字段都不会有制表符，而**文件名什么都可能有** ——
所以写的时候把名字里的制表符/换行换成空格（它只用于显示与上传名，换掉无害）。

### 53.3 验证

- 离线新增 10 项（UI 纯逻辑 147 → 157）：往返不丢条目、中文与空格保真、
  **已拿到的凭据也存下来**、没传过的是 null、文件名里的制表符/换行不破坏存档格式、
  空/脏数据不炸；
- 真机：装机后 App 正常运行、未崩；
- **留给用户的一手验证**（最直观）：
  1. 选两三张图 → chip 出现（提示语现在是"点发送时才传给电脑"）；
  2. 电脑上 `ls ~/.dsh/attachments/v1/files | wc -l` **不该变**；
  3. 点发送 → 数字才涨。

> 这次真机验证被我自己打断了：用户当时正开着系统文件选择器，
> 我 `am force-stop` 抢屏把他打断了（不该在用户正用时抢）。植入的测试数据已清理干净。

## 54. 选文件只能单选 + "删除标识被挤到屏幕外"

### 54.1 单选：契约用错了

```kotlin
ActivityResultContracts.OpenDocument()      // ← 单选
```

`OpenDocument()` 就是**一次一个**的契约（回调给一个 `Uri`），所以系统选择器
不会给多选界面 —— 用户"进选图片不能一次多选"。改成：

```kotlin
ActivityResultContracts.OpenMultipleDocuments()   // 回调给 List<Uri>
```

回调里逐个读（复用原来的 `readPickedFile`），**批量加入**：一次选七八张只报一条
提示（"已加入 7 个待发附件（共 3.4 MB）"），而不是刷七个 toast；
读不到 / 超体积的按个数汇总成一句（"有 2 个没加成"）。

### 54.2 删除标识"没有"：其实是被挤到屏幕外

上一轮把 ✕ 从 22dp 放大到 32dp，用户**还是**说看不到。再查才发现真正的原因：

- chip 里的文件名 `Text` **没有任何宽度约束**；
- 小米截图的名字长这样：
  `Screenshot_2026-10-16-10-07-42-951_com.ss.android.ugc.aweme.jpg`（60+ 字符）；
- 一条 chip 被撑得比屏幕还宽 → **末尾的 ✕ literally 在屏幕外** ✗。

修法两条：

1. chip 加 `widthIn(max = 280.dp)`，文字 `weight(1f, fill = false)` + `maxLines = 1`
   + 省略号 —— 文字最多占满剩余宽度，✕ 永远留得下；
2. 文件名用 `shortFileName()` 缩成"头…尾"（**保留扩展名**，
   纯函数有单测）—— 尾部截断会把 `.jpg` 吃掉，头部才是时间戳这种有用信息。

顺带：**长按 chip 也能删**（`combinedClickable` 的 onLongClick）——
两个入口总有一个能被发现。

### 54.3 教训（第二次了）

上一轮我按"按钮太小"去修，其实**尺寸不是唯一原因**：一条内容宽度不受约束时，
排在它后面的元素会被推出可视区 —— 这类问题**不能只靠读代码里的 dp 数值判断**，
要么在真机上量（这次是拿 60 字符的真实文件名推出来的），
要么干脆给它加上宽度约束再谈大小。

## 55. "我删了待发图片，返回时却提示已上传电脑" —— 迟到的 toast

用户报：删掉待发的图片、返回上一级时，弹出**「已上传电脑」**，
于是担心"是不是真有东西占着电脑或 DSH 的缓存"。

### 55.1 先把事实核清楚（三处都没有）

| 查了哪里 | 结果 |
| --- | --- |
| 电脑附件库（11:00 之后新增） | **0 个文件 / 0.0 MB** |
| 手机本地缓存 `cache/draft-attachments/<会话>/` | **空目录**（用户删掉的图片，本地文件也真删了 ✓） |
| 存档里的 `attach_<会话>` | **0 条**（列表也跟着清空了 ✓） |
| 代码里 `uploadFile()` 的调用点 | **只有 `send()` 一处** |

也就是说：**"删了却又上传"这件事没有发生**，而这条链（选中只落手机 → 删除即清本地
→ 发送才上传）恰好被这次测试验证了一遍 —— 三个地方都干净。

### 55.2 那提示是哪来的：迟到的"已加入待发"

真正的提示是这句（`attachFiles` 成功后）：

> 已加入 N 个待发附件（共 X MB）—— **点发送时才传给电脑**

问题是**它来得太晚**：一次选 7 张图，SAF 要逐个读、逐个落盘，几秒到十几秒才读完；
这段时间用户完全可能已经**退回上一级、甚至把 chip 都删了** ——
这时才蹦出"…传给电脑"，看起来就像"我删了它却上传了"。

两个错都在我：

1. **文案容易被误读** —— "传给电脑"四个字太像"已上传"。改成
   **「已加入 N 个待发（还没传到电脑，点发送才传）」**，把否定词放前面；
2. **迟到的提示没有作废机制** —— 现在弹出前先确认
   "会话还开着 **且** 这些附件还在列表里"，否则**一声不响地放弃**。

### 55.3 与 §53 的关系

§53 改掉了"选中即上传"，但把 toast 挪到了"加入待发之后"却忘了它可能**迟到**。
教训：**异步完成时再报的提示，必须重新校验"此刻还成立吗"** ——
否则用户看到的是"过去的动作"被当成"现在发生的事"（同一个坑：删除后仍报成功、
撤回后仍报已发）。

## 56. "看不到有后台任务的会话的运行状态"

用户报：带后台任务的会话，在列表里看不出它在跑。

### 56.1 根因：三栏判据只看 `running`，没看 jobs

`refreshWorking()` 原来只有一句：

```kotlin
if (fresh[s.id] ?: s.running) out.add(s.id)
```

而**后台任务的生命周期常常长过一轮**：`nohup` 起的训练、子代理、长跑实验 ——
agent 那一轮早就结束了，`running` 是 `false`，可活儿还在跑。
于是这种会话既不进「正在工作」（判据漏了），也不进「未读」（已读、且未读本身
要求 `agentSpokeLast`）→ **它从三个板块里消失了**，用户以为它没在跑。

`SessionInfo.activeJobs` 早就有了（`status == running/stopping`），只是没人用它做判据。

### 56.2 改法

1. **判据**（`Models.kt` 的纯函数 `sessionWorking(running, jobs)`，有单测）：
   `running || 有 running/stopping 的任务` → 算「正在工作」；
   `refreshWorking()` 用它，jobs 优先取 `state` 那份（比工作区树新）。
2. **看得见**（卡片 `jobsBadgeText(jobs)`，也有单测）：
   - 只有一个任务 → 直接写它的名字（`⚙ npm run dev`）——
     用户要的是"它在忙什么"，不是数量；
   - 多个 → `⚙ 3 个后台任务`；没有在跑的 → `null`（不占地方）；
   - 图标也区分：**agent 在跑**用转圈，**只剩后台任务**用 `⚙`
     （一眼看出是哪种忙）。

### 56.3 一个省事的选择：jobs 从 state 取，不动桥接

工作区树（`/phone/workspaces`）那份**不带 jobs**，`/phone/state` 那份带。
本来打算给桥接的工作区接口也补上 jobs —— 但那要**再重启一次 `dsh web`**
（ESM 模块缓存，见 §50）。而 App 本来就同时持有 `state`（三栏判据一直用它），
所以卡片按 id 去 `state.sessions` 里查 jobs 就够了 —— **少一次停机**。

（顺手记一条：`SessionInfo` 里的 `activeJobs` 早就在，问题从来不是"没有数据"，
而是**判据没用它**。这类"数据有、判据漏"的 bug，先看判据再怀疑数据。）

## 57. 没有数据线怎么装 APK（远程装机）

数据线在这台机器上极不稳（一天掉七八次），而且 `adb` 服务自己重启时
`adb reverse` 还会跟着丢。所以得有"不插线也能装"的路子。

### 57.1 最快的一条：临时 HTTP 分发 + tailnet 发布

App 只是**更新**（同包名同签名），所以只要能把 APK 送进手机、点一下安装就行：

```bash
# ① 把 APK 放到一个目录，起一个临时下载服务
mkdir -p /tmp/apk-share && cp android/app/build/outputs/apk/debug/app-debug.apk /tmp/apk-share/dsh-phone.apk
(cd /tmp/apk-share && setsid nohup python3 -m http.server 8099 --bind 0.0.0.0 &)

# ② 家里同一个 WiFi 直接用局域网地址；在外/蜂窝就用 tailnet 那条
#    （tailscaled 是用户态，所以必须显式 serve 一下）
tailscale --socket ~/.ts-userspace/tailscaled.sock serve --bg --tcp 8099 tcp://127.0.0.1:8099
```

手机上打开其中一条即可（两条都可用时优先局域网，快）：

- 同 WiFi：`http://<电脑局域网IP>:8099/dsh-phone.apk`
- 任意网络：`http://dsh-home.<tailnet>.ts.net:8099/dsh-phone.apk`

收工后**记得收摊**（服务与发布都是临时的）：

```bash
pkill -f "[h]ttp.server 8099"          # 注意中括号：否则会匹配到自己这条命令
tailscale --socket ~/.ts-userspace/tailscaled.sock serve --tcp 8099 off
```

### 57.2 一个必须做的配套：`versionCode` 要递增

用浏览器/文件管理器装 APK 时，**系统要求新包的 `versionCode` 不低于已装的**，
否则弹"应用未安装"。`adb install -r` 比较宽容，所以这个坑只有在
"用户自己点安装"时才会暴露 —— 因此

```kotlin
versionCode = 2      // 每发一版 +1
versionName = "1.1"
```

改这一行**不改任何逻辑**，只是让"自己点安装"这条路走得通（升级安装会保留
设置、草稿、阅读位置等）。

### 57.3 以后可以更顺手（可选，需要一次重启）

桥接里加一条 `/phone/apk`：把当前构建的 APK 直接吐出来（带令牌校验）。
那样以后**在手机上点一个链接就能更新**，连临时服务和 tailnet 发布都不需要。
它属于桥接代码改动，要等下一次 `dsh web` 重启才生效（§50 的 ESM 缓存）。

另一条更强大的路是**无线调试**：手机开发者选项里开启"无线调试"并配对一次，
之后 `scripts/adb-over-tailnet.sh` 就能让 `adb` 走 tailnet ——
不只装 APK，还能远程读 logcat、跑 uiautomator（今天缺的正是这个）。

## 58. "电脑上明明有后台任务，手机上一条都看不到"

用户报：会话 `39575a11` 明明有后台进程，手机上却看不到。

查下来的事实：`/phone/state` 里 `jobs` **是空数组**、每个会话的 `jobs` 也是空 ✗，
而电脑端的 job 面板看得见 ✓ —— 说明"数据有、投影错"。

### 58.1 两个契约都读错了

宿主的 `dsh-jobs-local`：

```js
list(caller) {
  return [...this.store.values()]
    .filter((job) => job.owner === void 0 || job.owner.id === caller)
    .map((job) => this.view(job));
}
view(job) {
  const owner = job.owner?.id;
  return { id, kind, label, ...(owner !== undefined ? { owner } : {}), status, startedAt, ... };
}
```

**错 ①：`list()` 空参调用。** 过滤条件是「**无主任务** ∪ `owner.id === caller`」——
caller 传 undefined 时只会拿到**无主**的那批，而后台任务基本都是有主的
（owner 指向发起它的 agent/会话）。所以桥接的 `state.jobs` **永远是空数组**。
电脑端的 job 面板走的是另一个 API（`job-controller`），所以它照样看得见。
→ 修法：**按会话逐个问** `list(sid)`。

**错 ②：owner 字段名。** 原来读的是 `j.ownerSession` —— 这个字段根本不存在；
宿主的投影里 `owner` 就是**字符串**（`job.owner?.id`），无主任务干脆不带这个字段。
→ 修法：读 `j.owner`，缺失记 `null`。

### 58.2 顺手躲掉一个"会重复"的坑

`list(caller)` 会把**无主任务返回给每一个 caller** —— 按会话逐个问之后，
无主任务会被塞进来 N 次。所以还要**按 id 去重**（这个坑是离线用例的输出里
先露出来的：`["job-unowned","job-owned","job-unowned","job-unowned",…]`）。

### 58.3 验证

`create-harness.mjs` 里加了一组**契约用例**（假 jobs 服务**逐字照抄**宿主的
`list(caller)` 过滤 + `view()` 投影两层语义）：

- ★ 有主任务必须被报出来（空参调用就会永远为空）；
- ★ owner 填会话 id（而不是去读一个不存在的 `ownerSession`）；
- ★ 无主任务只报一次（去重）；
- 没列出来的会话的任务不会混进来；会话自己的 `jobs` 不夹带别人的。

**反向验证**：改动前的桥接跑同一份用例，3 项红、报的正是 `["job-unowned"]` ✓。

> 教训：**"电脑上有、手机没有"先怀疑投影，别怀疑数据** —— 这次数据一直好好的，
> 是两个字段/调用方式读错了。而且这类错误**不会报错**（`safe()` 把它吞成空数组），
> 只会安静地少东西 —— 所以每读一个宿主 API，都要有一条"它到底返回什么"的用例。

## 59. "点开子代理会话的历史就报错"

用户报：会话 `c94ebae3-…` 的历史打不开。

### 59.1 诊断只花了 30 秒 —— 因为昨天加了 `diag.http`

```json
GET /phone/sessions/c94ebae3-…/history -> 500
  "subagent Sessions require their durable parent address"
```

（§49 加的"失败请求留痕"第一次真正派上用场：手机上报错、电脑这边**直接有据**，
不用再猜、也不用读 logcat。）

### 59.2 根因：地址有两套，我只用了其中一套

宿主的 `dsh-api-session-controller` 里 `validateAddress`：

```js
if (address.kind === "session") {
  if (header.origin === "subagent")
    throw new RemoteError("session/agent-busy",
      "subagent Sessions require their durable parent address", …);
  return;
}
// 子代理走这里：必须带父会话，且 mode 要对得上
if (header.origin !== "subagent" || header.parentSession !== address.parentSessionId) throw …
```

也就是说：**子代理会话（`origin === 'subagent'`）不能用 `{kind:'session'}` 的地址读**，
得给 `{kind:'subagent', parentSessionId, childSessionId, mode}`。
而桥接在**三处**都写死了 `{kind:'session', sessionId}`（历史快照、翻页、实时流）。

而父会话 id 一直都在手上：`sc.list()` 的每项就带 `origin` 与 `parentSessionId` ——
**又一次"数据有、没用它"**（§58 同族）。

### 59.3 改法

- `sessionMeta` 缓存（`buildState` 顺手记下 `origin`/`parentSessionId`）；
- `resolveAddress(sessionId)`：缓存命中就同步给答案，没命中就问一次 `sc.list()`；
  是子代理就返回 subagent 地址（`mode: 'unknown'` —— 宿主只在
  `address.mode !== 'unknown'` 时才比对），否则返回普通 session 地址；
- **三处全部改用它**：`loadHistory`（快照与 `page` 两条路）、`handleSessionStream`；
- App 侧：给"往子代理会话发消息"一句人话
  （宿主原话 `durable parent address` → **"这是子代理会话，只能看历史"**）。

### 59.4 验证

`create-harness.mjs` 的假宿主里加了 `validateAddress`（**逐字照抄宿主的两层校验**）
和一个子代理会话：

- ★ 子代理会话的历史能读（HTTP 200 + 有消息）；
- 对照：普通会话的历史照常能读（别把所有人都改坏）。

**反向验证**：改动前的桥接跑同一份用例 → 2 项红，而且报的就是用户那句
`subagent Sessions require their durable parent address` ✓。

## 60. "在子代理里发不出消息"

用户报：打开子代理会话以后发不出消息。

### 60.1 宿主其实留了门，只是不在 sessionController 上

上一节（§59）修历史时看到的错误里就写着 **`use subagent delivery for this child session`**
——即"别用会话路由，用子代理投递"。宿主的原话（`dsh-subagent`）：

```js
// 服务 ctx.subagents 上的方法（浏览器/宿主都走这条）
async prompt(request, signal) {
  const { parentSessionId, childSessionId, clientTimeZone, delivery } = request;
  validateControlRequest("subagent.prompt", request);
  const parent = this.ctx.get("agents")?.get(parentSessionId);
  if (parent === void 0) throw new RemoteError("subagent/parent-unavailable", …);
  const source = { kind: "user", rpcId: request.requestId, … };
  … // 文本直接过；含图片/文件的部分走 attachments.admitPromptContent
  return { messageId: await this[deliverSubagentPrompt](parent, childSessionId, content, source, signal, delivery) };
}
```

三个必须照做的细节：

1. **control schema 只认 `mode: 'continuable'`** —— 一次性子代理（`one-shot`）
   **本来就给不了消息**（不是 bug），所以得给用户一句人话，而不是把 schema 报错抛出去；
2. **父会话必须是活的**（`agents.get(parentSessionId)`），否则 `subagent/parent-unavailable`；
3. 停止子代理也有自己的门：`interruptByParent(child, parent, 'continuable')`。

而"这个子代理是一次性还是可续谈"**就在会话投影里**（`projections.values.subagent.mode`
= `one-shot` | `continuable`）—— 又一次"数据有、没用它"。

### 60.2 改法

- `subagentsSvc = ctx.get('subagents')`；
- `sessionMeta` 多记一个 `subagentMode`（buildState 与 resolveAddress 两处都记）；
- `doPrompt`：目标 `origin === 'subagent'` 时改走 `subagents.prompt({…mode:'continuable'…})`；
  一次性 → 直接拒绝并给中文提示；父会话不在 → 提示"父会话没开着"；
- `doCancel`：子代理改走 `interruptByParent`。

### 60.3 验证

假宿主里加了 `subagents` 服务（**照抄** control schema 的 `mode:'continuable'` 与
"父会话要活着"两条），并让假 `sessionController.prompt/cancel` **照抄**宿主对子代理的拒绝：

- ★ 能给可续谈的子代理发消息（且确实带 `mode`/`delivery` 走了 subagents.prompt）；
- ★ 一次性子代理给的是中文提示，不是宿主原话；
- 普通会话发消息照常（别把所有人改坏）；
- ★ 能停止子代理（走 `interruptByParent`）。

**反向验证**：改动前的桥接跑同一份用例 → 3 项红，报的正是用户那句
`use subagent delivery` ✓。合计 8 组 **346 项**全过。

> 这条链今天问了三次同一个问题："电脑上有的，手机为什么没有？"
> 三次都是**同一类错**：宿主把信息/门放在 A 处，我一直在 B 处找
> （§58 空参调用、§59 地址只认一套、§60 手段只认一套）。
> 所以每接一个宿主能力，先看它**有没有第二扇门**（`grep` 那句错误提示本身，
> 它常常直接写着该走哪儿）。

## 61. 让桥接"改完不用重启"：带版本号的动态 import

### 61.1 问题

桥接是**静态宿主插件**：改了 `bridge-core.js` 必须重启 `dsh web` 才生效
（§50 的 ESM 模块缓存）。而重启会打断用户正在跑的会话 ——
今天为桥接改动重启了四五次，每次都要用户手动来。

### 61.2 机制：Node 的模块缓存按**完整 URL**（含 query）索引

```js
import('./core.js?v=1')   // 实例 A
import('./core.js?v=1')   // 还是 A（缓存命中）
import('./core.js?v=2')   // 实例 B ← 新代码
```

所以只要**在加载时把文件版本拼进 query**，每次重新挂载都会拿到一份新实例，
老实例由 disposer 正常卸载（终端、SSE、监听全清）。这条假设用真文件真 import
钉在 `tests/bridge/reload-harness.mjs` 里（"同一 URL 命中缓存" + "换 query 拿新代码"）。

### 61.3 三层结构（关键是**入口绝不承载业务**）

| 文件 | 职责 | 要不要改 |
| --- | --- | --- |
| `lib/entry.js` | 薄壳：按 mtime+size 拼 query，动态 import `mount.js`；同步注册 effect | **永远不改**（见下） |
| `lib/mount.js` | 挂载层：解析令牌、动态 import `bridge-core.js`、返回 disposer | 偶尔改（开关插件即生效） |
| `bridge-core.js` | 桥接实现 | 经常改（开关插件即生效） |

**为什么入口必须空**：Node 的缓存同样锁住入口自己 —— 实测**改完入口代码后，
`plugin_manager` 开关一次拿到的还是旧的入口**（这次实测过：报的仍是 `version 6`）。
更狠的是，我试过"换一个新文件名 + 改 `package.json` 的 `main` 指过去"，
**也没用** —— 宿主对"包 → 入口"的解析结果同样被缓存了。所以：

> **安装这个机制本身，必须重启一次；装完之后，`mount.js` 与 `bridge-core.js` 的改动
> 就只需要开关插件。** 真到了必须改入口的那天，换新文件名 + 重启一次即可。

### 61.4 生命周期细节（踩过的坑）

- `ctx.effect` 的工厂函数要返回 **disposer**，而"加载模块"是异步的 ——
  所以做成：**同步登记 effect**，把 `import()` 放进 effect 内部，
  disposer 同步返回并带一个 `cancelled` 标志（加载还没完成就被卸载时不挂载）；
- `mount.js` **不再自己登记 effect**：effect 的主人只有一个（入口），
  否则卸载语义会重叠（实测用例专门钉了这条：`mount.js` 里不许出现 `ctx.effect`）；
- 每次加载都拼一个随机后缀：同一毫秒内改两次（或被 `touch`）时 mtime 不变，
  版本号只用于"区分这一次加载"，不需要稳定。

### 61.5 用法（改完桥接之后）

```bash
# 插件管理器里把 include:phone-bridge 关一次再开一次（我这边用 plugin_manager 工具做）
# 然后核对版本：
curl -s -H "x-phone-token: <token>" http://127.0.0.1:3080/phone/health
```

`/phone/health` 里的 `version` 就是核心文件的 `VERSION` 常量 ——
**改它就等于"这次改动生效了吗"的自检**。今天的核实流程：
① 记下当前 version → ② 改 `bridge-core.js`（含 `VERSION += 1`） →
③ 开关插件 → ④ 再打 health，version 变了就是生效了。

## 64. "看思维链时，会话突然跳到上一条消息的最上方"

用户报：会话 `e994c242` 收到 headless+timer 的**上下文注入**时，他正在看某条回复的
思维链，页面却跳回**上一条消息的开头**。

### 64.1 根因：消息列表没有 `key`

```kotlin
items(visible.size) { i -> MessageRow(visible[i], onOpenFile) }   // ← 没有 key
```

Compose 的 LazyColumn 在**没有 key** 时按**位置**复用每一项。而会话里随时会有新消息
插到中间 —— 最典型的就是 harness 注入的上下文（§63 刚把它的显示打开，
于是"插入"从"看不见"变成"看得见"）。一插入：

- 后面每一项的位置**整体下移一格** → 你正在看的那条被顶走，
  屏幕跳回上一条的开头（用户看到的现象）；
- 每个气泡自己的 `remember` 状态（思维链展开、参数展开、结果展开）
  也按位置错位 → 展开的那条"变成"了别的消息在展开。

### 64.2 改法：给每一项一个稳定 key

```kotlin
val msgKeys = remember(visible) { stableMessageKeys(visible) }
items(count = visible.size, key = { i -> msgKeys[i] }) { i -> MessageRow(visible[i], onOpenFile) }
if (streamText.isNotEmpty() || ...) item(key = "__stream__") { StreamingRow(...) }
```

`stableMessageKeys()`（纯函数，有单测）用**宿主给的事件序号 `seq`** 打底
（`"${seq}:${role}"`），同一 seq 重复出现时补 `#2` 后缀 ——
**重复 key 会让 Compose 直接抛异常**，所以要防。
有了稳定 key，Compose 按 key 锚定当前项，中间插入新消息**不会移动视线**。

顺带：`__stream__` 那个"正在流式输出"的临时行也给了固定 key（它是唯一的临时项）。

### 64.3 验证

- 单测：每条都有 key、key 互不重复、**中间插入一条后原有 key 全部不变**
  （这是"不跳位"的充要条件）、重复 seq 也不产生重复 key；
- 真机数据：用户报的会话历史 142 条，`seq` **全部唯一** ✓（key 稳定性的前提成立）；
- 合计 9 组 **379 项**全过。

> 这条和 §63 是连着的：**把一个原本隐藏的东西显示出来，会顺带激活它引发的布局问题。**
> 以后"打开某个被过滤掉的内容"时，第一件事应该是检查列表有没有 key。

## 65. "有一个待发的消息，手机上看不到"

用户报：会话 `3018ca07` 里明明有一条"代发/待发"的东西，手机上看不到。

### 65.1 先核事实：不是待答问题

`/phone/state?watching=session-3018ca07` 里 `question = null`。查投影才知道真相：

```
GET /phone/debug/observe?sessionId=session-3018ca07…   （这次为排查新增的、带令牌的诊断口）
→ projectionKeys: title, goal, tokenUsage, contextPressure, …, inbox, userQuestions, todos, plan, …
→ userQuestions: {"active": [], "settled": []}      ← 真的没有待答问题
```

也就是说那条东西是**排队中的消息**（agent 在跑时发出去、等它这一轮结束才执行的那种），
不是 `ask_user_question`。而它也没显示，因为：

### 65.2 两个"内存版"的数据源

| 数据 | 原来的来源 | 问题 |
| --- | --- | --- |
| 待答问题 | 桥接 hook 住 `userQuestions.ask`，存在**内存 map** 里 | 桥接一重载（热重载/重启）就空 |
| 排队消息 | 从 `control` 事件攒到**内存 `queues[]`** | 同上 |

而这两样东西在宿主里都是**持久化投影**：

- 待答问题 `userQuestions`：`{active: [{callId, questions, state}]}`，`state` 是 `open`/`continued`；
- 排队消息 `inbox`：`{'next-turn': [message…], 'next-step': [message…]}`。

**关键细节**：`sessionController.list()` 返回的会话项**不带投影**（标题、上下文占用
原来一直是走别的回退算出来的，所以这个限制一直没暴露）。要投影只能：

```js
ctx.get('sessionQuery').observeSession(sessionId, { projectionMode: 'all' })
// → { header, projections: { values: { …19 个投影… } }, … }   （用完要 Symbol.dispose）
```

### 65.3 改法

- 新增 `extrasFromObserve(sessionId)`：一次 `observeSession` 同时取出
  **待答问题**与**排队消息**（一次调用，别问两次）；
- `buildState`：待答问题先看 hook（快通道，带等待句柄），没有再退回投影；
- `/phone/sessions/<id>/queue` 与单会话流的 `queue` 事件：**以 inbox 投影为准**，
  内存缓存只做兜底；
- 回答投影来的问题：用 `questionSessionById`（记录"问题 id → 会话 id"）找到活 agent，
  调宿主的 `answer()`。`open` 状态（agent 正卡在 ask 里等）**答不了** —— 那种等待句柄
  在桥接重载时就没了，所以给一句人话：「还在电脑上等回答，请到电脑上回答」。

### 65.4 验证

- 假宿主的 `sessionQuery` **照抄"list 不带投影、只能 observe"** 这个限制；
  断言待答问题与排队消息都能读出来、不串台；
- **反向验证**：改动前的桥接 5 项红（`question` 为 null、队列为空）；
- 合计 9 组 **386 项**全过。

> 这条是今天第 N 次同一个根因：**"数据在宿主的内存里"和"数据在投影里"是两回事。**
> 桥接只要在内存里攒状态，热重载一次就归零 —— 而宿主的投影本来就是持久的，
> 直接读投影既不丢也不用自己维护。以后新增任何"宿主那边已经有的状态"，
> 先问一句：**它有没有投影？有就别自己攒。**

## 66. 排队消息还有两处"最后一公里"

§65 把队列改成读 `inbox` 投影之后，用户又给了个例子
（`session-b5ed21d1`）。查下来接口已经能返回那条消息了 —— 但手机上仍然看不到，
还有两处：

### 66.1 `notifyQueue` 用空缓存把手机上的队列**抹掉**

`notifyQueue()` 原来推的是内存缓存：

```js
sessionStreamSend(sessionId, 'queue', { items: queueViews(sessionId) })   // ← 内存
```

桥接重载后缓存是空的 → 它推一次空数组 → **手机上已经显示出来的排队消息被覆盖掉**
（`_queue.value = parseQueue(空)`）。这和 §65 是同一个病：**推之前要读投影**。
现在 `notifyQueue` 也走 `extrasFromObserve`，缓存只作兜底。

### 66.2 词表不一致：`next-turn` vs `queued`

宿主 inbox 投影里的位置叫 `next-turn` / `next-step`，而 App 的排队卡只认
`queued` / `steer`（`if (item.placement == "queued")`）。词对不上，卡片就会走错分支。

**在桥接里翻译一次**（`next-step → steer`，其余 → `queued`），而不是改 App ——
省一次 APK 安装，也避免了"App 版本和服务端词表"的耦合。

### 66.3 验证（这次是真机数据，不是构造）

```
GET /phone/sessions/session-b5ed21d1…/queue
→ [{"id":"865f5734-…","placement":"queued","text":"按步号分层重算 Δ_FR30，检查维度②…"}]

单会话流连上时的 queue 事件
→ event: queue / data: {"items":[{…"placement":"queued"…}]}
```

即：**手机上打开这个会话就能看到排队卡**（App 不用重装）。
合计 9 组 **386 项**全过。

> 这一串（§65+§66）的教训合并成一句：**"显示不出来"要分两段查 ——
> ① 数据有没有到接口；② 到达之后有没有被别的推送覆盖。**
> 这次是 ① 修好了、② 把它抹了，所以"改了却没效果"。

App 那边于是走到 `say("读取更早消息失败：…")`。

### 67.2 真正该补的：让"手机上的错误"在电脑上有据

今天已经有好几轮"手机上出错、我这边什么都看不到，只能靠用户描述"。所以补一条通道：

**桥接**：`POST /phone/clientlog  { lines:[…], app:"1.5" }` → 落在 `diag.clientLog`
（最近 60 条，带时间戳与 App 版本）。

**App**：`recordError()` 写完本地日志后，顺手把这一行推上去（`reportClientLog`，
best-effort，失败就忽略 —— 不能因为上报失败再弹一次错）。

这样以后"读更早失败""上传失败"这类只发生在手机上的错误，我打一次
`/phone/diag` 就能看到原文与版本号，不用再猜。

### 67.3 验证

- `POST /phone/clientlog` → `{ok:true,total:1}`，`diag.clientLog` 里能看到那一条 ✓；
- 桥接 v19（热重载生效，进程没重启）；App `versionCode 6`（`versionName 1.5`）。

> 顺带把 `oldestSeq`/`cursor` 的对接口径核了一遍：App 用"当前最小 seq"作
> `beforeSeq`（不依赖 `cursor`），所以桥接仍返回 `cursor: 0` 不影响翻页 ✓。
