# 技术路线：小米 14 Pro（澎湃 OS）上的 DSH 手机端

> 目标：在小米 14 Pro 上有一个原生应用，能**实时看到本机 harness 的状态**，
> 并且能**和 harness 实时对话**。
> 硬约束：不 root、不解锁 Bootloader、不刷机 —— 即"不弄坏手机操作系统"。

---

## 1. 先说结论：三层架构

```
┌─────────────────────────── 电脑（Arch Linux）───────────────────────────┐
│                                                                        │
│   dsh web (127.0.0.1:3080)                                             │
│     ├── 原有浏览器 UI（Typert Remote：/api + /api/remote.mux WS）        │
│     └── dsh-phone-bridge  ← 本项目新增，Host 平面 Cordis 插件            │
│           ├── 消费 webServer         → 注册 /phone/* 路由                │
│           ├── 消费 sessionController → list / follow / prompt / cancel   │
│           ├── 消费 jobs / goals / sessionTitle / agentDefaultModel       │
│           └── 对外只讲 JSON + SSE，不讲 Typert 协议                       │
│                                                                        │
└───────────────────────────────┬────────────────────────────────────────┘
                                │  adb reverse tcp:3080 tcp:3080
                                │  （USB 线内，不经过局域网、不监听 0.0.0.0）
┌───────────────────────────────┴────────────────────────────────────────┐
│                        小米 14 Pro / HyperOS 3                         │
│                                                                        │
│   com.dsh.phone （原生 Kotlin + Jetpack Compose）                       │
│     ├── 状态页   ← SSE /phone/events（会话、运行中任务、goal、模型）      │
│     ├── 会话页   ← GET /phone/state                                     │
│     ├── 聊天页   ← SSE /phone/sessions/<id>/live + POST .../prompt       │
│     └── 通知栏   ← 前台服务，同一条 SSE，关着 App 也能看                 │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

一句话：**harness 里加一个桥接插件把内部状态翻译成简单 JSON/SSE，
手机用 adb reverse 通过 USB 直连，App 是原生客户端。**

## 2. 关键取舍（以及为什么不选另外几条路）

### 2.1 为什么不在 Android 上重写 harness 的浏览器协议

harness 的浏览器传输是 **Typert Remote**：`/api` 前缀 + `/api/remote.mux` 上的
WebSocket，带 RPC 信封、schema 校验、事件/瀑布流双向调用、流式端点。

在 Kotlin 里复刻这套协议意味着：

- 把 TS 侧的类型系统手抄一遍，还得跟着上游版本同步；
- 浏览器认证（browser-auth / api-request-trust）要重新实现；
- 任何一次 harness 升级都可能让手机端静默失效。

**代价远高于收益。** 桥接插件只依赖少数几个稳定 Service
（`sessionController` / `jobs` / `goals`），升级时坏在哪一目了然。

### 2.2 为什么不用 WebView 套壳

WebView 加载 `http://127.0.0.1:3080` 确实能"零开发"拿到完整 UI。但它给的
是**浏览器界面**，不是**手机应用**：

- 状态无法进入通知栏、无法做息屏/后台提醒；
- 三指缩放一个桌面布局，触控体验差；
- 想要"打开就停在某个会话"这类手机习惯的交互做不了。

本项目保留了这条路作为兜底（见 §7），但主线走原生。

### 2.3 为什么用 SSE 而不是 WebSocket —— 一个具体的坑

桥接插件有两种装载方式：

| 方式 | 生效 | 生命周期 | 能力边界 |
| --- | --- | --- | --- |
| **静态插件**（生产） | 随 `dsh web` 启动 | 持久 | 完整 Node |
| **动态插件**（开发） | 进程内即时 | 重启即失效 | 受限 ctx，**没有 crypto** |

动态宿主只提供 `ctx / console / btoa / atob / TextEncoder / TextDecoder`
这几个 builtin。WebSocket 握手要对 `Sec-WebSocket-Key` 做 SHA-1 + base64，
**动态宿主里拿不到 crypto**，硬写一个纯 JS SHA-1 既丑又慢。

SSE 只需要一个长连接 + `text/event-stream`，两种宿主都能跑，
Android 侧用 OkHttp 读 body 流按行解析即可（本项目就是这么做的，
连 `okhttp-sse` 依赖都省了）。

实时性上 SSE 与 WebSocket 对本场景没有区别：都是服务端推送。

### 2.4 为什么走 adb reverse 而不是局域网

| | adb reverse（USB） | 局域网直连 |
| --- | --- | --- |
| 暴露面 | 仅手机回环 | 需要 harness 监听 `0.0.0.0` |
| 依赖 | 一根线 | WiFi 必须同网段 |
| 换网络 | 无影响 | 换网即失效 |
| 明文 HTTP 风险 | USB 线内 | 同一局域网可被嗅探 |

`adb reverse tcp:3080 tcp:3080` 让**手机上的** `127.0.0.1:3080` 指向电脑的
`127.0.0.1:3080`。harness 依然只绑回环，不需要任何配置变更；拔线通道即消失。

## 3. 桥接接口（`/phone/*`）

全部 JSON，UTF-8，路径前缀 `/phone`。`token` 为空时不校验。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/phone/health` | 探活，返回 `{ok,name,version,ts}` |
| GET | `/phone/state?max=60` | 整机快照：模型、会话列表、任务、goal |
| GET | `/phone/events` | **SSE**：`hello` 首帧 + 状态变化时推 `state` |
| GET | `/phone/sessions/<id>/history?max=40` | 一页历史消息（已归一化） |
| GET | `/phone/sessions/<id>/live?max=60` | **SSE**：`snapshot` → `messages` / `delta` / `attempt` |
| POST | `/phone/sessions/<id>/prompt` | body `{text}` → 投递用户消息 |
| POST | `/phone/sessions/<id>/cancel` | 打断当前回合 |
| POST | `/phone/new` | body `{cwd?}` → 新建会话 |

### 3.1 数据从哪来

| 桥接字段 | harness 来源 |
| --- | --- |
| `model` | `agentDefaultModel.currentSelection()` |
| `sessions[]` | `sessionController.list()` |
| `sessions[].title` | `sessionTitle.get(session)`（仅活会话） |
| `sessions[].goal` | `goals.get(agent)`（仅活会话，冷会话没有 Agent） |
| `jobs[]` | `jobs.list()` |
| 聊天消息 | `sessionController.follow()` 的开场快照 + 增量帧 |
| 发消息 | `sessionController.prompt({requestId, sessionId, mode:'queue', content})` |
| 打断 | `sessionController.cancel({sessionId})` |

### 3.2 两个实现上的坑（已踩）

1. **`follow` 是 `async *` 生成器**，调用即返回异步迭代器，**不是 Promise**。
   写成 `await sc.follow(...)` 或 `.then()` 会直接失败。
2. **`cancel` 是同步方法**，返回 `SessionCancelValue` 而不是 Promise，
   必须包一层 `Promise.resolve()` 才能统一处理。
3. 动态宿主**没有 `AbortController`**，而这些 Remote 方法都要求传 `signal`。
   桥接里给了一个鸭子类型替身（`aborted` / `addEventListener` / `abort()`），
   实测 DSH 只读 `signal.aborted` 并挂 abort 监听，替身足够。

### 3.3 消息归一化

harness 的会话日志是事件流（`user/message`、`assistant/message`、`tool/call`、
`tool/result`、`turn/start` …），手机不该理解这套领域模型。
桥接把它压成：

```json
{ "seq": 16, "time": 1792043924028, "role": "assistant",
  "text": "收到", "interrupted": false, "usage": {"input": 9531, "output": 2} }
```

`role ∈ {user, assistant, tool, tool-result}`。
用户消息额外带 `source`：`user` 是人说的，`plugin` / `skill-catalog` /
`runtime-context` 是 harness 注入的上下文 —— App 默认**折叠**这些，
避免手机屏幕上刷满系统提示词（可在设置里打开）。

## 4. 装载桥接的两种方式

### 4.1 静态插件（生产，持久）

`bridge/` 是一个标准的 Profile Bundle：

```
bridge/
├── package.json        dsh.bundle.patch → ./cordis.patch.yml
├── cordis.patch.yml    - insert: 一行 phone-bridge
├── lib/index.js        ESM 入口，inject: [webServer, sessionController]
└── bridge-core.js      全部逻辑（宿主无关）
```

安装：

```bash
dsh plugin --profile web add <本仓库>/bridge
# 然后重启 dsh web
```

**为什么必须重启**：web profile 的 `patchReload: startup`，
新增 bundle 只在启动时参与组合。

**为什么它属于 Host 平面**：桥接消费 `webServer` 与 `sessionController`，
服务的是整个进程的 HTTP 面，消费方（手机）在 agent 平面之外。
按 Cordis 的分层规则，这类"发布给会话之外的消费者"的能力必须挂宿主组成，
放进 agent preset 会在第二个会话挂载时冲突。

**为什么补丁层要写 `- insert:`**：`--patch` / bundle patch 默认是按 id
*覆盖已有行*，直接写 `- id: xxx` 会得到
`patch: entry "xxx" not found`。新增行必须显式放在 `insert:` 下。

### 4.2 动态插件（开发，即时）

`bridge/tools/gen-dynamic.mjs` 把 `bridge-core.js` 的函数体原样内联进
`cordis_define` 的 `code.host`，于是同一份逻辑可以在**不重启 harness** 的
前提下立刻上线调试。重启后消失，属于开发路径。

### 4.3 更省的做法：动态加载器（不内联源码）

内联 32KB 源码代价不小（去注释去缩进后仍有 32KB），而且等于在插件定义里
放了桥接的**第二份副本**，两边会走叉。更好的做法是让动态插件当**加载器**：

```js
ctx.effect(function mount() {
  let dispose = null, stopped = false
  Promise.resolve().then(async function load() {
    const fsSvc = ctx.get('fs')
    const target = await fsSvc.resolve(BRIDGE_PATH, {})
    const raw = await fsSvc.readText(target, undefined)
    // 去掉 ESM 的 export，否则 Function 编译报 "Unexpected token 'export'"
    const body = raw.replace(/^export\s+function\s+createBridge/m, 'function createBridge')
    const createBridge = new Function(body + '\nreturn createBridge')()
    dispose = createBridge(ctx, { token: TOKEN })
  }).catch(e => console.error('load failed: ' + e.message))
  return function disposeAll() { stopped = true; if (dispose) dispose() }
})
```

十几行，运行时从磁盘读 `bridge-core.js` 现场编译 —— 桥接逻辑仍然只有一份。

**前提是探测过的，不是想当然**：动态 Cordis 宿主虽然只暴露
`ctx / console / btoa / atob / TextEncoder / TextDecoder`，
但 `new Function` 是 JS 语言本身的能力、并没有被挡；
`fs` 服务也在，能读到宿主机文件。所以先花几十行写个探针插件确认
（实测 `new Function('return 1+1')()` 返回 2、`fs.readText` 读到 43544 字节），
再写加载器。

这条路径的价值：**不用重启正在用的 harness** 就能把桥接挂上真实进程。
重启 `dsh web` 会结束当前对话，所以当用户不想中断工作时，
动态加载器是唯一能立刻用上真实数据的办法。代价是重启后消失 ——
持久生效仍然要走 §4.1 的 bundle 装载。

## 5. Android 端

- Kotlin + Jetpack Compose（Material 3），`minSdk 26 / targetSdk 37 / compileSdk 37`
- 工具链：JDK 21 + Gradle 9.8.1 + AGP 9.4.1 + build-tools 37.0.0
- 唯一的网络依赖是 OkHttp；JSON 用系统自带 `org.json`
- 四个界面：**状态** / **会话列表** / **聊天** / **设置**
- 实时性来自两条 SSE：
  - `/phone/events` → 整机状态（事件驱动推送，另有 3–5s 轮询兜底，
    防止澎湃 OS 的省电策略静默掐断长连接）
  - `/phone/sessions/<id>/live` → 会话内消息与模型输出增量
- 模型输出增量按 chunk 类型累加：`text-delta` 进正文、
  `reasoning-delta` 进思考区；收到定稿 `messages` 帧后清掉草稿并按 `seq` 去重
- 前台服务 `StatusService` 复用同一条状态 SSE，把状态写进常驻通知
  （可选，默认关闭）
- 支持用 intent 直达某个会话，便于脚本/快捷方式/通知跳转：
  `adb shell am start -n com.dsh.phone/.MainActivity --es sessionId <id>`

## 6. "不弄坏手机"是怎么保证的

| 动作 | 是否触及系统 |
| --- | --- |
| `adb install` 一个普通 APK | 等价于手动点安装包，走系统正常安装流程 |
| `adb reverse` | 只在 adb 连接上建端口转发，拔线即消失 |
| `adb shell am start` | 只是启动应用 |
| 请求通知权限 | 系统标准运行时权限弹窗 |
| **没有**：root / 解锁 BL / 刷机 / 改系统分区 / 装 Magisk / 改 build.prop | — |

卸载：`adb uninstall com.dsh.phone`，手机侧设置里"卸载"同样有效。
电脑侧改动只有 `~/.dsh/profiles/web` 里加了一个 bundle（`dsh plugin remove` 可撤销）。

## 7. 已知限制与后续可做

- **`adb reverse` 不稳定**。拔插数据线必然失效；实测在系统重新协商 USB 时也可能被清掉
  （adb transport 重新握手，`adb reverse --list` 变空）。重跑
  `scripts/install-to-phone.sh` 即可恢复。
  长期方案是把 USB 换成局域网直连（App 设置里改地址即可，桥接不用动），
  但那时应把 `/phone` 的 `token` 配上，并把 `dsh web --host 0.0.0.0` 的暴露面想清楚。
  考虑过用 `adb shell input` 做自动化验证，被澎湃的 `INJECT_EVENTS` 限制挡住，
  因此 App 改用截图 + intent 直达会话（`--es sessionId`）来做无人值守验证。
- **掉线时的降级**：聊天页单独维护一个 `chatError`（而不是只靠整机连接状态），
  因为"聊天页空白"和"真的没有消息"看起来完全一样，而掉线是常态。
  掉线时显示横幅并提供「重试」；通道恢复后 SSE 快照会补齐历史，无需重启 App。
- **App 目前不能发图片/附件**。桥接的 prompt 只收 `{type:'text'}`；
  要支持图片得走 `attachments` / `fileUploads`，是明确可加的下一步。
- **不展示 diff / 文件预览 / 工具卡片**。`tool/result` 目前只显示截断文本。
- **WebView 兜底**未实现。若想要"完整 UI 且零维护"，
  加一个 `WebView` 指向 `http://127.0.0.1:3080/?token=...` 即可，成本很低。
- 动态插件路径（§4.2）需要把内联后的代码贴进 `cordis_define`，
  体积约 30KB，属于调试工具而非交付物。

## 8. 复现步骤


## 9. 踩坑清单（都是实测出来的，不是推测）

### 9.1 组合 / 插件侧

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| `patch: entry "xxx" not found` | 补丁层默认是按 id **覆盖已有行**，不是新增 | 新增行必须写在 `- insert:` 下 |
| 动态宿主里 WebSocket 做不了 | 动态 ctx 只给 `ctx/console/btoa/atob/TextEncoder/TextDecoder`，**没有 crypto**，算不了握手用的 SHA-1 | 改用 SSE |
| `sc.follow(...)` 当 Promise 用会失败 | 它是 `async *` 生成器，调用即返回异步迭代器 | 直接 `iter[Symbol.asyncIterator]()` |
| `sc.cancel(...)` 没有 `.then` | 它是**同步**方法，返回 `SessionCancelValue` | 包一层 `Promise.resolve()` |
| 冷会话没有标题，列表全长一样 | 只从 `sessionTitle.get(session)` 取，而冷会话没有 Agent | 改用 `list()` 自带的 `projections.values.title` 投影（持久化，冷热通吃） |
| `AbortSignal` 缺失 | 动态宿主没有 `AbortController` | 给鸭子类型替身（`aborted` + `addEventListener` + `abort()`） |

### 9.2 Android 构建侧

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| `Dependency ... requires AGP 9.1.0 or higher` | 2026 年的 AndroidX（Compose 1.12 / lifecycle 2.11）已经要求 AGP 9 + compileSdk 37 | 升到 AGP 9.4.1 + Gradle 9.8.1 + compileSdk 37，**不要**降库 |
| `The 'org.jetbrains.kotlin.android' plugin is no longer required` | **AGP 9 内置 Kotlin 支持**，再应用 kotlin-android 会直接报错 | 从顶层和模块 build 文件里都删掉它；Compose 编译器插件保留 |
| `Unresolved reference 'icons'` | Compose 1.12 起 `material3` 不再传递引入图标核心包 | 显式 `implementation("androidx.compose.material:material-icons-core")`（BOM 钉版本） |
| `Type annotations are not allowed on destructuring declarations` | Kotlin 语法：解构声明不能带类型标注 | 拆成逐个 `val` |
| `Alignment.Start` 传给 `Box(contentAlignment=)` 编译不过 | `Alignment.Start` 是 `Alignment.Horizontal`，不是 `Alignment` | 用 `Alignment.TopStart` / `Alignment.TopEnd` |
| `gradle ... \| tail` 返回 0 却其实失败了 | shell 管道取的是 `tail` 的退出码 | 重定向到日志再读，或 `set -o pipefail` |

### 9.3 澎湃 OS 侧（都是系统限制，不是代码问题）

| 现象 | 系统设置 |
| --- | --- |
| `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user` | 开发者选项 → **「USB 安装」/「通过 USB 安装」** 打开（可能要求登录小米账号）。不开的话用文件管理器手动点安装包也可以 |
| `adb shell input tap` 报 `SecurityException: ... INJECT_EVENTS` | 开发者选项 → **「USB 调试（安全设置）」** 打开。不开的话无法用脚本模拟点击，只能手动操作手机 |
| 拔插数据线后 App 连不上 | `adb reverse` 是 adb 连接级的，拔线即失效；重跑 `scripts/install-to-phone.sh` |

## 10. 外网访问：为什么是 Tailscale，以及它在这台机器上的三个坑

需求从"插着线用"变成"人在外面、电脑在家"之后，USB 那条路就不够了。
公网可达有三条路：Tailscale / Cloudflare Tunnel / IPv6 直连。
选了 Tailscale，理由是它 CGNAT 可达、端到端加密、地址固定、且**不把 harness 暴露到公网**
（README 里写了对比）。落地过程中遇到三个必须记下来的坑。

### 10.1 坑一：控制面域名被 DNS 污染

```
$ getent hosts controlplane.tailscale.com
2001:2::fc      controlplane.tailscale.com     <- 封锁用的黑洞地址
$ curl https://controlplane.tailscale.com/key?v=148
000 (20s 超时)
$ curl -x http://127.0.0.1:7897 https://controlplane.tailscale.com/key?v=148
200                                            <- 走本机代理就通
```

真实地址在 `192.200.0.0/24`（通过 DoH 查得 192.200.0.101~116），
直连这些 IP 是可以的，所以**问题只在 DNS**。

`tailscaled` **不认 `HTTPS_PROXY` 环境变量**（试过，仍报
`fetch control key: context deadline exceeded`）。
最终解法是给它挂上本机 HTTP 出口：

```ini
# ~/.config/systemd/user/tailscaled-userspace.service
Environment=HTTPS_PROXY=http://127.0.0.1:7897
```

挂上之后日志出现 `Switching ipn state Starting -> Running`，netmap 才拿得到。

### 10.2 坑二：免 root 只能用 userspace 模式，于是只能用 serve

这台机器 `sudo` 要密码，所以走 **userspace-networking**：`tailscaled`
不建 TUN、不改内核路由、不碰 `/etc/resolv.conf`。
代价是「tailnet IP 不是本地网卡地址，没法直接 bind」，
入站只能靠 `tailscale serve` 在进程内代理。

`serve` 的 HTTPS 模式失败了：

```
error enabling https feature: ... Post "https://unused/machine/feature/query":
all connection attempts failed
```

（控制面 feature 查询走不通，跟 10.1 同源。）
所以改用 **纯 TCP 转发**：

```bash
tailscale serve --bg --tcp=3080 127.0.0.1:3080
# |-- tcp://dsh-home.<tailnet>.ts.net:3080 (tailnet only)
```

TCP 层没有 TLS，但整条链路已经是 WireGuard 端到端加密，
所以 App 侧对 tailnet 地址放行明文是安全的（见 `network_security_config.xml`
的注释）。**不要**因为"没 TLS"就以为内容会裸奔。

### 10.3 坑三：对称 NAT，但 IPv6 救了一命

`tailscale netcheck` 的关键几行：

```
* UDP: true
* IPv4: yes, 101.82.168.86:23023          <- 联通上海的真实出口
* IPv6: yes, [240e:46c:...]:50340
* MappingVariesByDestIP: true             <- 对称 NAT，UDP 打洞基本无望
* Nearest DERP: Los Angeles 303ms         <- 中继都在境外
```

对称 NAT 意味着 IPv4 打洞失败，只能走 DERP 中继，而最近的也在洛杉矶 300ms+。
但**两边都有全局 IPv6**，于是实际跑起来是这样：

```
$ tailscale ping <phone>
pong from <phone> (<tailnet-ipv4>) via [<tailnet-ipv6>]:40895 in 58ms
```

手机用自己的蜂窝 IPv6、电脑用家宽 IPv6，**打洞成功走直连，58ms**。
这是本次最幸运的一点：中国的联通/电信蜂窝与家宽普遍有全局 IPv6，
只要两边都有，Tailscale 就能绕开对称 NAT 和境外中继。

### 10.4 顺带做的加固与 App 改动

| 改动 | 原因 |
| --- | --- |
| `/phone/*` 强制令牌 | 一旦离开回环，令牌是唯一门禁。实测无令牌/错令牌 401，正确令牌 200（含走 tailnet） |
| App 端点改成**有序列表** | "在家 USB、在外 tailnet"要自动切换，不能靠人手改地址 |
| `BridgeClient.probe()` 用 2.5s 短超时 | 默认 8s 连接超时下，在家试第一个端点会白等，出门试 USB 端点更会卡住 |
| 每次操作/每次 SSE 重连都重新解析端点 | 从家里出门（USB 断、tailnet 通）能自动切过去，反之亦然 |
| intent 预置 `endpoints` / `token` | 澎湃的 `INJECT_EVENTS` 限制让脚本没法模拟点击，只能靠 intent 灌配置 |

### 10.5 手机侧还有一个必须交代的前提

Android 的 `VpnService` 是**按 UID 路由**的，`adb shell` 的流量不走 VPN。
所以"从手机 shell 里 curl 一下 tailnet 地址"验证不了任何东西 ——
必须让 App 自己去连。这一点浪费过一次排查。

另外，手机上必须把 Tailscale 设为「始终开启的 VPN」并关掉电池优化，
否则澎湃 OS 会在后台杀掉它，表现为 App 突然连不上（`tailscale status` 里
手机变成 `offline, last seen Nm ago`）。

## 11. 工作区（项目文件夹）：harness 已有的那一层，别再造一套

需求里「新建文件夹 + 创建 harness 工作区 + 看历史工作区」正好对上 harness
自带的 `workspaceRegistry` / `workspaceController`，所以桥接只是把它翻出来，
没有自己造目录模型。

### 11.1 数据从哪来

`workspaceRegistry.list()` 同步返回durable 顺序的工作区，
每个带 `path` / `title` / `sessionIds[]` / `createdAt` / `updatedAt`。
`sessionIds` 是 harness 按 canonical-cwd 索引过滤好的 —— **直接用，不要自己按
cwd 匹配**，否则两边规则一旦不同就会不一致。

### 11.2 三个实测出来的坑

**坑一：`create({cwd})` 建的会话不会挂进工作区。**

| 建会话方式 | 挂进工作区 |
| --- | --- |
| `{ workspaceId }` | 会 |
| `{ cwd }` | 不会 |

只带 `cwd` 的会话能正常跑，但在工作区列表里看不见 —— 界面上像是"丢了"。
解法：给 `cwd` 时先 `workspaceRegistry.resolveByPath(cwd)` 反查再带上 id。

**坑二：`workspaceRegistry.create(path)` 只收已存在的目录。**
它内部走 `fs.realpath`，路径不存在直接 reject。所以"新建文件夹"必须
先 mkdir，再登记工作区，再开会话 —— 三步，顺序不能换。

**坑三：mkdir 会被沙箱静默丢弃。**
组合里 `sandbox-policy` 的默认值是：

```yaml
- id: sandbox-policy
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
    workspaceRoot: !!js process.cwd()
```

工作区目录通常在 `process.cwd()` 之外，于是 `shell.run` 里的 `mkdir`
**退出码 0 但文件没建出来**（沙箱是 partial enforcement，写入被吞掉）。
桥接做了两件事：显式传 `sandboxPolicy: { mode: 'danger-full-access', ... }`，
以及建完用 `fs.stat` 复核 —— 不信退出码。

### 11.3 目录浏览为什么不走 directoryPickerController

它看着最合适（`list` / `createDirectory` 就是为这个设计的），
但这台机器的组合装的是 `dsh-host-directory-picker-auto`，
在桌面 Linux 上选了 **native** 后端，于是：

```
directoryPicker.list needs the browse capability; the composed picker serves "native"
```

harness 的设计是"组合不能提供的动词就明确拒绝，而不是糊弄过去"。
所以桥接改用自己的两条路：

- **浏览**：`fs.resolve(path)` + `fs.listDir(target)`（`fs` 服务两种宿主都有）
- **新建**：优先 `directoryPicker.createDirectory`，不可用则退回 `shell` 执行 `mkdir`

走 shell 就必须自己把关，因为命令是字符串而不是 argv 数组：

```js
// 只接受绝对路径、拒绝 .. 段；名字只接受单个路径段
// 然后 POSIX 单引号转义，再拼进命令
'mkdir -p -- ' + shellQuote(target)
```

实测 `"x; touch /tmp/PWNED"` 这种名字在名字校验阶段就被拒了，
`/tmp/PWNED` 没有被创建。

## 12. 用户提问（ask_user_question）在手机上的接入

### 12.1 坑：瀑布是按 agent 作用域派发的，根监听器收不到

最直觉的写法是监听那个瀑布事件：

```js
ctx.on('user-questions/request', function (request, next) { ... })
```

**实测收不到** —— 诊断计数一直是 0。原因是 `ask()` 的派发：

```js
this.ctx.waterfall(scopeTarget(agent, agent), 'user-questions/request', {...}, noAnswerer)
```

带 agent 时它派发到 **agent 自己的作用域**上，注册在根上下文上的监听器不在那个
作用域里。（浏览器 UI 的回答者是通过 `typertGateway.registerRemoteEvents`
按 agent 注册的，所以它能收到。）

### 12.2 解法：把 `userQuestions.ask` 包一层

绕开作用域问题，语义还更直白：

```js
const uq = ctx.get('userQuestions')
const original = uq.ask
uq.ask = function (request) {
  return askPhoneFirst(request, function () { return original.call(uq, request) })
}
```

- 手机正开着那个会话 → 推给手机，等回答
- 没开 / 超时 / 中止 → `original.call(...)`，浏览器 UI 照常接管

**只在手机真的开着该会话时才拦截**，所以你人在电脑前时不会有额外延迟。
"开着"的判断来自 App 打开聊天页时建立的那条 `/live` 流 —— 不需要额外的心跳接口。

清理时把 `ask` 还原（`disposers` 里存了 restore 函数），插件卸载后不留痕。

### 12.2bis 判断"手机在看"必须用心跳，不能用连接是否开着

第一版用"`/live` 连接还在吗"来判断，**有个 180 秒的坑**：

手机静默掉线（App 被杀、蜂窝断、没发 FIN）时，那条 TCP 连接可能挂很久才被系统
回收。这期间桥接以为手机还在看，把提问推给一条死连接，**电脑要干等满超时**。

改成**心跳新鲜度**（`WATCH_TTL_MS = 15000`）：

- 心跳搭在 App 本来就有的 `/phone/state` 轮询上 —— `?watching=<sessionId>`，
  不额外加请求
- 心跳一停，最多一个 TTL 之后就不再算"在看"
- 待回答问题还会在心跳失效后 **3 秒**就交还电脑，不等满超时

**实测**（直接 `am force-stop` 模拟静默断开）：

```
+4s  watched=[...]   +8s  watched=[...]   +12s watched=[...]   +16s watched=[]
```

**还有一个同源的坑**：App 退到后台时轮询仍在跑，心跳会继续，
提问就被推给一个用户看不见的屏幕。所以心跳要求**同时满足**「App 在前台」
和「开着那个会话」。前台判断用 `Activity.onResume/onPause` 打标志位
（避开 Compose 生命周期 API 的版本差异）。

三层保证合起来：

| 情况 | 结果 |
| --- | --- |
| 手机在看 | 提问只弹手机，电脑不弹 |
| 手机没开聊天页 / 在后台 | 提问立刻走电脑（同步 fallback） |
| 手机静默断开 | 最多 16 秒后走电脑 |

### 12.3 顺带修正的呈现问题

原来的 `deriveMessages` 把 reasoning 用 `"[思考] "` 前缀**塞进正文**，
既难读也和电脑上的呈现不一致。现在：

| 字段 | 含义 |
| --- | --- |
| `text` | 正文（只含 text / image / file / tool-result 块） |
| `reasoning` | 思考过程，独立字段 —— 手机上渲染成可折叠的独立区块 |
| `title` | 工具调用的一行摘要（`command` / `file_path` / `query` …） |

工具卡片因此能一眼看出"干了什么"，完整参数收在"参数"折叠里，
和电脑上的卡片是一个意思。

### 12.4 `/phone/diag`

排查"手机上没收到提问"这类问题用的自检接口，直接暴露内部状态：

```json
{ "watchedSessions": [...], "sessionStreams": [...], "pendingQuestions": [...],
  "questionEventCount": 1,
  "lastQuestion": { "sid": "...", "watched": true, "intercepted": true, ... } }
```

`questionEventCount` 为 0 就是"监听器压根没被调用"（12.1 那个坑），
`watched` 为 false 就是"手机没开着这个会话"。

## 13. 反向：让电脑能通过网络调试手机

前面所有通道都是**手机连电脑**。要反过来（电脑 `adb` 连手机），
有两个各自独立的障碍：

1. **内核没有到 tailnet 的路由。** tailscaled 跑在 userspace 模式（为了免 root、
   不建 TUN），所以只有它进程内部的 `serve` 能接收入站 —— 本机 socket 到不了
   `100.x.x.x`。
2. **adb 不支持 SOCKS。** 而 userspace 模式下唯一能主动出站到 tailnet 的路径
   就是 tailscaled 的 SOCKS5 出口。

解法是两者之间加一层用户态 TCP 桥（`scripts/tailnet-tcp-bridge.py`，
纯标准库）：本地端口 → SOCKS5 → tailnet 目标。然后
`adb connect 127.0.0.1:<本地端口>` 即可。

再配合手机上 `adb tcpip 5555`（只需在 USB 上执行一次），
之后拔线也能调试。全流程在 `scripts/adb-over-tailnet.sh` 里。

**安全提醒**：`adb tcpip` 会让 adbd 监听**所有网卡**，不只是 Tailscale。
手机连公共 WiFi 时，同网的人可能连上 adb（等于 shell）。
不用时执行 `scripts/adb-over-tailnet.sh off` 切回 USB 模式。

## 14. 未读回复提醒

### 14.1 harness 没有「已读」概念，别去找

翻遍了 `*.d.ts`：所有 `unread` 命中都是"文件不可读"，没有任何服务端已读状态。
**这是对的** —— 已读天然是每个观察者自己的状态，不该写进共享的会话存储。

所以分层：

| 谁 | 负责什么 |
| --- | --- |
| 桥接（电脑） | 提供**判断依据**：每个会话最后一次助手回复 / 最后一次人提问的 seq 和时间 |
| App（手机） | 保存已读 watermark（SharedPreferences），算未读、出角标 |

会话存储仍然只在电脑上；已读是手机侧的小状态，换手机重装就重新计未读。

### 14.2 判断依据怎么来

两路合并：

1. **实时**：`session/event` 火线。
   注意它和 §12.1 那个瀑布不一样 —— 瀑布按 agent 作用域派发、根监听器收不到，
   而这个火线**能**到根监听器（实测计数在涨，带 `session-…` 和 `tool/call`/seq）。

2. **回填**：挂载时对最近 7 天活跃、且尚未被实时跟踪到的会话（最多 60 个）
   串行读一次日志尾部（`follow({maxMessages: 8})`，拿完即关）。
   没有这步，"挂载之前就已经存在的未读回复"就看不出来。

只认 `user/message` 里 `source.kind === 'user'` 的 —— harness 注入的运行时提醒、
技能目录那些不算"人提问"，否则每个会话都会被判成"助手在最后说话"。

### 14.3 未读的定义

```
未读 = 助手最后说话(agentSpokeLast)   // lastReplySeq > lastUserSeq
     && lastReplySeq > 手机已读 watermark
     && lastReplyAt 在 7 天窗口内
```

「助手最后说话」比单纯"有新事件"准得多：如果最后一条是人提问、助手还没答，
那不该提醒你（是你在等它）。

**标记已读**的判定集中在 `refreshUnread()` 里：
「App 在前台 && 正开着这个会话」就写入 watermark。放在一处，
就不会出现"某个入口忘了标已读、角标永远消不掉"。

### 14.3bis 但光有"集中"不够 —— 时机错了照样漏标

第一版只在 `refreshUnread()` 里标，而它要等状态（5s）或工作区（20s）刷新后
才知道那个会话的 `lastReplySeq`。**用户点进去看一眼、几秒内就退出 ——
还没等到那次刷新，watermark 从来没写进去**，表现就是"点过了还是未读"。

实测：点进去等 **30 秒**才写进 prefs。这不是偶发，是必然。

修法是两件事：

1. **维护一张"已知 activity"表**（只增不减），`refreshUnread()` 每次
   从状态和工作区往里灌。查找时优先读它。
2. **在打开和关闭的瞬间各标一次**（`openSession` / `closeSession`），
   不再依赖轮询。

这样从"必须停留到一个轮询周期"变成"点下去就标"。
实测：热状态下点进一个未读会话，**3 秒**后 prefs 里已有
`seen_session-…=2520`。

教训是通用的：**"什么时候"和"在哪算"一样重要。** 只把逻辑收敛到一处，
但如果那一处只在低频路径上被触发，对用户来说就等于没生效。

### 14.4 一个自找的对不上

第一版角标显示 21、区块只列 20 —— 因为角标把 `/phone/state` 里那 60 条最近会话
也算进去了，而区块遍历的是全部工作区。**两边必须同源**：
统一只以工作区为来源（它还更全）。这种"两处各算一遍"的分歧是 UI 里最容易漏的。

### 14.5 通知栏

`StatusService`（可选，默认关）每分钟拉一次工作区算未读，
写进常驻通知的正文和展开区。它和 App 内**共用同一份已读 watermark**，
所以在 App 里点开过的，通知栏也不会再算未读。

## 15. Markdown 渲染与可点链接

### 15.1 为什么自己写

手机上原来把 `**粗体**` 原样显示 —— harness 的正文是 markdown，得渲染。
没有引第三方库：Compose 1.12 / AGP 9 这一代里现成的 markdown 库大多还没跟上，
版本一冲突就是整包编不过；而需要的规则本身并不复杂。

`ui/Markdown.kt`，纯 Compose 原生，约 300 行。

### 15.2 链接靠 LinkAnnotation，不自己发 Intent

```kotlin
withLink(LinkAnnotation.Url(url, TextLinkStyles(SpanStyle(
    color = linkColor, textDecoration = TextDecoration.Underline,
)))) { append(label) }
```

**不给 `linkInteractionListener` 时，点击会落到平台的 `UriHandler`**，
也就是系统默认浏览器 —— 正是要的效果，而且不用自己拿 Context 发 Intent。

只认 `http://` / `https://`：`intent://`、`javascript:` 这类 scheme 不进链接，
免得一个消息就能触发任意组件调用。

行内解析是**手写扫描而不是正则**：标记会互相嵌套（`***粗斜体***`、链接文字里带
`` ` ``），一个正则塞多组很快就不敢改了。

### 15.3 实测踩到的两个

**坑一：`***粗斜体***` 会渲染成字面的 `*粗斜体*`。**
因为 `**` 分支先命中，吃掉了前两个星号，剩下 `*x*` 当一个星号处理。
三星号的分支必须排在两星号**之前**。

**坑二：测试方法本身会骗人。**
用 `adb shell am start --es send '...'` 发测试样本时，
样本里的**反引号被设备 shell 当命令替换执行了**，消息被吃掉大半，
看起来像"渲染坏了"。第一版截图里我只写了 `` `**粗体**` ``（把 markdown 样本
包在反引号里），结果原样显示其实是**正确**的 —— 白白怀疑了一轮。

教训：**用会被两层 shell（本机 bash + 设备 sh）解析的通道传测试样本，
先确认样本原样到达**，否则你验证的是通道不是功能。

### 15.4 覆盖范围

| 语法 | 支持 |
| --- | --- |
| `**粗体**` / `__粗体__` | ✅ |
| `*斜体*` / `_斜体_` | ✅ |
| `***粗斜体***` | ✅ |
| `` `行内代码` `` | ✅ 等宽 |
| `~~删除线~~` | ✅ |
| `[文字](url)` / 裸链接 | ✅ 可点，走系统浏览器 |
| `#` ~ `######` 标题 | ✅ 逐级加大 |
| `-` / `*` / `1.` 列表 | ✅ 保留有序编号 |
| `>` 引用 | ✅ 左侧竖条 + 斜体 |
| ``` 代码块 ``` | ✅ 带底色 + 等宽 |
| `---` 分隔线 | ✅ |
| 表格 | ✅ 见 §15.5 |
| 图片、脚注 | ❌ 未做（会原样显示） |

### 15.5 表格

Compose 没有内置表格控件，用 `Row` + 每格 `Modifier.weight(1f)` 拼了一个：

```
│ 语言    │   用途   │   年份 │   ← 表头（加粗 + 底色）
├─────────┼──────────┼────────┤
│ Kotlin  │ 安卓开发 │   2011 │
```

- **列宽按内容量**，不搞等分：用 `TextMeasurer` 把每个单元格量一遍，
  取该列最大值（夹在 48dp ~ 220dp 之间）。等分列宽会把长内容挤成一行几个字；
  而让各行各自"按内容撑开"又会导致列对不齐 —— 必须统一量一次。
- **比屏幕宽时横向滚动**：外面套一层 `Modifier.horizontalScroll(...)`。
  实测 6 列的长表格，视图里最后一列在右边缘被切掉、后两列完全在屏外，
  说明溢出成立、可以左右滑。
- **列对齐**从分隔行读：`:---` 左 / `:---:` 中 / `---:` 右
- **单元格内的行内标记照常解析**（粗体、代码、链接都能用）
- 支持转义竖线，不会被当成分隔符
- 短的一行自动补空凑齐列数，不会串列

**判定表格的关键是「下一行是分隔行」**：只看到竖线就当成表格的话，
一句普通的话里带个竖线就会被误判。

另外记一笔：写这个解析器时，我在 Kotlin 里用原始字符串（三个双引号）
写正则 `:?-+:?`，而它正好落在一段 Python 三引号脚本里 ——
**两者引号形式相同，直接把脚本本身搞崩了**，白跑两次。
跨语言写脚本时，字符串定界符要错开。

流式输出也过同一套渲染。未闭合的标记在流中途会短暂显示成字面量，
但定稿后就被解析掉 —— 比全程显示 `**` 要好。

## 16. 停止生成 与 模型切换

### 16.1 停止：接口本来是好的，坏的是"按钮不出现"

`sessionController.cancel({sessionId})` 一直是对的，但**按钮只在 `running` 为真时显示**，
而那个 `running` 来自 5 秒一次的状态轮询 —— 于是经常该出现时不出现，
用户的感觉就是"没有停止按钮"。

修法是把运行态改成**三源取或**：

```kotlin
running = session?.running == true || liveRunning || streamText.isNotEmpty()
```

`liveRunning` 来自会话实时流里新转播的 `turn` 帧（`turn/start` → true，
`turn/end` → false），`attempt` 帧也置 true。这样开始思考的瞬间按钮就出来。

UI 上也从顶栏那个小 `✕` 挪到**输入框旁边**，变成显眼的红色「✕ 停止」。

**接口本身补做了验证**（之前从没验过）：

```
停止前 running = True
调 /phone/sessions/<id>/cancel → {"ok":true,"cancelled":true}
停止后 running = False
```

注意 `cancel` 对**未挂载的会话会抛 `session/not-found`** ——
它作用于活 Agent，不是冷会话。桥接把这情况如实当 500 报出去。

### 16.2 模型切换

harness 现成的两件东西正好够：

| 用途 | 接口 |
| --- | --- |
| 列目录 | `sessionController.modelCatalog()` |
| 切模型 | `sessionController.selectModel({sessionId, provider, model, reasoningEffort?})` |

>`modelCatalog()` 返回 `{default, routableProviders, groups[], failures[]}`，
>每个模型还能带 `reasoning.efforts[]` 和 `defaultEffort`。

**当前会话用的是哪个模型**，从 `sessionController.list()` 的投影里取：
`summary.projections.values.modelSelection` 有 `{lastUsed, next}`，
取 `next` 回退 `lastUsed`。所以只多花一次 list，不用逐个会话去问。

这台机器实测能路由 2 个 provider、8 个模型：

```
[deepseek-official] deepseek-v4-flash / v4-pro / v4-flash-vision-exp / flash   efforts: off low high max
[kimi-coding]       k3 / k3-256k / kimi-for-coding / -highspeed                 efforts: 各不同
```

UI：顶栏右侧显示当前模型短名，点开是底部面板 —— 按 provider 分组、
选中项打勾；**只有当前正用着的、且支持推理强度的模型才展开强度选项**，
免得一屏全是按钮。

## 17. 消息折叠 与 输入草稿缓存

### 17.1 工具结果也收起

原来只有「思考」和工具「参数」折叠，**工具结果全文铺开** —— 而 bash 结果动辄
几十行，会把整屏真正要读的东西挤走。

现在和思考一致：收起时给一行摘要 + 首行预览，点开才展开。

```
▸ 结果 · 16 行 · 716 字
=== 当前 prefs 里有 draft 键吗 ===
```

三类折叠（思考 / 参数 / 结果）用的是同一个模式：`▸`/`▾` 前缀 + `clickable` +
`remember(m.seq)` 的展开状态。**按 seq 做 key**，否则列表滚动复用时展开状态会串。

### 17.2 输入草稿缓存

需求是"误退出不丢编辑"，所以**不能用 `rememberSaveable`** ——
它只扛配置变更和进程被回收，**完全退出 App 就没了**。要落盘。

- 存在手机侧 SharedPreferences，**按会话分开**（`draft_<sessionId>`）
- 输入时**防抖 400ms** 落盘，不是每敲一个字写一次
- **离开聊天页时立即落盘**（`closeSession` 里 `flushDraft`），不走防抖 ——
  这一下就是要防丢的那一下
- 发出去之后清空

为什么放 ViewModel 而不是 ChatScreen 的 `remember`：离开聊天页再回来、
退出 App 重进，草稿都还在。

**验证**：直接往 prefs 里写一条 `draft_<sid>`，启动 App 打开该会话 ——
输入框自动填回那行字（不依赖"模拟打字"，那条路被 INJECT_EVENTS 封着）。

顺带一个真实事故：写这篇的时候我第一次注入失败，因为
**heredoc 没加引号，`$key` 被 bash 展开成空**，写进去的键名是空的。
同一个坑在这台机器上已经踩过好几次（跨语言/跨 shell 的引号与变量展开），
统一规矩：**凡是往脚本里嵌变量，heredoc 一律用引号定界符**。

## 18. 选中复制：一个被"想多了"去掉的功能

用户报"正文选不中、没法复制"。原因很直接：

> 当初把 markdown 接进来时，我**主动去掉了正文外面的 `SelectionContainer`**，
> 理由是"怕长按选择和点链接抢手势"。

**那是想多了。** Compose 里：

- **点按**由 `LinkAnnotation` 处理（开链接）
- **长按 / 拖动**由 `SelectionContainer` 处理（起选区）

两者作用在不同手势上，不冲突。去掉它换来的只是"正文整个没法复制"。

修法就是加回来，正文、思考、参数、工具结果四处现在都有 `SelectionContainer`，
长按即可选中并用系统工具条「复制」。

这条的教训和 §12.2bis、§14.3bis 是同一类：
**没有实测支撑的取舍，很可能是在砍功能而不是在防冲突。**
当时的注释写得很笃定（"免得互相抢手势"），但没有任何一次实际点击验证过。

### 18.1 顺带：一次真实的异地验证

改这个的时候手机被带出门了（WiFi 换到 `192.168.5.x`，USB 已拔）。
`adb -s 127.0.0.1:15555` 依然 `device` —— 装包、截图、取日志全部照常。
中间出现过一次 `device offline`，是**切网那一瞬间**，重连即恢复。

这正是 §10 那套远程通路要证明的事，只是这次不是构造出来的测试，
而是真的"人在外面、电脑在家里"。

## 19. 工作区展开状态要活过导航（和退出）

需求：从会话返回后，之前展开的工作区要**保持展开**，直到用户自己点收起 ——
这样一眼能看出最近看过哪些工作区。

### 19.1 根因是状态放错了地方

```kotlin
// 会话页里
var expanded by remember { mutableStateOf(setOf<String>()) }
```

`remember` 的生命周期跟着**这个 composable 在组合树里的存在**。
一进聊天页，会话页整个从组合里移除，`remember` 就被丢弃 —— 返回时全收起。

修法两步：

1. **提到 ViewModel**（`_expandedWorkspaces: StateFlow<Set<String>>`）。
   仅这一步就解决了"返回后全收起"。
2. **落盘** SharedPreferences。这样连退出 App 重进都还在，
   才是真正的"我最近看过什么"。

### 19.2 顺便：打开会话时自动展开它所属的工作区

`openSession` 里查一下这个会话在哪个工作区，把它展开（**只展开不收起**，
免得把用户手动收起的又弹开）。返回列表时，刚读的那个工作区就是开着的。

### 19.3 验证

- **写入**：prefs 里出现了 `expandedWorkspaces = a0253bce…`（某个工作区），
  是 App 自己写的，不是我注入的
- **渲染**：列表里该工作区显示为 ▾ 并列出会话

「读取」那一侧没拿到干净的独立证据（验证时用户正在用手机，
我重启 App 会打断他，就没反复试）—— 但它和 §17.2 的草稿走的是同一套
`SharedPreferences` 读写，而草稿是端到端验过的（注入 prefs → 输入框自动填回）。

顺带观察到：改这个的时候用户的模型已经切成 `k3` 了 ——
上一轮做的模型切换已经有人在用。

## 20. 在手机上点开文档

需求：会话产出一个 `.md` 文档后，手机上点一下（像超链接那样）就能看渲染好的内容。

### 20.1 桥接：读文件

新增 `GET /phone/file?path=<p>&sessionId=<id>`。两个关键决定：

1. **相对路径按"该会话的 cwd"解析。** 用户在正文里点的是
   `docs/技术路线.md` 这种相对写法，不可能要求他写全路径。
   桥接先用 `sessionController.list()` 查出该会话的 cwd 再拼。
2. **有大小上限**（默认 512KB，最多 2MB），超了截断并在响应里标记
   `truncated` —— 不能因为一个巨型文件把手机内存吃光。

读的是 harness 自己的 `fs` 服务（`resolve` + `stat` + `readText`），
不是另开一条文件访问路径。

### 20.2 让路径变成可点的

两处来源：

| 来源 | 怎么识别 |
| --- | --- |
| 工具调用的标题 | 桥接在 `toolSummary` 里判断摘要取自 `file_path`/`path` 时，额外给一个 `titlePath` 字段 |
| 正文里的行内代码 | `looksLikeDocPath()`：含 `/`、末段有扩展名、扩展名在文档白名单里 |

第二处是启发式，所以**限定得比较死**（必须像路径才认），
否则每个变量名都会变成链接。

### 20.3 为什么用私有 scheme 而不是自己发 Intent

链接点击在 Compose 里最终落到 `LocalUriHandler`。所以在 `MarkdownText` 外层
`CompositionLocalProvider(LocalUriHandler provides ...)` 包一层：

```kotlin
if (uri.startsWith("dshfile:")) onOpenFile(uri.removePrefix("dshfile:"))
else platformHandler.openUri(uri)      // http(s) 照旧交给系统浏览器
```

好处是**解析层保持纯函数**：`inline()` 只负责生成 `dshfile:<path>` 这样的 URL，
不需要知道任何回调。而且 http 链接的行为一点没变。

### 20.4 验证

加了一个 `--es file <path>` intent 参数（和 `tab`/`send`/`sessionId` 同一套路，
本身也能当深链用），于是可以无人值守验证：

```
adb shell am start -n com.dsh.phone/.MainActivity \
  --es sessionId <id> --es file "docs/技术路线.md"
```

结果：标题栏显示 `技术路线.md`、副标题显示**解析后的绝对路径**，
正文的 `#` 标题、`>` 引用、``` 代码块``` 全部正确渲染。

**"点击"这个动作本身没验证**（注入手势被 INJECT_EVENTS 封着），
但点击之后的所有环节都验过了。

### 20.5 又一个"replace 没加断言"的教训

`Models.kt` 里给 `ChatMessage` 加 `titlePath` 时，我用
`s.replace("title = ...", "title = ...\ntitlePath = ...")` **没带数量限制** ——
于是这个字段被同时塞进了 `parseState` 和 `parseWorkspaceSessions`，
而那两处构造的对象根本没有这个参数，直接编译不过。

规矩：**跨多处出现的文本做替换，要么带 `count=1`，要么先 `assert` 存在且唯一**
（grep 出来的行号也要看一眼是不是同一处）。

## 21. 长按管理：会话与工作区

需求：长按会话弹出和电脑上「···」同一批操作（归档 / 重命名 / 分支），
长按工作区弹出删除工作区等。**并且这些操作要真的同步到电脑。**

### 21.1 用 harness 自己的接口，不自己写存储

| 操作 | 接口 |
| --- | --- |
| 重命名会话 | `sessionController.rename({sessionId, title})` |
| 分支会话 | `sessionController.fork({sessionId, atSeq?})` |
| 归档会话 | `workspaceController.archiveSession({sessionId})` |
| 重命名工作区 | `workspaceController.rename({workspaceId, title})` |
| 删除工作区 | `workspaceController.delete({workspaceId})` |

因为走的是同一套服务，**电脑上的 UI 和手机看到的是同一份状态** ——
不需要任何"同步"逻辑，本来就是同一个后端。

### 21.2 「删除」的语义必须在 UI 里讲清楚

两个都容易被误解，所以对话框里直接写明：

- **会话没有删除**：日志是只追加的，harness 提供的是**归档**
  （从工作区分组里隐藏，日志完整保留）。而且**没有反归档接口** ——
  这一点让"归档"比"删除"更需要二次确认。
- **删除工作区删的是注册记录**：电脑上的目录和里面所有会话日志都不动。
  验证方式很直接：删除后对那个目录执行 `rmdir` 成功了，
  说明目录确实还在（`delete` 没碰它）。

对话框里因此分别写成「归档」和「删除注册」，而不是一个含糊的「删除」。

### 21.3 UI

长按用 `combinedClickable(onClick, onLongClick)`，菜单用 `DropdownMenu`
**挂在每一行自己的 Box 里**（DropdownMenu 相对父级定位，所以必须挨着那一行）。

回调收成一个 `DshActions` bundle 传进 `SessionsScreen` ——
否则参数列表会有十来个 lambda，没法读也没法改。

### 21.4 又踩了一次同一个坑

给 `Screens.kt` 加 import 时用了
`s.replace("import ...Card", "import ...AlertDialog\nimport ...Card")`，
结果 `Card` 是 `CardDefaults` 的前缀，**把 `CardDefaults` 也改了**，
变成 `OutlinedButtonDefaults` 这种不存在的类。

这是本项目里**第三次**因为"替换没加约束"出错（§20.5 是没加 count，
这里是前缀匹配）。规矩再收紧一条：
**改 import 之类的短标识符，替换串里带上换行或结尾锚点，别只给标识符本身。**

## 22. 别把正在翻旧记录的读者拽回底部

问题：助手正在流式输出时，用户往上翻想看上一轮说了什么 ——
结果每来一个 chunk，页面就被拉回底部，根本读不了。

原因就是那段自动滚动**无条件执行**，而且它的 key 里带着 `streamText.length`：

```kotlin
LaunchedEffect(visible.size, streamText.length) {
    listState.scrollToItem(target - 1)   // 每个 chunk 跳一次
}
```

改成「只在用户本来就贴着底部时才跟随」。难的是**怎么判断"贴着底部"**。

### 22.1 第一版判断错了，而且一截图就露馅

第一版看的是**滚动位移的方向**：索引/偏移变小 = 用户往上翻了。

写完一装上，截图里**刚打开会话就显示「↓ 回到最新」** —— 说明 `followTail`
被误判成 false 了。

原因：**布局自身的调整也会改这两个值**。消息从 SSE 合并进来、去重、重新排序，
都会让 `firstVisibleItemIndex` 变化，被当成了"用户往上翻"。

### 22.2 改对：只有"用户正在滚"时的位移才算意图

```kotlin
snapshotFlow {
    Triple(listState.isScrollInProgress,
           listState.firstVisibleItemIndex,
           listState.firstVisibleItemScrollOffset)
}.collect { (inProgress, idx, off) ->
    val movedUp = idx < prevIdx || (idx == prevIdx && off < prevOff)
    if (inProgress && movedUp) followTail = false      // 用户往上翻 → 停止跟随
    else if (!inProgress) {                            // 停下时：到底了就恢复
        if (lastVisibleIndex >= totalCount - 1) followTail = true
    }
    ...
}
```

关键在于**位移只有配合 `isScrollInProgress` 才解读为意图**；
不在滚动时的位置变化一律忽略（那八成是布局在动，不是人在动）。

另外还加了个「↓ 回到最新」按钮：上翻之后总得有个一键回去的入口，
不然用户只能一路手动滑。

### 22.3 为什么"在内容变化时判断是否到底"一定失败

顺带记下这个反直觉点：不能在 `LaunchedEffect(visible.size)` 里去问
"最后一屏可见吗"。那一刻 `totalItemsCount` 已经涨了、
`visibleItemsInfo` 还是旧的 —— 问出来的答案必然是"不在底部"，
于是跟随永远开不起来。**判断必须基于变化之前的意图，而不是变化之后的布局。**

## 23. 阅读位置要能"接着看"

需求：看到一半退出（去处理别的事），再点回来要停在原处继续看。

### 23.1 光把 LazyListState 提到 ViewModel 不够

滚动位置提到 ViewModel 只解决了"进程内导航"。还有两个坑：

**坑一：不能在 `closeSession` 里清空 messages。**
清空之后列表变空，`LazyListState` 的索引会被夹到 0 —— 位置就没了。
所以 `closeSession` 刻意**保留 messages**，只断开实时流。
再点回来时 `openSession` 认出是同一个会话，就直接接着用旧列表和旧位置。

**坑二：不能在列表还空着时恢复位置。**
所以换会话时先把存档读出来，**等历史加载完**才 `scrollToItem`。

### 23.2 第一次验证失败，原因很典型

注入一份存档（`scroll_<sid> = 8,0,0`，表示"看到第 8 条、没在跟随"）后打开会话 ——
结果它还是停在最新，也没出现「回到最新」按钮。存档确实写进去了，说明是代码没生效。

原因是 §22 那段 `snapshotFlow`：它在**非滚动状态**下也会评估"是否到底"，
而**启动那一刻列表还短，最后一个 item 必然可见** ——
于是把刚恢复出来的 `followTail = false` 又覆盖成了 `true`。

改成**只在"一次真正的滚动刚结束"时才评估**（`isScrollInProgress` 的下降沿），
外加"手指还在屏幕上且往上挪了就立刻停止跟随"。
这样启动时的布局状态不会污染用户意图。

这已经是这个滚动逻辑的**第三次**修正了，三次都栽在同一个点上：
**分不清"布局在动"和"人在动"。**

## 24. 三个板块的互斥分类：「最近会话」是怎么切出来的

需求：会话页顶上再加一块**「最近会话」**，方便在手机上快速找回刚点开过的会话。
但一加就撞上一个必须先回答的问题：**一个会话到底该出现在哪一栏？**

### 24.1 问题出在「未读」的定义上

原来的未读判据是（`ActivityInfo`，见 §13）：

```
agentSpokeLast && lastReplySeq > seen && 7 天内
```

`agentSpokeLast` 只看"最后说过话的是助手还是人"。问题是**一轮里助手会说很多次话**：
调工具前的说明、工具返回后的中间结论、最后才是收尾回复 —— 它们**都带 seq**，
都会被 `assistant/message` 事件记进 `lastReplySeq`。

于是一个正在跑、**还没有最终回复**的会话，会被算成"有未读回复"：

- 用户点进去，只看到半截输出（甚至还在转圈），**这就是骗人**；
- 它明明在「正在工作」栏里，却同时又出现在「未读回复」栏，**两栏打架**。

实测（改动前，电脑侧真实数据）：143 个会话里旧规则算出 3 条未读，
其中 **2 条其实正在跑** —— 包括用户当时正盯着看的那一个。

### 24.2 规则：三栏互斥，优先级从"动"到"静"

```
正在工作 = 电脑上 running（或手机正开着且实时流说在跑）
未读回复 = 没在跑 且 助手最后说话 且 手机没看过这条 且 7 天内
最近会话 = 没在跑 且 已读 且 手机上点开过（按点开时间新→旧）
```

一个会话**只出现在一栏**里。所以"退出一个还在跑的会话"之后它仍在「正在工作」，
跑完变成「未读回复」，你点开看过之后才落到「最近会话」。
这正是"已读且停止工作的才算最近"的字面含义。

### 24.3 两个实现细节

**一、「正在工作」的数据源要取新的，不能取并集。**
两份快照都来自电脑上同一次 `sessionController.list()`：
`/phone/state` 每 ~5 秒一次，工作区树 ~20 秒一次。
如果用并集（任一份说在跑就算在跑），一个 20 秒前就做完的会话会被旧快照
按在「正在工作」里出不来 —— 「未读」就永远不出现。
所以按"谁新用谁"：state 里有这个会话就用 state 的，不在 state 最近 60 条里才回退。
再叠上手机自己那条实时流的 `turn/start`（比 5 秒轮询还快）。

**二、「最近」是手机侧的记忆，电脑端一个字节都不改。**
存 `SharedPreferences`，格式 `会话id:时间戳\n...`，新的在前。
**记 12 条、显示 6 条**（`RECENT_MAX` / `RECENT_SHOWN`）：多留一倍是为了
"正在跑"或"有未读"的那几条被上面两栏借走时还能往下补位，
免得最近会话一眼看上去是空的；30 天没点开过的自动过期。
界面上按这个顺序映射到工作区树里的会话对象 ——
映射不到的（刚被归档/删掉）自然消失，不需要额外清理。
`openSession()` 里记一笔，所以未读卡片、工作区树、通知、`--es sessionId` 深链
全都算"点开过"。

> 注意"显示 6 条"不等于"永远有 6 张卡"：只有手机上点开过、且此刻不在
> 「正在工作」/「未读回复」里的才在这里，所以条数是浮动的。

### 24.4 顺带挖出来的一个真 bug：`onNewIntent` 在这台机器上根本没被调

验证时按老办法用 intent 打开会话：

```bash
adb shell am start -n com.dsh.phone/.MainActivity --es sessionId <id>
```

**没用**。事件日志里 `result code=3`（`START_DELIVERED_TO_TOP`，意思是"已投递给栈顶实例"），
但 App 的 `onNewIntent` 没有跑 —— `lastSessionId` 和最近列表都没变。
（澎湃的 `ActivityStarterImpl: boost warm start` 走了 `LAUNCH_MULTIPLE` 路径。）

对着"一条新 APK + 强制 stop 后冷启动"再试就正常，说明是**已在栈顶时的投递**这条路径坏了。
修法是给 Activity 加 `android:launchMode="singleTop"`：
单 Activity 应用本来就该这样，顺带也杜绝了重复实例。
加完之后同一条 `am start` 立刻生效（最近列表按新→旧写入三笔，见 §24.5）。
这也说明了那条纪律：**"参数传对了"不等于"代码跑了"**，必须回读落盘结果。

### 24.5 验证

- 电脑侧用真实数据重放分类规则：`未读 ∩ 正在工作 = ∅`，旧规则里 2 条"正在跑的假未读"被摘掉。
- 连发三次 `--es sessionId`，`recentSessions` 落盘为
  `14c08bcc:…\ne994c242:…\na8f31a46:…`（新→旧），顺序正确。
- 截图核对：`未读回复（1）` / `正在工作`（3 条）/ `最近会话`（3 条，带「清空」）/ `工作区`
  四段从上到下依次渲染，底部导航的未读角标与「未读回复（1）」一致。

## 25. 手机上的电脑终端：不用 SSH，用宿主已有的真 PTY

需求：在手机上也能操作这台电脑 —— 尤其在会话里复制一段命令后，
切到终端粘上就能跑。

### 25.1 为什么不用 SSH

SSH 是第一直觉，但它对**这个**项目是更差的选择：

| | SSH | 走桥接（实际选的路） |
| --- | --- | --- |
| 手机侧依赖 | 要往 APK 里塞一个 Java SSH 实现（密钥、known_hosts、密码/私钥输入全自己做） | 无（就是 OkHttp） |
| 通道 | 再开一条（`adb reverse 22` 或 `tailscale serve 22`） | 复用已有的 `/phone/*`（一个端口、一把令牌） |
| 延迟 | 差不多（都是本地/tailnet） | 在家 `adb reverse` ~5ms，在外 tailnet ~58ms |

省掉的不是"协议"，是**一整套客户端实现 + 第二套鉴权与端口**。

### 25.2 关键是宿主本来就有真 PTY

先查 Inspect 的 `Service.listService`，发现两个候选：

- `shell.start(spec)` —— 管道式的流式命令，**不是终端**（没有 job control、没有行编辑）；
- `subprocess.spawnTerminal(spec)` —— 描述原文是
  *"Allocate a real terminal and start one owned process session."*，
  返回 `{ pid, output: Readable, write(data), signalForeground(sig), terminate(), done }`。

这就是要的东西。还有个 `terminals` 服务（`spawn(owner, ...)` / `read` / `startSend`），
但它按 **Agent 归属**、读法是"拉一屏滚动文本"，不适合手机这种"一直挂着看"的用法，
所以选了更底层的 `subprocess.spawnTerminal`。

于是整条链路是：

```
手机终端页 ──POST /phone/term/<id>/input──▶ 桥接 ──handle.write()──▶ PTY(bash -l)
        ◀──SSE /phone/term/<id>/stream──── 桥接 ◀──handle.output──┘
```

### 25.3 四个必须处理的细节

**一、UTF-8 会被切开。** 一次 read 可能正好切在一个汉字中间。
桥接侧用一个 `TextDecoder` 实例反复 `decode(chunk, {stream:true})`（**不能**每次新建），
手机侧同理：`AnsiParser` 把半截转义序列留着，等下一块接上再解析。
（宿主没有 `Buffer`，但 Builtin 里有 `TextDecoder`。）

**二、PTY 尺寸是分配时定死的。** 没有 resize 接口，所以列数必须按手机屏幕
实际能放多少列来传：终端页用 `rememberTextMeasurer` 量一个等宽字符的宽度，
再除以可用宽度。实测小米 14 Pro 竖屏是 **54 列 × 47 行**。
列数传错的后果很直接：`ls`、表格、提示符全部折行。

**三、`TERM=dumb`。** 宿主给的基线环境是 `TERM=dumb`（实测），
后果是没颜色、全屏程序直接报错。
修法**不是**往 `spec.env` 里塞 `TERM` —— 那个字段的语义是"完全指定环境"，
只塞一个 TERM 有把 PATH/HOME 一起抹掉的风险（那就从"没颜色"变成"命令都找不着"）。
改成 argv 前面挂 `/usr/bin/env TERM=xterm-256color`：只覆盖指定的变量，其余原样传递。
`/usr/bin/env` 存不存在是先查一次 `fs.stat` 再决定的，不靠猜。

**四、手机切走时终端不能死。** 用户的用法就是在"会话 ↔ 终端"之间来回切。
所以：离开终端页只**断开输出流**，电脑上的 shell 留着；
桥接给每个终端留一段 96KB 滚动缓冲，重连时先发一帧 `hello.buffered` 把屏幕补全；
真没人要了由 20 秒一次的扫描回收（30 分钟无连接就关）。
**插件卸载时必须全杀** —— 否则 reload 一次就在宿主里漏一堆 bash。

### 25.4 手机侧的文本层：够用就好的 ANSI

`Ansi.kt` 里是一个**有状态的增量解析器**，不是终端模拟器：

- **认** SGR：粗体/暗色/下划线/反显 + 16 色、256 色、真彩色；
- **丢** 光标移动、清屏、OSC（starship 和 shell 集成会发 `\e]3008;...`）、私有模式 `?2004h`；
- `\r` = 重写当前行，`\b` 退格，`\t` 按 8 列制表位展开；
- 样式**跨行保留**（终端本来就这样）。

已知取舍：全屏 TUI（vim/htop）会显示成重绘残影，因为"回到第几行第几列"这类
光标寻址被丢掉了。要真支持得写完整的屏幕缓冲 + 光标模型，对"跑命令、看输出"
这个主用途不划算 —— 需要时再说。

### 25.5 一次真机字节救回来的 bug

合成用例（`hello\n`、`\e[31mred\e[0m`）**17 项全绿**的时候，我把一段真机抓下来的
字节喂进同一个 buffer：结果是**每一行都是空的**。

原因是 PTY 的行尾是 **CRLF**：`文字\r\n` 里的 `\r` 在 `\n` **之前**。
我原来"见到 `\r` 就清行"（为了进度条重绘），于是把这一行的内容在提交前抹掉了。
正确语义是：`\r` 只是"光标回第 0 列"，真正覆盖旧内容的是**回列之后又写来的字符**。
改成懒清行（`crPending`）后，进度条照样对，CRLF 也对了。

这条用例现在固化在 `tests/ansi/AnsiTest.kt` 里，跑 `scripts/test-offline.sh` 就会执行。
教训和 §22/§23 是同一个：**合成数据全绿 ≠ 对，必须拿真机/真进程的字节回放一遍。**

### 25.6 顺手修掉的第二个 UI 坑

功能键那排原本是"横向滚动的 Row"。实测在手机上启动后，
**第一个按钮被挤到屏幕左侧只露出 36px**，文字被裁掉 ——
无障碍树里那一行只剩一个没有文字的 36px 空按钮。
换成 `FlowRow` 自动换行后 12 个键全部可见可点。

顺带的原则：**藏在屏幕外、要滑一下才看得见的键，等于没有。**
（这也和 §24.4 一样：`uiautomator dump` 能把 Compose 的文字读出来，
比截图更适合做"有没有渲染出来"的验证，也不会把用户屏幕上的内容拍进上下文。）

### 25.7 深链（也方便无人值守验证）

```bash
# 直接落到终端页
adb shell am start -n com.dsh.phone/.MainActivity --es screen terminal
# 终端就绪后自动执行一条命令（PTY 是异步开出来的，会等 hello 到了再发）
adb shell am start -n com.dsh.phone/.MainActivity --es termSend "ls -l ~"
```

`screen=terminal` 走的是一个"请求计数器"（`terminalRequest`）：
冷启动和热启动（`onNewIntent`）共用一个入口，不必写两套。

### 25.8 验证

- **离线（不需要 harness / 手机）**：`scripts/test-offline.sh`
  - `tests/bridge/term-harness.mjs`：假 ctx + 真 `script`(PTY) 起一个 HTTP，
    打 `/phone/term/*` 全流程 —— 开、SSE、中文、大段输出、
    Ctrl-C（往 PTY 写 `\x03`，行规程会把它变成前台进程组的 SIGINT）、
    重连拿缓冲、close 杀掉真进程、`dispose` 杀干净。**15/15 通过**。
  - `tests/ansi/AnsiTest.kt`：解析器 + 行缓冲，含真机字节回放。**17/17 通过**。
- **在线**：`scripts/verify.sh` 增加"桥接版本 / 终端接口 / 离线验收"三组（15 项全过）。
- **手机上**：`--es screen terminal` 冷启动后，电脑侧 `/phone/term/list` 里出现
  一条 `cols=54 rows=47` 的真 PTY，`clients=1`；无障碍树里能看到渲染出来的
  starship 提示符、各功能键和输入框。

### 25.9 安全边界

终端 = 这台电脑上的一个**真 shell**。所以：

- `/phone/term/*` 和别的 `/phone/*` 一样，**无令牌 401**；
- 只经 `adb reverse`（USB）或 `tailscale serve`（tailnet only）到达，公网不可达；
- 令牌的强度就是这台电脑的强度 —— 它现在等价于 SSH 私钥，别往聊天里贴；
- APK 是 debug 自签名、只经 `adb install` 安装，不碰系统分区（与全程的硬约束一致）。

## 26. 排队消息：跑着的时候发的那几句去哪了

### 26.1 问题

harness 在跑（思考、调工具）的时候手机又发一条，它进的是会话的**待处理队列**，
要等这一轮跑完才执行。原来的界面什么都不显示 —— 用户的角度就是
"发出去了、没人理"，于是重复发一遍。

### 26.2 宿主已经给了答案，只是散在两个地方

查 Inspect 的 `sessionController` 契约，一次就找齐了：

| 接口 | 作用 |
| --- | --- |
| `control(signal)` | 一条**常驻流**：先给全量基线 `{queues, jobs, projections}`，之后推增量帧 |
| `updateQueue({sessionId, itemId, action})` | 改一条还没执行的：`{kind:'remove'}` / `{kind:'edit',content}` / `{kind:'steer'}` |
| `prompt({mode:'queue'\|'steer'})` | 发消息时就决定"排队"还是"插话" |

桥接做的事就是**镜像**：常驻消费 `control()`，把 `queues` 存下来，
一份供 `GET /phone/sessions/<id>/queue` 查询，一份在变化时推给正在看这个会话的手机
（事件名 `queue`）。不让手机自己去拉 `control()` 的理由很实在：
那是一条长期流，手机一断线状态就丢了；桥接本来就常驻，多镜像一份最省事。

### 26.3 三个容易错的点

1. **段数**。桥接的 `segments()` 会先剥掉 `/phone`，所以
   `/phone/sessions/<id>/queue` 是 **3** 段而不是 4 —— 写多一层会静默落到
   后面的通用分支，报一个"unknown session action: queue"，看着像没实现。
2. **乐观更新**。点「撤回」先在本地把这条拿掉（点下去立刻有反馈），
   权威值随后由 `control()` 推回来覆盖。否则网络一个来回，用户以为没点上。
3. **`QueueAction` 的形状**。三种 action 的字段名各不相同，拼错**不会报错**，
   只会静默不生效。所以离线测试专门断言发出去的 JSON 长什么样
   （`tests/bridge/queue-harness.mjs`）—— 拿假 ctx 推一帧 baseline、一帧增量，
   看镜像对不对、推给手机了没有、updateQueue 收到的是什么。

## 27. 手机上真的能编辑文件了：把终端从"行"改成"屏幕"

### 27.1 第一版为什么不行

需求是"在手机上开终端，`vim test.md` 能顺手改文件"。第一版把 PTY 输出当
**一行行往下写的文本**（见 §25.4）。这有三个后果，用户全撞上了：

1. 全屏程序靠光标寻址反复重绘同一块区域 —— 行式渲染画出来是**残影**；
2. **光标位置根本不知道**，所以没法"滚到你正在编辑的那一行"，
   软键盘一弹就把正在打字的那行盖住；
3. 看起来是"Tab 补全有 bug"：其实 Tab 发出去了、补全也回来了，
   只是补全列表用 `\r` + 光标移动重绘，被行式渲染吃掉了。

所以真正的修法是**把"行"换成"屏幕"**：cols × rows 的格子 + 光标。

### 27.2 `TermScreen`：够用的 VT100

`TermScreen.kt` 是一块真正的屏幕缓冲区。支持到什么程度不是拍脑袋定的，
是按 **vim / nano / htop / less 实际会发什么**倒推的：

| 类别 | 支持 |
| --- | --- |
| 光标 | CUP/HVP、A/B/C/D/E/F、G/CHA、d/VPA、CR/LF/BS/HT、`ESC7/8`、`CSI s/u` |
| 擦除 | ED(J)、EL(K)、ECH(X)、删字符(P)、插字符(@)、删行(M)、插行(L) |
| 滚动 | 滚动区域 DECSTBM(r)、S/T、到底自动上滚 |
| 备用屏 | `?1049` / `?1047` / `?47` —— 进出全屏程序时主屏历史留得住 |
| 其它 | 自动换行（`?7`，含**延迟换行**语义）、`ESC(0` 制表符映射、宽字符占两列、`?25` 光标可见性 |

明确不做：鼠标上报、完整字符集表、真 24 位光标形状。
判断标准是"跑命令、编辑文本够不够"，不是"能不能过 vttest"。

### 27.3 界面跟着屏幕模型一起改

- **进全屏程序自动换输入方式**（`TermState.fullScreen` = 备用屏中）：
  - 命令行模式：输入框写好一行再发送（中文输入法能组词、联想、纠错）；
  - 全屏模式：**逐键直通** —— 隐藏发送框，手机原生输入法打字，
    输入法一提交就把内容发进 PTY 并清空挂钩框。这样中文能组词，
    而 vim 收到的是逐个按键。
  - 多一排电脑上才有的键：Esc / ⏎ / Tab / ⌫ / 方向键 / **Ctrl 锁存**（Ctrl 亮起后按一个键 = 那个控制字符）/ `:` `/` `|` `-` / 粘贴。
- **滚动跟着光标走**，不是跟着最后一行走 —— 这是"键盘盖住正在编辑那行"的根治办法。
- **行不软换行**：PTY 的列数是按屏宽算好的，软换行会把下面所有行挤下去、
  全屏网格当场错位。宁可裁掉超出的最后几个字符。

### 27.4 一个必须记住的语义：裸 LF 不回列

改完屏幕模型，40 项测试里挂了 6 项，全是同一个原因：
**测试数据里写了裸 `\n`**。VT 里 `LF` 只下移一行、**保留列**，
回列是 `CR` 的事；真 PTY 的行尾是 **CRLF**（行规程的 ONLCR 会把程序的 `\n`
翻译成 `\r\n`）。所以我实现的没错，是测试在按"行式"的旧直觉写。
这类"测试数据与真机字节不一致"的坑，这个项目已经踩到第三次了（§25.5 的 CRLF那次）。
现在的规矩：**屏幕相关的用例一律用 CRLF**，并单独留一条用例把
"裸 LF 只下移不回列"的语义钉住，防止以后有人"顺手"改成换行。
